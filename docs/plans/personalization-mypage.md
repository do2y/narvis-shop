## 1. 무엇을 만드는가

`/mypage/preferences` — "AI가 이해한 내 취향" 화면 하나.

- 요약 문단(`markdown`) · 개인화 ON/OFF · 전체 초기화
- 관계 5종(선호·좋아함·회피·관심·구매)으로 묶인 취향 항목 트리
- 항목별 수정(✏️)·삭제(🗑)
- 화면 상태 5종: 로딩 / 정상 / 빈 상태 / 개인화 OFF / 오류

**핵심 제약** — 최대 200개가 페이지네이션 없이 한 번에 옴. 그룹당 12개 + `+N개 더`로 자름.

이미 있는 것을 그대로 쓴다. 새로 만들지 않는다.

| 인증 게이팅 | `selectIsAuthReady` — 쿼리 `enabled`에 필수 |

## 4. 상태 관리 설계

### 4.1 `graphVersion` — 가장 위험한 축

모든 성공 응답에 들어 있고, 갱신을 빠뜨리면 **다음 요청이 전부 409**가 된다.

> **결정: 별도 state로 들고 다니지 않고 React Query 캐시 한 곳에서만 읽는다.**
> 뮤테이션 성공 시 `setQueryData(['profile','graph'], …)`로 캐시의 `graphVersion`을 갱신하면
> 보관값이 물리적으로 한 벌만 존재하게 되어 "갱신을 빠뜨리는" 실수 자체가 불가능해진다.
> useState로 복제하면 갱신 지점이 4곳(수정·삭제·초기화·개인화)으로 흩어진다.

쿼리 키: `['profile', 'graph']` (CLAUDE.md 소문자 세그먼트 컨벤션)
staleTime: 0 — 서버가 원본이고 버전 충돌이 있는 데이터라 캐시를 오래 붙들면 안 된다.

### 4.2 `edgeId` 교체 — 두 번째로 위험한 축

수정하면 `edgeId`가 바뀐다. React key로 쓰는 구현이 특히 위험(화면은 멀쩡한데 다음 요청만 404).

> **결정: 뮤테이션 성공 핸들러에서 응답 `data.edge`로 캐시의 해당 edge를 통째로 교체한다.**
> 낙관적 업데이트를 쓰지 않는다 — 서버가 라벨을 정규화하고 병합까지 할 수 있어
> 낙관적으로 그린 결과와 실제 결과가 다를 수 있다.
> `merged: true`면 캐시 조작을 포기하고 M-11 재조회(`invalidateQueries`).

### 4.3 409 분기 — `error.code`로 갈라야 함

```
409 PROFILE_VERSION_CONFLICT   → 재조회하면 풀림
409 PROFILE_EDGE_NOT_EDITABLE  → 몇 번을 해도 안 됨 (M-12만)
```

HTTP 상태로만 보면 정반대 대응이 섞인다. `ApiError.code`로 분기.

동작별 재시도 정책:

| 동작 | 재조회 | 자동 재시도 | 중단 조건 |
| --- | --- | --- | --- |
| 삭제 | O | **O (1회)** | 재조회 후 그 `edgeId`가 없으면 **중단** |
| 수정 | O | X | — |
| 초기화 | O | X | — |

401 재시도와 409 재시도는 **카운터를 각각** 둔다(겹칠 수 있음).

## 5. 마크다운 자체 렌더 (SummaryMarkdown)

LLM이 만든 문자열이라 신뢰 경계 밖이다. **HTML을 파싱하지 않는 것**이 방어 전략.

허용 문법만 처리하고 나머지는 평문 취급:

| 문법 | 처리 |
| --- | --- |
| `# ~ ###` | `<h3>`~`<h5>` (페이지 제목과 위계 충돌 방지로 한 단계 낮춤) |
| `- ` / `* ` | `<ul><li>` |
| `**bold**` | `<strong>` |
| 그 외 | 평문 |

- `dangerouslySetInnerHTML`을 **쓰지 않는다** → 원문에 `<script>`가 있어도 그냥 글자로 나감
- 링크·이미지도 미지원 (계약에 없고, 열어주면 피싱 표면이 됨)
- 파서는 순수 함수로 분리해 vitest로 테스트 (`parseSummary.test.ts`)

## 6. 트리 렌더 (1단계)

노션 10.2의 **세로형 트리를 전 해상도에 적용**한다. 방사형은 2단계.

```
  선호 24  ├─ ● 3~5만원대       ✏️  🗑
           ├─ ● 노이즈캔슬링    ✏️  🗑
           └─ + 22개 더

  좋아함 8 ├─ ● 광택            ✏️  🗑

  회피 0    (아직 없어요)
  구매 0    (아직 없어요)
```

규칙(노션 확정 사항 그대로):

- **서버 정렬 순서 그대로** — 클라이언트 재정렬 금지
- 그룹당 **12개** + `+N개 더` → 그 그룹만 포커스 모드(바깥 클릭·ESC 복귀)
- **접기/펼치기 없음** — 처음부터 전부 전개
- 빈 그룹(회피·구매)은 지우지도 강조하지도 않고 "아직 없어요"로 자리만
- 관계 5색 전부 **중립 채도** — 회피에 빨강·경고색 금지
- `nodeId` 대신 `label` 표시
- `derivedFromSensitive`에 **시각적 차이 없음**
- `unprojectedCount` 노출 금지, "숨겨진 항목 N개" 금지

배지 매핑:

| 필드 | 표시 |
| --- | --- |
| `confidence` | 크기 3단계 + 텍스트("확실해요"/"그런 것 같아요"/"아직 확실하지 않아요") — 색만으로 전달 금지 |
| `origin: "user"` | 테두리 강조 + "내가 수정함" |
| `verified: false` | 점선 테두리 |
| `editable: false` | 🔒 + ✏️ 비활성 (🗑은 **활성**) |
| `challenged: true` | 느낌표 배지 (색 변경 없음) |
| `truncated: true` | 목록 하단 안내 |

**접근성**: 트리 컨테이너는 `aria-hidden`, `ScreenReaderList`를 sr-only로 병행. 이게 없으면 스크린리더에 화면이 통째로 비어 보인다. 아이콘엔 `aria-label="수정"`·`"삭제"`, 터치 타겟 44×44px, 아이콘 간격 16px 이상, ✏️ 왼쪽 / 🗑 오른쪽.

> ⚠️ CLAUDE.md의 radius 2단계(`rounded-full` / `rounded-sm`)와 토큰 색상만 사용.
> 관계 5색은 기존 팔레트로 표현이 안 되면 **토큰 추가를 먼저 제안**한다(임의 값 금지).

## 7. 확인 다이얼로그

```
되돌릴 수 있나?
  ├── 예   → 확인 없음  (수정 · 개인화 ON/OFF)
  └── 아니오 → 확인 필수  (삭제 · 전체 초기화)
```

**삭제 확인창**
- 제목에 **항목 이름 포함** — "○○를 삭제할까요?"
- **"되돌릴 수 없습니다" 문구 필수**
- 기본 포커스 **[취소]**, `role="alertdialog"`
- [삭제]와 [취소]를 시각적으로 구분하고 붙여두지 않기

**전체 초기화 확인창** — 한 단계 더 무겁게
- 삭제 대상 개수 나열 (취향 N건 · 대화 기록 N건)
- **"대화 기록을 포함한"** 명시 — 가장 놓치기 쉬운 부분
- 버튼 문구 "초기화"가 아니라 **"모두 삭제"**
- 성공 후 `purged` 개수로 결과 안내

> 개수를 확인창에 띄우려면 M-11에 취향 수는 있지만 **대화 기록 수(`transcriptTurns`)는 없다.**
> 계약상 `purged`(응답)에만 존재 → **사전 개수는 취향만 정확히 표시하고 대화 기록은
> 개수 없이 "대화 기록 전체"로 문구 처리한다.** 계약에 없는 필드를 임의로 만들지 않는다.
> (BE 협의 시 사전 카운트 필드를 요청할 항목으로 기록)

## 8. 개인화 ON/OFF

- `PUT /api/profile/personalization` · `If-Match` 없이 · 연타 허용(`replayed`)
- 끄면 **꺼짐 배너** 표시 — 특히 "'기억해'라고 말해도 저장되지 않아요"를 반드시 포함
- 끈 직후 토스트: "개인화를 껐어요. **홈 화면 반영까지 몇 분 걸릴 수 있어요.**"
  → "즉시 반영"을 약속하지 않는다(서버 캐시 10분)
- **OFF여도 조회·수정·삭제·초기화가 전부 동작해야 한다.** 편집 잠금 금지
- 그래프는 채도만 낮추고 **숨기지 않는다**

## 9. 절대 만들지 않는 것 (노션 7장)

- 휴지통 / "최근 지운 항목" / **실행취소 토스트** / "다시 묻지 않기" 체크박스
- "숨겨진 항목 N개" 개수 표시
- `derivedFromSensitive` 시각적 구분
- 원본 발화를 보여주는 "왜 이 취향이 있나요"
- "몇 번 말했는지" 횟수 표시
- **취향을 검색 필터로 변환** (`usagePolicy.filterSafe: false`는 분기용 값이 아니라 표지판)
- 요청에 회원 id 담기 (IDOR)
- `nodeId` 화면 노출

## 10. 목(mock) 전략

`mock.ts`에 계약 그대로의 응답 픽스처를 두고 `api.ts`에서 스위치.

준비할 픽스처 — 노션 9장 시나리오 12개가 전부 재현되어야 한다:

1. 정상(취향 24/8/5, 회피·구매 0)
2. `exists: false` (신규 회원)
3. `edges: []`
4. `personalization.enabled: false`
5. 200개 + `truncated: true`
6. `editable: false` 포함
7. 수정 → `edgeId` 변경 응답
8. 수정 → `merged: true`
9. 409 `PROFILE_VERSION_CONFLICT`
10. 409 `PROFILE_EDGE_NOT_EDITABLE`
11. 삭제 409 → 재조회 시 edgeId **있음** / **없음** 두 갈래
12. `replayed: true`

## 12. 결정이 필요한 것 (BE·기획 확인 대기)

노션 12장 미확정 항목 중 **FE 진행을 막는 것**:

| 항목 | 영향 | 지금 대응 |
| --- | --- | --- |
| API 5종 초안 | 경로·필드 변동 가능 | 목으로 진행, `api.ts`·`types.ts`에 격리 |
| `markdown` 필드 (AI 계약 I-32에 없음) | 요약 문단 데이터 소스 | **온다고 전제**(노션 확정) + `null` 대비 분기 |
| 초기화 확인창의 사전 개수 | 대화 기록 수를 못 보여줌 | 취향 수만 표시, BE에 카운트 필드 요청 |
| **마이페이지에 수정·삭제를 두는 것 자체** | 🔴 기존 결정은 "조회 전용", 기획 승인 대기 | **이 화면 전체의 전제** — 승인 전이면 헛일이 될 수 있음 |
| 브랜드 통제 어휘 부재 | `brand` 항목이 추천에 반영 안 됨 | 화면은 만들되, 실효성 이슈로 기록 |
| 비로그인 접근 | 게스트 진입점 노출 여부 | 로그인 필수로 가정(`RequireAuth`) |

> **가장 큰 리스크는 마지막에서 두 번째 줄 위의 항목이다.** "마이페이지에 수정·삭제를 두는 것"이
> 기획 승인 대기 상태라 뒤집히면 이 계획서의 5·6·7단계가 통째로 사라진다.
> 착수 전에 이 건의 승인 여부를 먼저 확인하는 것을 권한다.
