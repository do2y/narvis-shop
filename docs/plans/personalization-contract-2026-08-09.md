## 0. 세 줄 요약

- API 5종은 **확정됐다.** 초안 딱지("🔴 BE 협의 중")는 낡은 정보다 — 구현 근거로 써도 된다.

## 1. 이 화면이 무엇인가

**"AI가 이해한 내 취향"** — AI가 대화에서 학습한 취향을 사용자가 확인하고 고치는 화면.

기존에는 취향 프로필이 **편집 불가능한 마크다운 한 덩어리**라 잘못 학습된 취향("소니 선호"인데 사실은
회피)을 사용자가 고칠 방법이 없었다. 같은 데이터를 **항목 단위(edge)로 쪼개** 반환해 개별 수정·삭제를
가능하게 한 것이 이번 계약이다.

성격은 기능 화면보다 **프라이버시 제어판**에 가깝다 — 조회 / 수정 / 삭제 / 전체 초기화 / 개인화 ON·OFF.

> **채팅으로는 취향을 변경할 수 없다.** "내 취향 지워줘"에는 AI가 "마이페이지에서 하세요" 안내만 한다.
> 저장은 되돌릴 수 있고 삭제는 못 되돌리니, 삭제는 화면에서 명시적으로 받는다.
> 무반응은 안 된다 — 아무 말이 없으면 사용자는 지워진 줄 안다.

## 2. API 5종

FE는 AI 서버를 직접 부르지 않는다. **Spring이 프록시한다** (M-xx = FE 대면 / I-xx = internal).

| API | Method · Path | `If-Match` | 프록시 대상 |
| --- | --- | --- | --- |
| **M-11** 조회 | `GET /api/profile/graph` | — | I-32 |
| **M-12** 수정 | `PATCH /api/profile/graph/edges/{edgeId}` | **필수** | I-33 |
| **M-13** 삭제 | `DELETE /api/profile/graph/edges/{edgeId}` | **필수** | I-34 |
| **M-15** 초기화 | `POST /api/profile/graph/reset` | **필수** | I-36 |
| **M-16** 개인화 | `PUT /api/profile/personalization` | 선택 | I-37 |

공통 규약:

- 인증 `access_token` 쿠키 · **`USER` 역할 전용** (SELLER·ADMIN은 403 `AUTH_FORBIDDEN`)
- **회원 id를 요청에 담지 않는다** — 경로·쿼리·본문 어디에도. 서버가 세션에서만 도출한다 (IDOR 방지)
- 봉투 `{success, data}` — 실제 값은 `res.data.graphVersion`
- **M-14(되돌리기)는 폐기.** 번호가 빈 것이지 누락이 아니다

> 우리 [client.ts](../../src/shared/api/client.ts) 인터셉터가 봉투를 이미 벗기고 401 재시도도 처리한다.
> 화면 코드에서 중복 구현하지 말 것.

### M-11 조회 — 응답 (확정본)

```json
{
  "success": true,
  "data": {
    "userId": 123,
    "exists": true,
    "markdown": "# 취향 요약\n- 3~5만원대 무선 이어폰 선호\n...",
    "generatedAt": "2026-08-04T21:10:00Z",
    "graphVersion": "g42",
    "personalization": { "enabled": true },
    "edges": [
      {
        "edgeId": "e_2f80d1aa63b74c19",
        "predicate": "avoids",
        "object": { "nodeId": "brand:소니", "type": "brand", "label": "소니" },
        "editable": true,
        "challenged": false
      }
    ]
  }
}
```

- **`nodes[]` 배열이 없다.** 대상은 edge 안에 `object`로 인라인된다 — 대상당 항목이 사실상 1개라
  정규화 이득이 없고, 조인이 없으면 "라벨 없는 항목·항목 없는 라벨"이 원리적으로 생기지 않는다.
  요청(M-12)의 `object`와 모양이 같아 **항목을 그대로 수정 요청에 재활용**할 수 있다.
- **`edges`는 전량 실린다 — 서버 화면 상한이 없다.** 서버가 자르면 상한 밖 항목을 사용자가
  보지도 지우지도 못해(전체 초기화 말고는 정리 수단이 없어짐) 화면 목적과 정면으로 부딪힌다.
  화면 부담은 **FE가 처음 N개만 렌더하고 "전체 보기"로 펼치는 방식**으로 푼다.
- `markdown`은 **배치(sleep-time consolidation) 산출물**이라 항상 최신이 아니다. `generatedAt`이 기준 시각.
- `exists: false`는 **오류가 아니라 신규 회원의 정상 상태**이고 HTTP 200이다.

### 관계 5종

정렬은 **서버 고정**이다 — `prefers` → `likes` → `avoids` → `interestedIn` → `purchased`,
그 안에서 최근 확인 시각 내림차순 → `edgeId` 오름차순(전순서 보장). **클라이언트 재정렬 금지.**

| `predicate` | 라벨 | 뜻 | 수정 |
| --- | --- | --- | --- |
| `prefers` | 선호 | 비교 선호 — 다른 것 대신 이것 | 가능 |
| `likes` | 좋아함 | 단순 긍정 | 가능 |
| `avoids` | 회피 | 명시적 회피 (**당분간 항상 빈 배열**) | 가능 |
| `interestedIn` | 관심 | 최근 관심 (시간 지나면 약해짐) | 가능 |
| `purchased` | 구매 | 구매 사실 (**당분간 항상 빈 배열**) | **불가** |

**노드 타입 7종** — `brand` / `category` / `attribute` / `priceBand` / `ratingBand` / `product` / `situation`

> `avoids`·`purchased`가 비는 것은 **생산 경로가 아직 없어서지 사용자 탓이 아니다.**
> 지우면 "회피를 등록 못 하나?" 오해가 생기고, 강조하면 오류처럼 보인다.
> **"죽은 가지"가 아니라 "아직 안 자란 것"으로** 읽히게 자리만 지킨다.

## 3. ⚠️ 초안 → 확정본에서 사라진 필드

기존 계획서 두 건은 아래 필드를 전제로 화면을 설계했다. **확정 응답에는 없다.**

| 초안이 쓰겠다던 것 | 확정 명세 | 화면 영향 |
| --- | --- | --- |
| `nodes[]` 별도 배열 | 없음 — `object` 인라인 | 룩업 맵 불필요 |
| `to` 로 노드 참조 | 없음 — `object.label` | — |
| `confidence` (HIGH/MEDIUM/LOW) | **없음** (C-25) | 크기 3단계·확신도 문구 **불가** — 요청 안 함(§3.1) |
| `source` | **없음** | "대화에서 알게 되었어요" **불가** — 요청 안 함(§3.1) |
| `lastConfirmedAt` | **없음** (정렬에만 사용) | "최근 확인 7월 29일" — 📮 **이것만 요청함**(§3.1) |
| `origin: "user"` | **없음** | "내가 수정함" 배지 → **1단계에서 두지 않음**(§3.1) |
| `verified: false` | **없음** | 점선 테두리 **불가** — 요청 안 함(§3.1) |
| `derivedFromSensitive` | **없음** | (금지 규칙 자체는 유지) |
| `usagePolicy.filterSafe` | **없음** | 표지판이 사라졌을 뿐, **필터 금지 규약은 유효** |
| `unprojectedCount` | **없음** | — |
| `truncated` · 서버 200개 상한 | **없음 — 전량 전송** | **그룹당 12개의 근거가 사라짐**. 상한은 FE가 다시 정함 |
| `purged.nodes` · `purged.facts` | `edges` · `transcriptTurns` 둘뿐 | 초기화 결과 문구 조정 |
| `personalization.disabledAt` | **없음** | 중지 시각 표시 불가 |

명세의 근거(I-32):

- 관측 횟수(`evidenceCount`)는 **셀 수가 없다** — 세션 버퍼 반복 상한(`profile_buffer_repeat_cap = 2`)이
  같은 발화를 2회로 자른다. 그래서 확신도(`confidence`)도 응답에 싣지 않았다.
- 응답 필드 기준은 **"FE가 화면에 그리거나 다음 요청에 되돌려 보낼 값만"** 이다.
  절단·검증·랭킹 반영 여부 같은 **AI 내부 판단 상태는 AI 안에 둔다.**

> 그런데 명세가 **탈출구를 명시해 뒀다**:
> *"FE 기획이 근거 표시(출처·최근 확인 시각)나 확신도를 화면에 쓰기로 하면 **요청 시 추가한다** —
> 저장 모델에 남아 있어 추가는 계약을 깨지 않는다(🟡 C-25, **FE 소유**)."*
>
> **즉 이건 FE가 요청만 하면 되는 건이다.** 안 하면 화면은 라벨 + 관계 그룹만 남는다.

### 3.1 요청 결정 (2026-08-10) — `lastConfirmedAt` 1개만

**구현 시간이 부족하다.** 남의 응답을 기다려야 진행되는 구조를 만들지 않는다 —
**없으면 없는 대로 완결되는 화면**을 만들고, 값이 오면 표시만 얹는다.

노션 요청서: [📮 I-32 응답에 lastConfirmedAt 하나만 추가 가능할까요?](https://app.notion.com/p/3b75ca79037b8145bf45fffa9d72e38c)

| 필드 | 결정 | 이유 |
| --- | --- | --- |
| `lastConfirmedAt` | 📮 **요청**(급하지 않음) | **삭제 판단의 유일한 재료.** 아래 |
| `source` | ❌ 요청 안 함 | **값이 `conversation` 하나로 몰린다** — `purchase`는 `purchased`가 빈 배열이라 안 오고, `user`는 수정 기능(2단계)이 있어야 의미가 생긴다. 전부 같은 값이면 정보가 아니라 노이즈다 |
| `origin` | ❌ 요청 안 함 | `source: "user"` 와 중복(I-33 규약). 수정 확인은 **직후 토스트**로 대신한다 |
| `confidence` | ❌ 요청 안 함 | 관측 횟수를 못 세서 뺀 값이라 근거가 약하고, "아직 확실하지 않아요"는 고칠 이유가 아니라 **지울 이유**로 읽힌다 |
| `verified` | ❌ 요청 안 함 | 사용자에게 아무 행동도 유발하지 않는 내부 사정 |
| `derivedFromSensitive` | ❌ 요청 안 함 | 어차피 시각적 차이를 두면 안 되는 값이라 쓸 곳이 없다 |

**`lastConfirmedAt`만 남긴 근거** — 이 화면에 온 사용자의 목적은 "잘못 들어간 취향 정리"인데,
날짜가 없으면 항목이 전부 똑같아 보여서 **뭘 지울지 고를 기준 자체가 안 생긴다.**
특히 `interestedIn`은 명세상 *"시간이 지나면 약해지는"* 관계인데 시간 정보가 없으면
그 성질이 화면에 전혀 드러나지 않는다. 이미 **정렬 키로 쓰는 값**이라 AI팀 부담도 작다.

> **필드가 없어도 화면은 성립한다** — `markdown` 요약 문단(A영역)이 "AI가 나를 이렇게 이해했다"를
> 담당하고, 그래프는 "그래서 뭘 지울까"를 담당한다. 역할이 갈려 있어 한쪽이 없다고 무너지지 않는다.
>
> **"내가 수정함" 배지는 1단계에서 두지 않는다.** 수정 기능 자체가 2단계이고,
> 수정 직후 확인은 토스트로 충분하다. 2단계에서 `source`가 필요해지면 그때 요청한다.

## 4. 놓치면 버그 나는 것 5가지

### 4.1 ★ 수정하면 `edgeId`가 바뀐다

```
수정 전: e_7b1c9a04e5f2438d
수정 후: e_9d41c7b0e8a2f356   ← 값이 달라짐
```

식별자가 `(관계, 대상)` 파생이라 둘 중 하나만 바꿔도 새 값이다. **응답 `data.edge.edgeId`로
클라이언트 키를 반드시 교체**해야 하며, 안 하면 **다음 수정·삭제가 전부 404**다.

React 리스트 key를 `edgeId`로 쓰는 구현이 특히 위험하다 — 갱신을 빠뜨리면 **화면은 멀쩡한데
다음 요청만 실패**해서 원인을 찾기 어렵다.

> **랜덤 id를 안 쓰는 이유**: 재파생 때 새 id로 부활해 삭제 표식을 비켜가기 때문이다.

### 4.2 ★ 모든 성공 응답의 `graphVersion`을 갱신

안 하면 다음 요청이 전부 409다. `graphVersion`은 **불투명 문자열** — 파싱·크기 비교·순서 추론 금지,
받은 값을 그대로 `If-Match`에 싣기만 한다.

**요청은 헤더, 응답은 본문이 정규다.** 응답 헤더 `ETag`는 CORS 때문에 브라우저 JS가 못 읽는다.
`If-Match: "g42"` 와 `If-Match: g42` 는 동등하고, `*`·약한 태그(`W/"g42"`)·누락·빈 값은 **400**이다.

### 4.3 ★ 409가 두 종류고 대응이 정반대

| code | 대응 |
| --- | --- |
| `PROFILE_VERSION_CONFLICT` | 재조회하면 풀림 |
| `PROFILE_EDGE_NOT_EDITABLE` | 몇 번을 해도 안 됨 (M-12 전용, 구매 파생) |

**HTTP 상태로만 분기하면 틀린다. 반드시 `error.code`로 갈라야 한다.**

409 응답에는 최신 버전이 동봉된다(`error.detail.graphVersion`). 다만 **재조회(M-11)를 권한다** —
버전만 갈아끼우면 화면은 여전히 옛 내용이라, 사용자가 보는 정보가 틀린 채로 요청이 나간다.

### 4.4 409 처리 — 삭제만 자동 재시도

| 동작 | 재조회 | 자동 재시도 | 이유 |
| --- | --- | --- | --- |
| **삭제** | O | **O (1회)** | 대상이 `edgeId`로 고정돼 결과가 안 바뀜 |
| **수정** | O | X | 병합 여부에 따라 결과가 달라짐 |
| **초기화** | O | X | 범위 자체가 달라짐 |

기준은 **"의도가 상태 변화에 흔들리는가"** 다.

- **삭제 자동 재시도 중단 조건** — 재조회했을 때 그 `edgeId`가 **없으면 중단**한다.
  그 사이 내용이 바뀌었다는 뜻이라 밀어붙이면 사용자가 의도하지 않은 걸 건드린다.
- **자동 재시도 금지 ≠ 사용자가 다시 못 함.** 수정·초기화는 *FE가 알아서 보내지 말라*는 뜻이지,
  사용자가 화면을 보고 다시 누르는 건 정상 경로다.
- **재시도는 1회까지.** 두 번 연속 실패하면 다른 일이 벌어지는 것이니 사용자에게 보여준다.
- 409 재시도와 401(토큰 만료) 재시도는 **카운터를 각각** 둔다 — 둘 다 "1회 재시도"지만
  다시 보내는 내용이 다르고 겹칠 수 있다.

### 4.5 멱등 — 통신이 끊겨도 재전송이 안전하다

같은 요청을 그대로 다시 보내면 `replayed: true`로 최초 응답이 돌아온다.
멱등 키가 `If-Match`를 겸한다(파생 키 `profile-graph-{동작}:사용자:대상:If-Match`).

> **결과가 200이면 "이미 삭제됨"이 아니라 "삭제 성공"으로 처리한다.** 확인창을 다시 띄우면 안 된다.
> 멱등 판정이 edge 존재 여부가 아니라 파생 키 기준이라, 원문이 물리 삭제된 뒤여도 200이다.
> 단 새로 조회한 뒤 다시 삭제하면 `If-Match`가 달라져 404다 — 이건 404가 맞다.

### 4.6 `merged: true` — 재조회

수정한 내용이 기존 항목과 합쳐진 것. 목록에서 항목 하나가 사라진 것처럼 보이므로 **M-11 재조회**.

## 5. 화면 구성

```
┌──────────────────────────────────────────────────┐
│ A. 요약 문단 (좌상단)      B. 컨트롤 (우상단)     │
│   markdown 렌더             개인화 [●ON]          │
│   "3~5만원대 무선 이어폰을   [ 전체 초기화 ]      │
│    선호하시고…"                                   │
├──────────────────────────────────────────────────┤
│              C. 그래프 (2단 트리)                  │
│                    선호 24                        │
│           ┌───────────┼───────────┐              │
│           ●           ●           ●              │
│      3~5만원대  노이즈캔슬링    무선              │
│        ✏️ 🗑       ✏️ 🗑       ✏️ 🗑  ← D. 항목 아이콘 │
└──────────────────────────────────────────────────┘
```

| | 영역 | 내용 |
| --- | --- | --- |
| **A** | 요약 문단 | `markdown` 렌더 — **HTML 비허용**(LLM 생성물) |
| **B** | 컨트롤 | 개인화 ON/OFF 스위치 · [전체 초기화] |
| **C** | 그래프 | `나 → 관계 5종 → 취향 항목` 2단 트리 |
| **D** | 항목 아이콘 | 항목 아래 ✏️(수정) 🗑(삭제) |

### 왜 2단 트리인가

**옵시디언 스타일 노드 그래프는 이 데이터로 못 만든다.** 모든 관계가 `나 → 대상` **한 방향·한 단계**이고
대상끼리 연결된 데이터가 없다. 출발점(`from`)을 응답에 일부러 넣지 않은 것도 같은 이유다 —
항상 "나"라서 중복이고, 넣으면 "여러 단계로 이어진 그래프"라는 잘못된 신호가 된다.
force-directed를 돌리면 중심 하나에 점이 매달린 방사형만 나온다. **그래프처럼 보이지만 목록보다 정보가 적다.**

데이터에 실제로 있는 중간 단계는 **관계 5종**뿐이라, 그걸 가지로 쓴다.
서버가 이미 관계 기준으로 정렬해 보내주므로 **재정렬 없이 그대로 그릴 수 있고**,
사용자가 고치고 싶어하는 축도 관계다("이건 싫어하는 건데").

- 5개 중 2개가 항상 비므로 **균등 72° 배치 금지** → **항목 수에 비례해 각도 배분**,
  데이터 많은 그룹은 위·양옆, 빈 그룹은 아래쪽 작게·흐리게
- **접기/펼치기 없음** — 화면 목적이 "확인하고 고치기"인데 접혀 있으면 확인에 클릭이 더 든다
- 모바일 768px 미만은 **세로형 트리** (목록이 아니라 같은 트리를 눕힌 것)

### 화면 상태 5가지

| 상태 | 조건 | 화면 |
| --- | --- | --- |
| **로딩** | M-11 대기 | 중심 + 가지 5개 스켈레톤 |
| **정상** | `exists: true` + edges 있음 | 기본 화면 |
| **빈 상태** | `exists: false` **또는** `edges: []` | "아직 파악한 취향이 없어요 — 채팅으로 쇼핑을 시작하면 여기에 쌓여요."<br>**스위치·[전체 초기화]는 그대로 보임** |
| **개인화 OFF** | `personalization.enabled: false` | 그래프 채도만 낮춤(**숨기지 않음**) + 상단 배너<br>**편집 기능은 전부 그대로 동작** |
| **오류** | M-11 실패 | 오류 안내 |

> **개인화가 꺼져 있어도 조회·수정·삭제·초기화가 전부 가능해야 한다.**
> "개인화를 켜야 편집할 수 있습니다" 같은 화면을 만들지 말 것 —
> 보존된 데이터를 정리하려고 개인화를 다시 켜야 하는 상황은 만들지 않기로 했다.

## 6. 컨트롤별 동작

### 확인 다이얼로그 판단 기준

```
되돌릴 수 있나?
  ├── 예   → 확인 없음  (수정 · 개인화 ON/OFF)
  └── 아니오 → 확인 필수  (삭제 · 전체 초기화)
```

수정에 확인창을 두지 않는 이유: ① [저장]을 누르는 것 자체가 확인 단계이고 ② 잘못 고쳐도
**결과가 화면에 보여** 바로 다시 고칠 수 있다. 삭제는 지우는 순간 뭐가 있었는지 사라진다.

> **✏️ · 🗑 · [전체 초기화]는 그 자체로 서버를 호출하지 않는다.** 연필은 수정 창을, 휴지통과
> 초기화는 확인창을 열 뿐이다. 실제 호출은 **[저장] · 확인창의 [삭제] · [모두 삭제]** 에서 일어난다.

### M-16 개인화 ON/OFF

- 확인창 없음 · 연타 허용(`replayed: true`로 정상 200) · `If-Match` 안 보내도 됨
- **`If-Match`가 선택인 유일한 API다** — 토글은 마지막 의사가 이기는 게 자연스럽고,
  **프라이버시 스위치가 백그라운드 작업 때문에 잠기는 설계는 틀렸다**
- 끄면 무슨 일이 일어나는지 반드시 알린다:

| | 중지 중 |
| --- | --- |
| 추천 | 개인화 안 함 (일반 추천으로 대체) |
| 새 취향 수집 | 중단 |
| **채팅의 "기억해" 요청** | **저장되지 않음** ← 이걸 모르면 사용자가 배신감을 느낀다 |
| 기존 데이터 | **보존** (재개하면 복원) |
| 이 화면 | **그대로 보이고 편집도 된다** |

- **중지 기간의 발화는 재개해도 소급 반영하지 않는다** — 전사록에서 백필하면 "수집 중지"를
  사후에 위반하는 것이다. 누락이 아니라 규칙이다
- **"즉시 반영"을 약속하지 말 것** → "홈 화면 반영까지 몇 분 걸릴 수 있어요" (P-5 캐시 10분)

### M-12 수정

- 팝오버(모바일은 바텀시트) · **수정 중인 항목을 가리지 않게** · 화면 밖이면 반대쪽으로 뒤집기
- 관계 선택지: 선호 / 좋아함 / 회피 / 관심 — **"구매" 제외**(서버가 400. 구매는 의견이 아니라 사실)
- `editable: false` 항목은 ✏️ 비활성 (호출하면 409). **🗑은 활성**
- `predicate`·`object` 중 **최소 하나**는 있어야 한다. 아무것도 안 바꿨으면 보내지 말고 창만 닫기
- 저장 중 [저장] 비활성 (연타 방지)
- **자동완성으로 골랐으면 `nodeId`로 전송**:

```json
{ "predicate": "avoids", "object": { "nodeId": "brand:삼성" } }          // ★권장
{ "predicate": "avoids", "object": { "type": "brand", "label": "삼성" } } // 새로 입력한 경우만
```

자동완성 선택인데 `type`+`label`로 보내면 **서버가 라벨을 재정규화하면서 사용자가 고른 것과 다른
대상으로 튈 수 있다.** 둘을 함께 실으면 400이다. 본문은 **camelCase만** 허용(snake_case·unknown field는 400).

> **[HARD] 사용자 수정은 기계 배치가 덮어쓰지 못한다.** 이후 배치가 같은 취향을 다시 추출해도
> 최근 시각만 갱신되고 관계·상태·확신도는 안 바뀐다. **이 보장은 만료되지 않는다** —
> 만료를 두면 사용자의 수정이 조용히 되돌려진다.
> 취향이 실제로 바뀐 경우의 탈출구는 **보이는 방식**뿐이다 — `challenged: true`가 뜨고 상태는 그대로며,
> 명시적 사용자 동작만 고정을 푼다.

`challenged`는 **표시가 아니라 동작 트리거**다 — FE가 "다시 반영할까요?"를 띄울지 판단하는 값이고,
이게 없으면 AI가 사용자 수정에 이견이 있어도 알릴 방법이 사라진다.

### M-13 삭제

- **확인 다이얼로그 필수** · "되돌릴 수 없습니다" 포함 · **확인창에 항목 이름 명시**
  ("3~5만원대를 삭제할까요?") — 아이콘이 작아 오터치 가능성이 있는데 "이 취향을 삭제할까요?"만
  뜨면 어느 것을 눌렀는지 확인할 방법이 없다
- 기본 포커스 **[취소]** (Enter 연타로 삭제되면 안 된다) · `role="alertdialog"` + 포커스 트랩
- [삭제]와 [취소]를 시각적으로 구분하고 서로 붙여두지 않기
- Body 없음 — 신원·대상이 전부 경로에 있다
- **즉시 물리 삭제.** 원문도 그 자리에서 지운다. **재파생 차단 표식만 영구히 남아**
  다음 배치가 같은 취향을 다시 만들어도 부활하지 않는다(원문이 없으므로 표식에 개인정보가 없다).
  표식 해제는 **사용자가 그 취향을 다시 말할 때만** 일어난다
- `editable: false`(구매 파생)도 **삭제는 허용** — 수정만 불가

> ⚠️ **명세가 FE 문구를 교정했다**: *"FE 문구를 '구매 기록 삭제'로 쓰면 안 된다 —
> 지워지는 것은 취향 항목이지 주문 이력이 아니다."*
> 재구매 dedup은 프로필이 아니라 **주문 이력(I-19)을 질의 시점에 읽어** 판정하므로,
> "구매 기록을 지웠으니 다시 추천되겠지"는 성립하지 않는다.

### M-15 전체 초기화

```json
{ "scope": "ALL" }
```

`scope`는 **빈 요청 하나로 전체 삭제가 일어나지 않게 막는 판별자**다. 파괴 범위를 호출자가 명시적으로
이름 붙이게 하는 장치라 생략할 수 없다. 누락·미지 값은 400.

- **스위치 바로 옆이라 오터치 위험** → 색·크기·간격으로 확실히 구분하고 확인창을 반드시 거친다
- 확인창에 삭제 대상 개수를 나열하고, 버튼 문구는 "초기화"가 아니라 **"모두 삭제"**
- 개인화 OFF 상태에서도 가능해야 한다. 버튼 비활성화 금지
- 프로필 없는 회원도 오류가 아니다 — `purged` 전부 0으로 정상 200

| 삭제되는 것 | 남는 것 |
| --- | --- |
| 그래프 node·edge · fact 항목 | 변경 감사 로그 (누가·언제·무엇을 — 내용 없음) |
| 요약 (마크다운 **및** 요약 임베딩) | **개인화 ON/OFF 설정** — 초기화가 이 값을 안 바꾼다 |
| 재파생 차단 표식 · 세션 버퍼 · 누적 게이트 상태 | 주문·구매 내역 (커머스 데이터라 대상 아님) |
| **대화 전사록 전체** ← 놓치기 가장 쉬움 | |

**문구** — 감사 로그가 남으므로:

```
✅ "개인화 데이터와 대화 기록을 삭제합니다. 되돌릴 수 없습니다."
❌ "모든 데이터를 삭제합니다"    ← 감사 로그가 남으므로 사실과 다름
❌ "취향을 초기화합니다"         ← 대화 기록이 지워지는 걸 숨김
```

> 대화 전사록 포함은 **원안 개정**이다. 원 계약(REQ-PGRAPH-062)은 전사록을 보존하도록 [HARD]로
> 규정했으나 뒤집었다. 근거: *"보존한다"의 대상은 기계·운영이지 사용자가 아니다* —
> 금지 대상은 기계가 조용히 지우는 것이고, **사용자 자신의 삭제권은 별개**다 (C-23).

## 7. 절대 만들면 안 되는 것

| 금지 | 이유 |
| --- | --- |
| "최근 지운 항목" / 휴지통 | 되돌리기 폐기(M-14). 서버가 데이터를 주지 않는다 |
| **"실행취소" 토스트** | 되돌릴 수 있다는 잘못된 신호 |
| "다시 묻지 않기" 체크박스 | 비가역 동작의 확인을 끌 수 있게 하면 안 된다 |
| "숨겨진 항목 N개" 개수 표시 | **그 개수 자체가 민감 카테고리 유출**이다 |
| 원본 발화를 보여주는 "왜 이 취향이 있나요" | 근거 원문은 제공되지 않는다 |
| "몇 번 말했는지" 횟수 표시 | 세션 버퍼 반복 상한(2회)에 잘려 정확한 수를 셀 수 없다 |
| **취향을 검색 필터로 변환** | ↓ 아래 |
| 요청에 회원 id 담기 | IDOR 방지 |
| `nodeId` 화면 노출 | 내부 식별자(`"category:음향가전 > 블루투스 이어폰"`). `label`을 쓴다 |
| "회피"를 빨강·경고색으로 | 피하고 싶다는 건 오류가 아니라 **정당한 선호**다 |

### 취향 → 검색 필터 변환 금지 (가장 중요)

프로필을 필터 생성(조건 분해) 단계에 주입했다가 **회원 추천이 비회원보다 나빠진 실측 회귀**가 있었다 —
**nDCG@10 −0.288**, 31턴 중 29턴에서 가격·브랜드·평점 축 오염 (이슈 #119).

**취향은 추천 *순서(랭킹)* 에만 쓰고, 후보를 *걸러내는 데* 쓰면 안 된다.**

> 취향 목록을 화면에 보여주면 **"그럼 이걸로 상품을 찾아주면 되잖아"** 는 요구가 자연스럽게 따라온다.
> 그런데 그게 정확히 −0.288을 만든 동작이다. 필요해지면 **계약 개정이 먼저**다.
>
> 확정본에서 `usagePolicy.filterSafe` 표지판 필드는 빠졌지만 **규약 자체는 유효하다**(I-32 규약에 명시).

## 8. 접근성

- **그래프는 `aria-hidden`, sr-only 목록을 반드시 병행.** 보이는 목록 뷰를 없앴으므로 이게 없으면
  스크린리더에 이 화면이 **통째로 비어 보인다.** 항목마다 관계·라벨·수정·삭제 버튼이 읽혀야 한다
- 아이콘에 `aria-label="수정"` · `aria-label="삭제"` 필수 (아이콘만으로는 안 읽힌다)
- 터치 타겟 **44×44px**, 아이콘 사이 **16px 이상**, **✏️ 왼쪽 / 🗑 오른쪽** (위험한 쪽이 바깥)
- 관계 5색은 **전부 중립 채도** — 방사형에서 각도만으로는 가지가 구분되지 않아 색이 필요하지만,

📡 API 명세서(mypage · chat · internal 전량)를 훑어 확인한 결과 **BE 요청은 0건**이다.

| 항목 | 결론 |

| 서버 오류 | 잠시 후 다시 시도해 주세요. |

## 11. 오류 코드

| `code` | HTTP | 어디서 | FE 처리 |
| --- | --- | --- | --- |
| `AUTH_TOKEN_EXPIRED` | 401 | 전부 | 재발급 → 같은 요청 1회 재시도 (인터셉터가 이미 처리) |
| `AUTH_REQUIRED` | 401 | 전부 | 로그인 화면으로 |
| `AUTH_FORBIDDEN` | 403 | 전부 | 접근 불가 안내 (SELLER·ADMIN 계정) |
| `VALIDATION_ERROR` | 400 | 전부 | 개발 버그. 일반 오류 안내 — **`error.fields`가 없다**(AI가 필드 단위 오류 목록을 만들지 않음) |
| `PROFILE_EDGE_NOT_FOUND` | 404 | M-12 · M-13 | 목록 재조회 + "이미 삭제되었거나 변경된 항목이에요"<br>**남의 것이든 미존재든 동일 응답**(열거 방지) |
| `PROFILE_VERSION_CONFLICT` | **409** | M-12 · M-13 · M-15 · (M-16은 `If-Match` 보냈을 때만) | 재조회 → 동작별 분기 (4.4) |
| `PROFILE_EDGE_NOT_EDITABLE` | **409** | **M-12만** | "구매 기록은 수정할 수 없어요" — **재시도 금지** |
| `INTERNAL_ERROR` | 500 | 전부 | "잠시 후 다시 시도" |

> ⚠️ **AI 서버의 503·504가 전부 `500 INTERNAL_ERROR`로 뭉개져 온다.** FE는 "느려서 실패"와
> "서버 오류"를 구분할 수 없으니 안내 문구는 하나로 간다. (재시도 안내가 필요하면 별도 code 신설 협의)
>
> 오류 코드 변환 규칙: 레인 공통 코드는 변환하고(`BAD_REQUEST`→`VALIDATION_ERROR`,
> `INTERNAL_TOKEN_INVALID`→`AUTH_REQUIRED`, `UPSTREAM_*`→`INTERNAL_ERROR`),
> **`PROFILE_*`은 그대로 FE에 노출**한다 — FE가 두 종류의 409를 구분해야 대응이 갈리기 때문이다.

## 12. 반드시 확인할 시나리오

| # | 시나리오 | 확인 |
| --- | --- | --- |
| 1 | 수정 후 `edgeId`가 바뀐 응답 | 화면 키가 교체되어 **다음 삭제가 성공**하는가 |
| 2 | 수정 응답 `merged: true` | 목록을 재조회하는가 |
| 3 | 삭제 → 409 → 재조회 시 `edgeId` **있음** | 자동 1회 재시도로 성공하는가 |
| 4 | 삭제 → 409 → 재조회 시 `edgeId` **없음** | **중단**하고 안내하는가 (재시도 금지) |
| 5 | 수정 → 409 | 자동 재시도 **안 하고** 화면만 갱신하는가 |
| 6 | 초기화 → 409 | 자동 재시도 **안 하고** 확인창부터 다시인가 |
| 7 | 409 두 종류 | `code`로 분기하는가 (상태코드로만 보면 실패) |
| 8 | 401 `AUTH_TOKEN_EXPIRED` | 재발급 후 1회 재시도하는가 |
| 9 | `exists: false` | 오류가 아니라 빈 화면 안내인가 |
| 10 | `personalization.enabled: false` | 편집 기능이 **그대로 동작**하는가 |
| 11 | `edges`가 아주 많을 때 | 화면이 뭉개지지 않는가 (서버 상한 없음 — FE가 자름) |
| 12 | `editable: false` 항목 | ✏️ 비활성 + 🗑은 가능한가 |
| 13 | `replayed: true` | 200을 "삭제 성공"으로 처리하는가 (확인창 재노출 금지) |

## 13. 타임아웃 예산 (참고)

```
FE ──▶ Spring ──▶ AI(FastAPI)
        M-11         I-32   응답 예산 2s / Spring 타임아웃 3s
        M-12·13·15·16  I-33·34·36·37  응답 예산 3s / Spring 타임아웃 4s
```

Spring 타임아웃을 AI 예산보다 1s 길게 둔다 — 같으면 Spring이 먼저 끊어 AI의
`504 UPSTREAM_TIMEOUT`을 받지 못한다.

**P-5 개인화 캐시**(`p5:home:{회원id}` · TTL 10분)는 Spring 소유라 AI가 비울 수 없다.
M-12·13·15·16 성공 시 Spring이 무효화한다(C-27). 그래도 FE는 "즉시 반영"을 약속하지 않는다.
