> ⚠️ **응답 필드 설명이 낡았다 (2026-08-09 확정본으로 대체됨).**
> 3장의 배지 필드 대부분(`confidence`·`source`·`lastConfirmedAt`·`origin`·`verified`·
> `derivedFromSensitive`)은 **확정 응답에 실리지 않는다.** `nodes[]` 배열도 없다(`object` 인라인).

> 노션 「개인화 마이페이지 구현」을 **기능 관점으로 다시 쓴 것**.
> 구현 순서·파일 구조는 [personalization-mypage.md](personalization-mypage.md) 참조.

## 1. 한 문장으로

**AI가 대화·구매에서 알아낸 "이 사람은 이런 걸 좋아한다"를 사용자에게 보여주고, 틀렸으면 고치게 하는 화면.**

추천이 왜 이렇게 나오는지 사용자가 볼 수 있게 하고(투명성), 잘못 파악된 걸 직접 지울 수 있게 한다(통제권).

## 2. 데이터가 어떻게 생겼나

취향 하나는 **"나 → 관계 → 대상"** 문장 한 줄이다.

```
나 ──[선호]──▶ 3~5만원대
나 ──[좋아함]─▶ 광택
나 ──[회피]──▶ 삼성
```

이걸 API 용어로 옮기면:

| 용어 | 뜻 | 예 |
| --- | --- | --- |
| **node** | 취향의 *대상* | `{ nodeId: "brand:소니", label: "소니" }` |
| **edge** | 나와 대상을 잇는 *관계 한 줄* | `{ edgeId: "e_2f8…", to: "brand:소니", predicate: "avoids" }` |
| **predicate** | 관계의 종류 | `prefers` / `likes` / `avoids` / `interestedIn` / `purchased` |

> **출발점(`from`)이 응답에 없다.** 항상 "나"라서 뺐다.
> 그래서 대상끼리 연결된 데이터가 없고, **옵시디언 같은 다단계 그래프는 만들 수 없다**(노션 10.1).
> 전부 나에게서 한 단계 뻗은 방사형뿐이다.

### 노드 타입 7종
`brand` / `category` / `attribute` / `priceBand` / `ratingBand` / `product` / `situation`

### 관계 5종

| `predicate` | 화면 라벨 | 뜻 | 수정 |
| --- | --- | --- | --- |
| `prefers` | 선호 | 비교 선호 — 다른 것 대신 이것 | 가능 |
| `likes` | 좋아함 | 단순 긍정 — 비교 없이 좋아함 | 가능 |
| `avoids` | 회피 | 명시적 회피 | 가능 |
| `interestedIn` | 관심 | 최근 관심 (시간 지나면 약해짐) | 가능 |
| `purchased` | 구매 | 구매 사실 | **불가** |

> **`avoids`와 `purchased`는 당분간 항상 빈 배열이다.** 이 관계를 만드는 경로가 아직 없다.
> **오류가 아니다.** 지우지도 강조하지도 말고 "아직 없어요"로 자리만 지킨다.
> 구매는 *의견이 아니라 사실*이라 사용자가 만들 수 없다 — 수정 창의 관계 선택지에서도 뺀다.

## 3. 항목 하나에 붙은 정보들

edge 하나가 이만큼의 상태를 들고 온다. 각각이 화면에서 다르게 읽혀야 한다.

| 필드 | 값 | 의미 | 화면 |
| --- | --- | --- | --- |
| `confidence` | HIGH/MEDIUM/LOW | AI가 얼마나 확신하나 | 점 크기 3단계 + 문구 |
| `origin` | machine / user | 누가 만들었나 | `user`면 "내가 수정함" 배지 |
| `source` | conversation / purchase / user | 어디서 알게 됐나 | "대화에서 알게 되었어요" |
| `lastConfirmedAt` | 날짜 | 마지막으로 확인된 시점 | "최근 확인 7월 29일" |
| `editable` | true / false | 수정 가능한가 | `false`면 🔒 + ✏️ 비활성 (**🗑은 활성**) |
| `challenged` | true / false | 최근 행동과 어긋나나 | 느낌표 + "취향이 바뀐 것 같아요" |
| `verified` | true / false | 검증된 대상인가 | `false`면 점선 (추천에서 빠질 수 있음) |
| `derivedFromSensitive` | true / false | 민감 정보에서 파생됐나 | **아무 차이도 두지 않음** ← 아래 |

### 확신도 문구

| 값 | 문구 |
| --- | --- |
| HIGH | 확실해요 |
| MEDIUM | 그런 것 같아요 |
| LOW | 아직 확실하지 않아요 |

"신뢰도 85%" 같은 수치는 쓰지 않는다. 3단계 경계값이 서버 설정이라 바뀌면 수치 라벨이 거짓이 된다.

### 🔒 `derivedFromSensitive`가 왜 특별한가

민감한 정보(건강·신념 등)에서 파생된 취향이라는 표시다.
**다르게 그리면 안 된다.** 테두리 하나만 달라도 "이건 민감한 데서 나왔다"를 화면에 공개하는 셈이다.
일반 항목과 **완전히 똑같이** 그린다. 같은 이유로 "숨겨진 항목 N개" 같은 개수 표시도 금지 — 그 숫자 자체가 정보 유출이다.

## 4. 사용자가 할 수 있는 일 5가지

| # | 기능 | API | 되돌리기 | 확인창 |
| --- | --- | --- | --- | --- |
| 1 | **보기** | M-11 `GET /api/profile/graph` | — | — |
| 2 | **고치기** | M-12 `PATCH …/edges/{id}` | 가능(다시 고치면 됨) | ❌ |
| 3 | **지우기** | M-13 `DELETE …/edges/{id}` | **불가** | ✅ |
| 4 | **전부 지우기** | M-15 `POST …/graph/reset` | **불가** | ✅ (더 무겁게) |
| 5 | **개인화 끄기/켜기** | M-16 `PUT /api/profile/personalization` | 가능(다시 켜면 됨) | ❌ |

확인창을 두는 기준은 하나다:

```
되돌릴 수 있나?
  ├── 예   → 확인 없음  (고치기 · ON/OFF)
  └── 아니오 → 확인 필수  (지우기 · 전부 지우기)
```

**고치기에 확인창을 안 두는 이유** — [저장]을 누르는 것 자체가 확인이고, 잘못 고쳐도 결과가 화면에 보여서 바로 다시 고칠 수 있다. 삭제는 지우는 순간 뭐가 있었는지 사라져 알아챌 방법이 없다.

## 5. 각 기능이 실제로 뭘 하나

### 5.1 보기 (M-11)

화면 진입 시 한 번 호출. 여기서 받은 것으로 화면 전부가 그려진다.

- `markdown` — 좌상단 요약 문단. "3~5만원대 무선 이어폰을 선호하시고…"
- `nodes` + `edges` — 트리에 그릴 항목들
- `personalization.enabled` — 스위치 상태
- `graphVersion` — **보관 필수** (아래 7장)
- `truncated` — 200개에서 잘렸는지

> **`exists: false`는 오류가 아니다.** 신규 회원의 정상 상태이고 HTTP 200이다. 빈 화면 안내로 처리.

**정렬은 서버가 정한다** — `prefers` → `likes` → `avoids` → `interestedIn` → `purchased`, 각 그룹 안에서는 최근 확인순. 클라이언트가 다시 정렬하지 않는다.

### 5.2 고치기 (M-12)

바꿀 수 있는 건 **관계**와 **대상** 둘뿐. 최소 하나는 바뀌어야 한다(아무것도 안 바꾸면 서버가 400).

```json
// 화면에 있던 항목을 자동완성으로 고른 경우 (권장)
{ "predicate": "avoids", "object": { "nodeId": "brand:삼성" } }

// 사용자가 새로 입력한 경우에만
{ "predicate": "avoids", "object": { "type": "brand", "label": "삼성" } }
```

자동완성으로 골랐는데 `type`+`label`로 보내면 **서버가 라벨을 다시 정규화하면서 엉뚱한 대상으로 튈 수 있다.** 둘을 함께 보내면 400.

> **★ 고치면 `edgeId`가 바뀐다.** ID가 `(관계, 대상)`에서 만들어지기 때문.
> 응답의 `data.edge.edgeId`로 클라이언트 키를 교체하지 않으면 **다음 수정·삭제가 전부 404**다.
> 화면은 멀쩡해 보이는데 요청만 실패해서 원인을 찾기 어렵다 — 이 기능에서 가장 놓치기 쉬운 지점.

`merged: true`가 오면 고친 내용이 이미 있던 항목과 합쳐진 것 → 목록 재조회.

### 5.3 지우기 (M-13)

**즉시 영구 삭제.** 되돌리기 API(M-14)는 폐기됐다.

그래서 화면에 만들면 안 되는 것들:
- "최근 지운 항목" / 휴지통
- **"실행취소" 토스트** ← 되돌릴 수 있다는 잘못된 신호
- "다시 묻지 않기" 체크박스

확인창에는 **항목 이름을 넣는다** — "3~5만원대를 삭제할까요?". 아이콘이 작아 오터치 가능성이 있는데 "이 취향을 삭제할까요?"만 뜨면 뭘 눌렀는지 확인할 방법이 없다. 기본 포커스는 [취소]에 둔다(Enter 연타로 삭제되면 안 됨).

**구매 기록도 삭제는 된다**(수정만 불가). 단 안내가 필요하다:
> "목록에서 지워요. 이미 산 상품이 다시 추천되지는 않습니다."

재구매 중복 방지는 주문 이력이라는 별도 경로로 동작해서, "구매 기록을 지웠으니 다시 추천되겠지"는 성립하지 않는다.

### 5.4 전부 지우기 (M-15)

개별 삭제보다 훨씬 파괴적이다. **대화 기록까지 지워진다** — 이게 가장 놓치기 쉬운 부분.

| 삭제됨 | 남음 |
| --- | --- |
| 취향 항목 전부 | 변경 기록 (*언제* 지웠는지만, 내용 없음) |
| 취향의 근거가 된 기록 | **개인화 ON/OFF 설정** |
| AI가 만든 요약 | **주문·구매 내역** (커머스 데이터라 대상 아님) |
| **대화 기록 전체** | |

그래서 문구가 정해져 있다:
```
✅ "대화 기록을 포함한 개인화 데이터를 모두 초기화합니다. 되돌릴 수 없습니다."
❌ "모든 데이터를 삭제합니다"   ← 변경 기록이 남으므로 사실과 다름
❌ "취향을 초기화합니다"        ← 대화 기록이 지워지는 걸 숨김
```

버튼 문구도 "초기화"가 아니라 **"모두 삭제"**. 요청 body의 `{ "scope": "ALL" }`은 생략 불가 — 빈 요청 하나로 전체 삭제가 일어나지 않게 막는 판별자다.

### 5.5 개인화 끄기/켜기 (M-16)

**끈다고 데이터가 지워지지 않는다.** 사용을 멈출 뿐이고, 다시 켜면 복원된다.

| | 중지 중 |
| --- | --- |
| 추천 | 개인화 안 함 (일반 추천) |
| 새 취향 수집 | 중단 |
| **채팅의 "기억해" 요청** | **저장되지 않음** ← 이걸 모르면 배신감을 느낀다 |
| 기존 데이터 | **보존** |
| 이 화면 | **그대로 보이고 편집도 됨** |

> ⚠️ **개인화가 꺼져 있어도 조회·수정·삭제·초기화가 전부 가능해야 한다.**
> "개인화를 켜야 편집할 수 있습니다" 같은 화면을 만들면, 데이터를 정리하려고 개인화를 다시 켜야 하는 모순이 생긴다.

> ⚠️ **"즉시 반영"을 약속하지 않는다.** 홈 추천에 최대 10분간 이전 결과가 남는다(서버 캐시).
> 문구: "개인화를 껐어요. 홈 화면 반영까지 몇 분 걸릴 수 있어요."

## 6. 취향을 어디에 쓰면 안 되나

응답에 `usagePolicy: { orderOnly: true, filterSafe: false }`가 온다.

**`filterSafe`는 분기용 값이 아니다.** 항상 `false`로 오고, *"이 데이터를 검색 필터로 바꾸는 것은 계약 위반"*을 응답에 박아둔 **표지판**이다.

취향 목록을 보여주면 "그럼 이걸로 상품을 찾아주면 되잖아"는 요구가 자연스럽게 따라오는데, **그게 정확히 추천 품질을 망가뜨린 동작**이다.

> 프로필을 필터 생성 단계에 주입했다가 **회원 추천이 비회원보다 나빠진 실측 회귀**가 있었다.
> nDCG@10 **−0.288**, 31턴 중 29턴에서 가격·브랜드·평점 축이 오염됨.

취향은 추천 **순서**에만 쓰고, 후보를 **걸러내는 데** 쓰지 않는다.

## 7. graphVersion — 이 기능의 동시성 장치

모든 응답에 `graphVersion`이 들어 있다. 수정·삭제·초기화 요청에는 이걸 `If-Match` 헤더로 실어 보낸다.

```
If-Match: "g42"        ← M-11 응답의 data.graphVersion 을 그대로
```

**왜 필요한가** — 다른 탭이나 AI 서버가 그 사이 취향을 바꿨을 수 있다. 옛 버전으로 요청하면 서버가 409로 거절해서, 사용자가 보고 있던 화면과 다른 걸 건드리는 사고를 막는다.

규칙:
- **불투명 문자열이다.** 파싱·크기 비교·순서 추론 금지. 받은 값을 그대로 실어 보내기만 한다
- **모든 성공 응답에서 보관값을 갱신한다.** 안 하면 다음 요청이 전부 409
- 요청은 **헤더**, 응답은 **본문**이 정규. 응답 헤더의 `ETag`는 CORS 때문에 브라우저 JS가 못 읽는다
- M-16만 `If-Match`가 **선택**이다

## 8. 실패했을 때

### 409가 두 종류다 — 대응이 정반대

| `error.code` | 뜻 | 대응 |
| --- | --- | --- |
| `PROFILE_VERSION_CONFLICT` | 그 사이 내용이 바뀜 | 재조회하면 풀림 |
| `PROFILE_EDGE_NOT_EDITABLE` | 구매 기록을 고치려 함 | **몇 번을 해도 안 됨** |

HTTP 상태로만 분기하면 틀린다. 반드시 `error.code`로 가른다.

### 버전 충돌 시 동작별 재시도 정책

| 동작 | 재조회 | 자동 재시도 | 왜 |
| --- | --- | --- | --- |
| **삭제** | O | **O (1회)** | "이걸 없애줘" — 대상이 `edgeId`로 고정돼 결과가 안 바뀜 |
| **수정** | O | X | "이 값으로 바꿔줘" — 병합 여부에 따라 결과가 달라짐 |
| **초기화** | O | X | "전부 지워줘" — 범위 자체가 달라짐 |

기준은 **"의도가 상태 변화에 흔들리는가"**.

> **삭제 자동 재시도의 중단 조건** — 재조회했을 때 그 `edgeId`가 **없으면 중단**한다.
> 그 사이 내용이 바뀌었다는 뜻이라 밀어붙이면 사용자가 의도하지 않은 걸 건드린다.

> **자동 재시도 금지 ≠ 사용자가 다시 못 함.** 수정·초기화는 *FE가 알아서 보내지 말라*는 뜻이지, 사용자가 화면을 보고 다시 누르는 건 정상 경로다.

### 그 외

| 코드 | HTTP | 대응 |
| --- | --- | --- |
| `AUTH_TOKEN_EXPIRED` | 401 | 재발급 후 1회 재시도 (**인터셉터가 이미 처리**) |
| `AUTH_REQUIRED` | 401 | 로그인으로 |
| `AUTH_FORBIDDEN` | 403 | 접근 불가 — SELLER·ADMIN 계정은 이 화면을 못 쓴다 |
| `PROFILE_EDGE_NOT_FOUND` | 404 | 재조회 + "이미 삭제되었거나 변경된 항목이에요" |
| `INTERNAL_ERROR` | 500 | "잠시 후 다시 시도" |

> AI 서버의 503·504가 전부 `500 INTERNAL_ERROR`로 뭉개져 온다. "느려서 실패"와 "서버 오류"를 구분할 수 없으니 안내 문구는 하나로 간다.

### 통신이 끊겼으면 그냥 다시 보내면 된다

서버가 중복 요청을 알아보고 처음 응답을 그대로 돌려준다(`replayed: true`).
**결과가 200이면 "이미 삭제됨"이 아니라 "삭제 성공"으로 처리**한다. 확인창을 다시 띄우면 안 된다.

## 9. 채팅과의 관계

**채팅으로는 취향을 변경할 수 없다.** 이 화면에서만 가능하다.

```
사용자: "내 취향 다 지워줘"
   ↓
AI: "취향은 마이페이지 > AI가 이해한 내 취향에서 직접 확인하고 지우실 수 있어요."
    [마이페이지로 이동]
```

**비대칭이다** — 채팅에서 "이거 기억해"는 되는데 "지워줘"는 안 된다.
저장은 되돌릴 수 있고 삭제는 되돌릴 수 없어서, 삭제는 화면에서 명시적으로 받는다.

> 무반응은 안 된다. 아무 말이 없으면 사용자는 지워진 줄 안다.

## 10. 화면이 가져야 할 상태 5가지

| 상태 | 조건 | 화면 |
| --- | --- | --- |
| 로딩 | M-11 응답 대기 | 스켈레톤 (스피너보다 체감이 짧음) |
| 정상 | `exists: true` + `edges` 있음 | 요약 + 트리 |
| 빈 상태 | `exists: false` **또는** `edges: []` | "아직 파악한 취향이 없어요" — **스위치와 [전체 초기화]는 그대로** |
| 개인화 OFF | `personalization.enabled: false` | 채도 낮추기(**숨기지 않기**) + 배너 — **편집은 그대로 동작** |
| 오류 | M-11 실패 | 재시도 버튼 |

## 11. 요약 — 이 기능의 어려운 지점 5개

1. **`graphVersion` 보관을 빠뜨리면 이후 요청이 전부 409** → 캐시 한 곳에서만 관리
2. **수정하면 `edgeId`가 바뀐다** → 응답으로 키를 교체하지 않으면 다음 요청이 404
3. **409가 두 종류고 대응이 정반대** → `error.code`로 분기
4. **삭제만 자동 재시도, 그것도 중단 조건이 있다** → 재조회 후 `edgeId` 확인
5. **되돌리기가 없다** → 실행취소 토스트·휴지통을 만들면 거짓말이 된다
