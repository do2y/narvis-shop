# §A 슬라이드 1장 (확정본)

> [슬라이드: 서버와 화면의 상태]
>
> **앞 슬라이드에서 세 가지를 예고하지 않았다면** 첫 문장을
> "세 번째는 상태 관리입니다"로 바꾼다 — 지금 문장은 앞 슬라이드에 기댄다.

세 번째가 가장 중요합니다. 사용자가 직접 담든, AI에게 "담아줘"라고 하든
화면에는 같은 결과가 나와야 합니다.

상태의 소유권을 갈랐습니다. 기준은 누가 이 값의 원본을 갖고 있는가입니다.
장바구니·찜·주문처럼 서버가 원본인 데이터는 TanStack Query가 유일한 소유자고,
대화 내용이나 바텀시트 같은 화면만의 상태는 Zustand로. 사용자가 직접 조작할 때는
낙관적 업데이트를 씁니다 — 진행 중인 조회부터 취소하고(안 하면 늦게 도착한 옛 응답이
방금 바꾼 값을 덮습니다), 캐시를 먼저 바꿔 즉시 반영하고, 실패하면 롤백,
끝나면 서버에서 재조회해 맞춥니다.

**AI를 붙이면서 여기에 세 가지가 더해졌습니다.**

먼저 대화를 어디에 저장할지입니다. 서버가 대화 맥락을 10분만 들고 있어서,
화면의 대화를 그보다 오래 남기면 사용자에겐 대화가 보이는데 AI는 기억 못 하는
어긋난 상태가 길어집니다. 그래서 탭 단위로 저장했습니다. 탭 수명이 세션 수명과
대체로 겹쳐서 그 간극이 가장 작습니다.

다음은 갱신 주체가 둘이 된 것입니다. AI가 행동하면 action 이벤트가 도착하는데,
프론트는 이게 서버 상태를 바꾸는 행동인지 판별해서 해당 캐시를 무효화합니다 —
**AI의 행동이 사용자 조작과 같은 갱신 경로로 합류하는 겁니다.** 행동 종류가
두 개에서 열 개로 늘면서 이 판별을 공통 함수 하나로 모았고, 실패한 행동은
서버가 안 바뀌었으니 무효화에서 뺍니다.

마지막은 AI가 만든 것을 프론트가 고쳐 보낼 수 없게 한 것입니다. 판매자가 상품 등록을
맡기면 AI가 초안을 만들고, 프론트는 그걸 화면에 그립니다. 그런데 승인할 때 보내는 건
초안 ID 하나뿐입니다. 화면에 그린 내용을 고쳐서 보내도 저장되는 값은 바뀌지 않습니다 —
실제로 등록되는 값은 서버가 들고 있는 초안이니까요. 프론트가 보낸 값을 서버가 믿으면,
그 길이 위조 경로가 되기 때문입니다.

## §A 줄이는 법

시간이 빠듯하면 **2문단(낙관적 업데이트)을 줄인다.** 라이브러리 문서에 있는
내용이라 "그건 기본 아닌가요"에 취약하고, 배경 역할이라 빠져도 논지가 선다.

> 축약형: "사용자가 직접 조작할 때는 낙관적 업데이트를 씁니다 — 다만 진행 중인
> 조회를 먼저 취소해야 합니다. 안 그러면 늦게 도착한 옛 응답이 방금 바꾼 값을 덮습니다."

**세 갈래(저장 수명·갱신 주체·신뢰 경계)는 줄이지 않는다.** 이 발표의 고유한 소재다.

## 블록 1 — 소유권: 무엇을 어디에 둘 것인가

> [슬라이드: 상태 2분할 — 서버 원본 / 화면만의 상태]

상태를 어디에 둘지부터 갈랐습니다. 기준은 하나입니다. **원본이 서버에 있는가.**

장바구니·찜·주문은 서버가 원본입니다. 이건 TanStack Query가 관리하고,
**같은 값을 useState로 복제하지 않습니다.** 복제하는 순간 원본이 둘이 되고,
둘이 어긋나면 어느 쪽이 맞는지 판단할 근거가 없어집니다.

대화 내용이나 바텀시트가 열렸는지 같은 건 서버가 알 필요가 없습니다. 이건 Zustand에 둡니다.

말로 하면 당연해 보이는데, **경계가 애매한 게 실제로 하나 있었습니다.** 찜 여부입니다.
"이 상품이 찜 상태인가"는 상품마다 필요한 값이라 따로 들고 있고 싶어지는데,
저희는 **찜 목록에서 파생시킵니다.** 별도 조회 API가 없기도 했지만,
따로 들고 있으면 목록 화면과 상세 화면의 하트가 서로 다른 답을 할 수 있기 때문입니다.

## 블록 2 — 즉시성: 하트는 기다리지 않는다

> [슬라이드: 낙관적 업데이트 — cancelQueries가 먼저다]

사용자가 하트를 누르면 **서버 응답을 기다리지 않고 화면을 먼저 바꿉니다.**
낙관적 업데이트라고 부르는 흔한 패턴인데, 저는 여기서 **순서 하나 때문에 고생했습니다.**

캐시를 바꾸기 전에 **진행 중인 조회를 먼저 취소해야 합니다.**
안 그러면 이런 일이 생깁니다 — 찜 목록을 불러오는 요청이 이미 날아가 있는 상태에서
사용자가 하트를 누릅니다. 화면은 즉시 바뀝니다. 그런데 아까 날아간 요청의 응답이
**그 다음에** 도착합니다. 그 응답에는 방금 누른 찜이 없습니다. **하트가 도로 꺼집니다.**

취소하고, 되돌릴 값을 백업해두고, 캐시를 바꾸고, 실패하면 롤백, 끝나면 재조회.
이 순서를 장바구니 수량 변경·삭제·찜 토글 세 군데에서 똑같이 씁니다.

그리고 여기 **예외 처리를 하나 넣었습니다.** 이미 찜한 상품을 또 찜하면 서버가 409를 줍니다.
형식상 실패지만 **사용자 입장에선 실패가 아닙니다.** 원하는 상태에 이미 도달해 있으니까요.
그래서 이 두 코드는 롤백하지 않고 서버 기준으로 다시 맞춥니다.
다만 **404를 뭉뚱그리면 안 됐습니다** — 없는 상품을 찜해도 404라서,
같이 처리했더니 진짜 실패인데 하트가 켜진 채 남았습니다. 그래서 status가 아니라 **코드로** 갈랐습니다.

## 블록 3 — 합류: AI가 담아도 같은 화면이어야 한다 ⭐

> [슬라이드: 두 개의 입구, 하나의 갱신 경로]
> **여기에 시간을 쓴다. 앞의 둘은 이 블록을 위한 준비다.**

이게 이 프로젝트에서 가장 고민한 부분입니다.

저희 서비스는 장바구니에 담는 **입구가 둘입니다.** 사용자가 버튼을 누르거나,
AI에게 "이거 담아줘"라고 말하거나. **그런데 결과 화면은 같아야 합니다.**
헤더 뱃지 숫자도, 장바구니 페이지도요.

AI가 뭔가를 하면 스트림으로 action 이벤트가 옵니다. 프론트는 이걸 받아서
**서버 상태가 실제로 바뀌었는지 판별하고, 바뀌었으면 해당 캐시를 무효화합니다.**
무효화하면 그 캐시를 보고 있던 화면이 전부 다시 불러옵니다.
**AI의 행동이 사용자 조작과 같은 갱신 경로로 합류하는 겁니다.**

여기서 판별을 **어디에 둘지**가 문제였습니다. 처음엔 액션이 두 종류뿐이라
채팅 화면 안에서 그냥 분기했습니다. 그러다 **열 종으로 늘었습니다.**
장바구니 담기·삭제·수량변경, 찜 추가·해제, 각각 성공과 실패, 판매자 수정까지.
화면에서 분기하고 있었으면 액션이 늘어날 때마다 고칠 곳을 찾아다녀야 합니다.
그래서 **판별 함수를 계약 타입 옆으로 옮겼습니다.** 액션이 또 늘어나면 고칠 곳이 거기 하나입니다.

그리고 **실패한 액션은 무효화하지 않습니다.** 서버 상태가 안 바뀌었으니 재조회할 이유가 없습니다.
이건 성능이 아니라 정확성 문제에 가깝습니다 — 실패를 성공처럼 처리하면
"담겼나?" 싶어 재조회하고, 안 담긴 걸 확인하는 헛걸음이 생깁니다.

**제약도 하나 있습니다.** 찜 이벤트에는 상품 ID가 안 실립니다.
그래서 "이 상품만 갱신"이 불가능하고 **목록을 통째로 다시 부릅니다.**
지금 규모에선 문제가 없어서 그대로 뒀는데, 목록이 커지면 계약부터 바꿔야 하는 지점입니다.

## 마무리 한 문장

> 입구가 둘이어도 **갱신 경로는 하나**로 모읍니다.
> 그래야 AI가 한 일과 사용자가 한 일이 화면에서 같아집니다.

## 예상 질문

**Q. 낙관적 업데이트는 라이브러리 문서에 다 있는 패턴 아닌가요?**
맞습니다. 패턴 자체는 표준입니다. 저희가 겪은 건 **순서를 지키지 않았을 때의 증상**이고,
그걸 테스트로 고정한 부분입니다. 취소 단계를 빼면 늦게 온 응답이 방금 바꾼 값을 덮는데,
이건 재현이 불규칙해서 테스트가 없으면 다시 들어옵니다.

**Q. AI가 한 행동을 프론트가 믿어도 되나요? 프론트가 상태를 바꾸는 건가요?**
아니요. **프론트는 상태를 바꾸지 않습니다.** action 이벤트는 "서버에서 이미 일어난 일"의 통지고,
프론트가 하는 건 **캐시를 버리고 서버에 다시 묻는 것**뿐입니다.
그래서 이벤트를 잘못 믿어도 최악의 경우가 불필요한 재조회지, 화면이 거짓말을 하진 않습니다.

**Q. 왜 목록 전체를 다시 부르나요? 그 상품만 바꾸면 되지 않나요?**
찜 이벤트에 상품 ID가 안 실려서 지금은 불가능합니다. 계약을 바꾸면 되는데,
현재 목록 크기에선 재조회 비용이 작아 우선순위를 낮게 뒀습니다. 알고 남겨둔 제약입니다.

**Q. 초안이 만료된 건 누가 알려주나요?**
프론트가 잽니다. 초안은 서버에서 10분 뒤 사라지는데, **그 시점엔 SSE 스트림이 이미 끝나 있어
서버가 알려줄 경로가 없습니다.** 프론트가 재지 않으면 판매자가 죽은 초안을 붙들고
수정을 시도하게 됩니다. 수정 턴에서 새 초안이 오면 타이머도 새로 잡습니다 —
첫 초안 시각을 물려받으면 5분 만에 사라져서, 이건 테스트로 고정했습니다.
([ChatPage.tsx:178-195](../src/features/seller/ChatPage.tsx#L178-L195), `activeDraft.test.ts`)

**Q. 화면 정보를 서버로 보낸다고 했는데, 그게 위조 경로가 되지 않나요?**
보내는 건 **상품 ID와 이름뿐**이고, 용도는 "그거 담아줘" 같은 지시대명사를 푸는 것뿐입니다.
가격이나 재고처럼 **판단의 근거가 되는 값은 보내지 않습니다** — 담기 요청에도 ID만 갑니다.
화면 정보는 **무엇을 가리키는지**에만 쓰고, **얼마인지**는 항상 서버가 정합니다.
