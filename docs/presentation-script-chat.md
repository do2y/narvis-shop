## 블록 1 — 스트림: 수신 계층

> [슬라이드: SSE 수신 — 표준 도구를 쓸 수 없었던 이유]

첫 번째는 AI 응답을 받는 부분입니다.

브라우저에는 서버가 보내는 스트림을 받는 표준 도구가 있습니다. EventSource라고 합니다.
그런데 이게 GET 요청만 되고, 헤더를 실을 수 없습니다. 저희는 인증 티켓을 헤더에 실어야 하고
대화 내용을 POST로 보내야 해서, 표준 도구로는 요청 자체가 성립하지 않았습니다.
그래서 fetch 스트리밍 위에 파서를 직접 구현했습니다.

직접 만들었다는 건 견고성도 직접 책임진다는 뜻인데, 저는 이걸 **사고를 두 번 겪고 나서야 알았습니다.**

첫 번째. 서버가 보낸 프레임 하나가 깨져서 왔는데, 파싱 실패가 읽기 루프 밖으로 던져지면서
스트림이 통째로 멈췄습니다. 뒤따라오던 정상 이벤트 — 종료 신호와 상품 목록 신호까지 — 를
영영 못 읽었고, 호출부는 이걸 스트림 실패로 처리했습니다.
**결과적으로 화면에 이미 다 찍혀 있는 답변 위에 "응답을 받지 못했어요" 오류 말풍선이 덮였습니다.**
프레임 하나 때문에요. 그래서 파싱 실패는 그 프레임만 버리고 계속 읽도록 바꿨습니다.

두 번째. 스트림이 마지막 프레임을 개행 두 개로 닫지 않고 끊기면, 버퍼에 남은 조각을
그냥 버리고 루프를 빠져나갔습니다. 그런데 마지막 프레임은 대개 종료 신호입니다.
이걸 잃으면 판매자 분석 리포트가 패널에 커밋되지 않고, 검색 결과가 없을 때 띄우는
기본 문구도 채워지지 않았습니다. 남은 조각도 같은 규칙으로 파싱하도록 고쳤습니다.

**둘 다 에러가 안 나는 종류의 실패였습니다.** 콘솔은 조용하고 화면만 이상합니다.
그래서 고친 다음엔 테스트로 고정했습니다.

그리고 하나 더, 파서를 열린 구조로 뒀습니다. 진행 단계를 알려주는 이벤트가 있는데,
처음엔 단계가 하나뿐이라 그 값만 받는 닫힌 목록으로 정의했습니다. 그런데 AI 서버가
단계를 일곱 종으로 늘리면서 프론트도 같이 배포해야 했습니다. 그때 타입을 개방형으로
바꿨습니다 — 모르는 단계가 오면 무시하고 넘어가되, **무시가 초기화는 아니게.**
직전 문구를 지우지 않고 그대로 둡니다. 계약에도 "프론트는 모르는 stage를 무시한다"를
명문화했고, 지금 예고돼 있는 다음 단계는 프론트 배포 없이 그냥 들어옵니다.

## 블록 2 — 탭: 그 위의 상태

> [슬라이드: 탭 사이의 상태 — sessionId와 threadId]

두 번째는 탭입니다. 이건 버그에서 시작했습니다.

탭을 두 개 띄우고 채팅을 하면 세션이 서로를 축출했습니다. 탭마다 세션을 새로 발급받는데,
나중에 발급된 게 앞엣것을 밀어내서 먼저 열어둔 탭의 대화가 깨졌습니다.

해결 방향은 분명했습니다. 세션 발급을 한 번만 하고 탭끼리 공유하면 됩니다.
락으로 묶고, 결과를 localStorage에 넣고, 방송으로 다른 탭에 알리고.

**그런데 여기서 멈추면 반대쪽이 깨집니다.** 세션을 공유한다는 건 모든 탭이 서버에서
같은 대화방에 들어간다는 뜻이거든요. 축출은 사라지는 대신, 이번엔 탭 A에서 신발을 묻고
탭 B에서 노트북을 물으면 AI가 두 대화를 한 맥락으로 섞습니다. 화면은 탭마다 따로인데
서버 맥락만 하나로 합쳐지는, 더 헷갈리는 상태가 됩니다.

이건 프론트 혼자 해결할 수 없었습니다. 대화 맥락을 들고 있는 건 AI 서버니까요.
그래서 프론트에서 계약 변경을 제안했습니다. 인증과 서버 맥락에 묶인 sessionId는 공유하되,
**대화방을 구분하는 threadId를 새로 도입해서 AI가 방 단위로 맥락을 분리하도록.**
세 팀이 명세를 함께 고치고 그 위에서 구현했습니다.

계약이 갈라지니 저장소도 갈라집니다. 두 식별자의 수명이 다르기 때문입니다.
sessionId는 사용자 단위라 모든 탭이 공유해야 하고, threadId는 탭마다 독립이어야 합니다.
그래서 세션과 티켓은 탭이 공유하는 localStorage에, threadId는 탭 수명인 sessionStorage에 뒀습니다.
threadId를 상태 스토어에 두지 않은 이유도 여기 있습니다 — '새 대화' 버튼이 스토어를
초기값으로 되돌리면서 방 번호까지 같이 날려버리거든요.
**새 대화는 방을 새로 만드는 거지, 방이라는 개념을 잃는 게 아닙니다.**
그래서 '새 대화'는 세션 재발급이 아니라 현재 탭의 threadId만 새로 파는 동작으로 정의했습니다.

탭 사이 동기화는 BroadcastChannel로 했는데, 방송 메시지를 두 종류로 나눴습니다.
새 티켓이 발급됐다는 갱신 통지와, 게스트가 회원으로 전환돼 기존 티켓을 버려야 한다는
무효화 통지. 합쳐두면 받는 탭이 갱신하면 되는지 버려야 하는지를 구분할 수 없고,
그러면 방송이 도착하기 전에 시작된 전송이 옛 게스트 티켓으로 나가서 AI 서버에서 403을 맞습니다.

## 블록 3 — 대화: 어디까지 살릴 것인가

> [슬라이드: 대화 복원 — 오래 남기는 게 답이 아니었다]
> **🎬 시연 있음** — 대화 3턴 → 새로고침 (10초)

세 번째는 대화 내용입니다. 앞의 두 블록이 식별자 이야기였다면 이건 말풍선 자체입니다.

새로고침 한 번에 대화가 날아가면 안 됩니다. 실수로 탭을 닫았다가 Ctrl+Shift+T로
되살렸을 때도 돌아와야 하고요. 그런데 **서버는 말풍선을 보관하지 않습니다.**
대화 내역을 내려주는 API 자체가 없어요. 서버가 들고 있는 건 AI가 참조할 맥락뿐이라,
프론트가 안 하면 아무도 하지 않습니다.

> 🎬 **여기서 시연** — 대화 3턴 하고 새로고침, 그대로 남아 있음

여기까지는 요구사항입니다. 판단이 필요했던 건 그다음이었습니다. **어디에 저장할 것인가.**

편한 건 localStorage입니다. 더 오래 살아남고, 브라우저를 껐다 켜도 남습니다.
그런데 그렇게 하면 안 됐습니다. **서버 맥락 TTL이 10분이거든요.** 슬라이딩이라 대화를
이어가면 연장되지만, 하루 지나서 돌아오면 서버 쪽 맥락은 이미 없습니다.
화면엔 어제 대화가 그대로 있는데 AI는 아무것도 기억 못 하는 상태가 됩니다.
사용자는 당연히 "이어서 물어보면 되겠네" 하고 말을 걸고, AI는 처음 보는 사람처럼 답합니다.
**대화가 남아 있는 게 오히려 사용자를 속이는 셈입니다.**

그래서 탭 수명인 sessionStorage로 잡았습니다. 탭 수명이 서버 세션 수명과 대체로 겹쳐서,
화면과 서버가 어긋나는 구간이 가장 짧습니다.
**저장소는 편한 곳이 아니라 수명이 같은 곳에 두는 것**이라고 정리했습니다.

그리고 저장이라는 게 생각보다 순서에 예민했습니다. 두 가지를 더 정해야 했습니다.

하나는 **복원과 저장의 순서**입니다. 저장을 스토어 구독으로 걸어놨는데, 복원보다 먼저 돌면
**빈 스토어가 저장된 대화를 덮어씁니다.** 새로고침했더니 대화가 사라지는데, 정작 저장
로직은 정상 동작하고 있는 상황이죠. 복원이 끝났다는 플래그를 두고 그전까지는 저장을 막았습니다.

다른 하나는 **저장 시점**입니다. 처음엔 응답이 끝나는 종료 이벤트에서만 쓸까 했는데,
그러면 스트리밍 도중에 탭이 닫히면 그때까지 받은 답변이 통째로 날아갑니다.
그래서 스토어 구독으로 바꿨습니다. 토큰이 쌓일 때마다 메시지 배열이 갈아끼워지니까
스트림 중에도 계속 갱신됩니다.
**답변이 반쯤 온 상태로라도 남는 게, 아예 없는 것보다 낫다고 봤습니다.**

**빈 대화는 저장하지 않습니다.** 안 그러면 다른 탭이 시작한 대화를 이 탭이 빈 값으로
덮어쓸 여지가 생깁니다.

## 예상 질문

| 질문 | 답변 |
|---|---|
| **"threadId 도입을 왜 프론트가 제안했나요?"** | 문제를 먼저 본 게 프론트였습니다. 세션을 공유하기로 한 게 프론트 결정이었고, 그 결정이 서버 맥락을 하나로 합친다는 걸 그 자리에서 봤습니다. 서버 입장에서는 요청이 정상적으로 들어오고 있어서 이상 신호가 없습니다 |
| **"세션을 공유하지 말고 탭마다 따로 두면?"** | 그게 원래 동작이었고 그래서 축출이 났습니다. 서버 발급이 신원·채널 단위라 탭을 구분하지 못합니다 |
| **"멀티탭을 서버에서 처리하면?"** | 세션 발급은 서버가 멱등으로 처리해줍니다. 프론트가 푼 건 호출 횟수와 탭별 방 구분입니다. **서버는 탭을 구분할 수 없습니다** |
| **"대화를 서버에 저장하면 되지 않나요?"** | 서버는 맥락을 10분만 들고 있고 말풍선은 보관하지 않습니다. 그리고 10분보다 오래 화면에 남기면 안 된다고 판단했습니다 |
| **"왜 localStorage가 아니라 sessionStorage?"** | 서버 맥락 TTL이 10분이라 영구 저장하면 어긋난 상태가 길어집니다. 탭 수명이 세션 수명과 가장 가깝습니다 |
| **"깨진 프레임이 실제로 오나요?"** | 빈도는 측정하지 않았습니다. 다만 한 번 나면 이미 찍힌 답변 위에 오류가 덮이는 형태라 피해가 커서 방어했습니다 |
| **"EventSource를 쓸 방법은 정말 없었나요?"** | 티켓을 쿼리스트링에 실으면 GET으로 가능하지만, URL은 로그·리퍼러에 남습니다. 단명 티켓이어도 노출 경로를 늘리고 싶지 않았습니다 |

> ⚠️ 마지막 두 질문은 **측정하지 않은 것**과 **선택하지 않은 대안**이다.
> 물어보면 답하되 먼저 꺼내지 않는다. `presentation-talking-points.md` §4 참조.
