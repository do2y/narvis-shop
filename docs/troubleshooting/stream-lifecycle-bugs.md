## ① 깨진 프레임 하나가 턴 전체를 죽였다

### 원인 두 가지

- `JSON.parse` 실패가 **read 루프 밖으로 던져졌다.** 깨진 프레임 뒤의 정상 이벤트를 전부 잃는다.
  `done`·`products.ready`가 그 뒤에 있으면 리포트 커밋도 카드 조회도 일어나지 않고,
  호출부는 이를 스트림 실패로 처리해 이미 찍힌 답변 위에 오류 말풍선을 붙였다.
- 서버가 마지막 프레임을 `\n\n`으로 닫지 않고 끊으면 **버퍼에 남은 조각을 버렸다.**
  마지막 프레임은 대개 `done`이라, 판매자 리포트가 패널에 커밋되지 않고 `zero_result` 기본 문구도 비었다.

### 선택

| 선택 | 버린 대안 | 이유 |
|---|---|---|
| 프레임 단위로 무시 (`emitChunk` 분리 + try/catch) | 엄격한 파싱(throw) | 계약이 이미 "모르는 이벤트는 무시"를 명문화했다(개방형 유니온). **같은 규칙을 깨진 프레임에도 적용하는 게 일관된다** |
| 루프 종료 후 남은 버퍼도 같은 규칙으로 파싱 | 현상 유지 | 정상 스트림은 버퍼가 비어 있어 no-op — 기존 동작이 바뀌지 않는다 |

### 후속 — 끊긴 스트림을 성공으로 보지 않는다 (`d161350`)

관용적으로 바꾸자 반대 방향의 구멍이 남았다. `done`·`error` 없이 read가 끝나도 정상 종료처럼 지나갔다.
**종결 이벤트를 보지 못하면 `StreamInterruptedError`로 실패시키고** 재시도 버튼을 준다.
반쯤 잘린 답변이 버튼 없이 남는 쪽이 사용자에게 더 나쁘다.

> 정리하면 **프레임은 관용, 종결은 엄격**이다. 개별 프레임은 흘려보내되 턴이 끝났다는 신호는 반드시 확인한다.

## ② 화면을 떠나도 스트림이 살아 있었다

### 원인

스토어가 **zustand 모듈 전역**이라 컴포넌트가 사라져도 남는다. 화면을 떠난 뒤에도 fetch 리더가 돌며
스토어를 갱신했고, 특히 `finally`의 `setStreaming(false)`가 늦게 도착하면 **`isStreaming`이 true로 굳어**
재진입 시 입력창이 막히거나 이전 턴 token이 복원된 대화에 이어붙었다.

### 선택

| 선택 | 버린 대안 | 이유 |
|---|---|---|
| 언마운트 시 `abort` | 이벤트 핸들러마다 `mounted` 가드 | 가드는 모든 분기에 뿌려야 하고 네트워크는 계속 돈다. abort는 **네트워크까지 실제로 정리**한다 |
| 중단을 오류와 분리 (`isAbortError`를 catch 최상단에) | 일반 실패로 처리 | abort를 넣자 abort 예외가 일반 실패로 떨어져 **떠나온 대화에 "응답을 받지 못했어요"가 남았다** |
| 중단을 **이름으로** 판정 | `instanceof` | fetch는 `DOMException("AbortError")`, axios는 `CanceledError`, jsdom·polyfill은 생성자가 다를 수 있다 |

두 번째 행은 첫 번째 수정이 드러낸 문제다. 종전에도 "새 대화" 버튼의 abort가 같은 자리로 떨어졌지만
뒤따르는 `reset()`이 말풍선을 지워 보이지 않았다. **언마운트 경로에는 지울 주체가 없다.**

### 후속 회귀 — StrictMode 가짜 언마운트 (`36fb6d5`)

같은 날 반대 증상이 나왔다. 홈에서 질문 칩을 누르면 `/chat`으로 넘어가 말풍선까지 뜨는데 **답변이 오지 않고
Network 탭에 AI 서버 요청이 아예 없었다.**

- React StrictMode(dev)는 마운트 → 언마운트 → 재마운트를 한 번 흉내 낸다
- 그 **가짜 언마운트**에서 abort가 즉시 실행돼, `?q=`로 시작한 유일한 전송을 첫 프레임 전에 끊었다
- 오류 문구도 없었다 — AbortError는 위에서 "의도적 이탈"로 걸러내도록 만들었기 때문

**abort를 한 틱 미루고, 재마운트가 뒤따르면 취소를 철회한다.** 진짜 이탈이면 타이머가 그대로 실행된다.
프로덕션에는 가짜 언마운트가 없어 한 틱 늦어질 뿐 동작은 같다.

진단 경위: 코드만 읽고 추측해 두 번 헛짚었고(`authStore`, 승계 실패 저장소),
임시 계측 로그로 AbortError 스택을 찍은 뒤에야 cleanup 지점이 드러났다.

## ③ 업로드 경쟁 상태 — 취소 수단이 없을 때

### 원인

1장째 업로드 중 2장째를 고르면 `clearAttach()`가 1장째 blob URL을 revoke하지만,
**1장째 업로드 요청은 계속 살아 있다가** 끝나면서 첨부 상태를 자기 것으로 되돌렸다.
깨진 미리보기가 뜨고, 전송되는 `imageUrl`은 판매자가 취소한 사진이 된다.

### 선택

| 선택 | 버린 대안 | 이유 |
|---|---|---|
| 세대 토큰(`uploadGenerationRef`) — 결과를 쓰기 직전에 최신인지 확인 | `AbortController` | 업로드 API가 `signal`을 받지 않아 호출부에서 취소할 수단이 없다 |
| 리소스 해제와 상태 무효화를 분리 (`clearAttach`도 세대를 올림) | revoke만 | revoke는 blob만 풀 뿐 **늦게 도착한 상태 갱신은 막지 못한다** |

같은 커밋에서 첨부한 채 화면을 떠날 때 blob URL이 revoke되지 않던 누수도 고쳤다.

## 함께 정리한 것

- `useChat`이 선택자 없이 스토어 전체를 구독해 token마다 챗 페이지가 통째로 리렌더되던 것을 `isStreaming` 구독으로 좁혔다.
  **렌더 횟수·프레임은 측정하지 않았다** — 성능 개선 수치로 말할 근거가 없다
- `ProductPanel`의 React key가 `group.title`이라 `label` 없는 추천 묶음이 여러 개 오면 중복 키가 되던 것을 `listId` 기반으로 바꿨다.
  조건 칩의 `(field, value)` 키 충돌(→ `docs/architecture/chat.md` §7)과 **같은 함정이 다른 파일에서 재발**한 사례다.
  경고가 그 파일 주석에만 있었다

## 배운 것

- **개방형 유니온을 택한 계약은 파서 층에도 같은 관용성을 요구한다.** 한 층만 엄격하면 그 층이 단일 실패점이 된다.
  다만 종결 신호까지 관용으로 처리하면 끊긴 응답이 성공처럼 남는다
- **"React가 정리해 준다"는 컴포넌트 지역 상태에만 해당한다.** 전역 스토어에 쓰는 비동기는 생명주기를 스스로 책임져야 하고,
  정리 코드를 넣을 때는 StrictMode의 가짜 언마운트까지 고려해야 한다
- **취소는 오류 분류 체계에 자기 자리가 있어야 한다.** 없으면 "실패"로 흘러든다
- **비동기 결과는 쓰기 직전에 "아직 최신인가"를 묻는다.** 해제와 무효화는 별개다
