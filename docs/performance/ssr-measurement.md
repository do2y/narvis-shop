# SSR 전환 효과 측정 — Vite(CSR) vs Next.js(SSR)

> 측정일: 2026-10-22 · 로컬 · Lighthouse 12.8.2 모바일 · **실측 스로틀링(`--throttling-method=devtools`)**
>
> 전환(2026-07-28)의 목적은 **검색 노출과 공유 링크 미리보기**였다. 전환 당시에는
> "HTML 에 본문이 들어가는 구조를 갖췄다"까지만 확인하고 수치로 재지 않았다.
> 이 문서는 그 전후를 같은 조건에서 비교한 기록이다.
>
> ⚠️ 이 문서의 첫 판(`7931375`)은 **"LCP 는 줄지 않았고 원인은 웹폰트"** 라고 결론 내렸는데 둘 다 틀렸다.
> Lighthouse 기본값인 시뮬레이션 추정치를 실측처럼 읽은 탓이다. 아래 [정정 이력](#정정-이력) 참조.

## 결론

- **목적한 것은 달성됨.** CSR 은 세 페이지 모두 459B 빈 껍데기(`<title>jarvis-web</title>`, 공유 메타 없음)였고,
  SSR 은 상품명·가격·페이지별 `og:title`·`og:image`·`description` 이 첫 HTML 에 들어 있음. SEO 점수 83 → 100
- **LCP 31~42% 단축.** 상세 4.18초 → 2.41초, 브랜드 4.04초 → 2.70초, 홈 3.34초 → 2.30초
- **FCP 약 1초 단축**, Lighthouse 성능 점수 78~83 → 92~95
- **웹폰트 서브셋은 LCP 를 줄이지 못함.** 전송량은 2.5MB → 0.85MB(−66%)로 줄지만 LCP 는 0.1~0.24초 늦어짐.
  SSR 에서는 글자가 대체 폰트로 먼저 그려져(`font-display: swap`) 폰트 크기가 LCP 를 막지 않기 때문 → **적용하지 않음**
- **대가**: JS 190KB → 473KB. 메인 스레드 차단(TBT)은 0~12ms → 7~65ms 로 늘었으나 기준(200ms) 대비 낮음

|---|---|---|

| 실행 | `vite build` → `vite preview` | `next build` → standalone `node server.js` (배포와 같은 방식) |
| 데이터 | `/api` 를 Next 목 서버로 프록시 | `MOCK_API=1` 목 (SSR·클라이언트 공용) |

- **양쪽이 같은 목 데이터를 네트워크로 받게 맞춤.** 처음엔 Vite 를 MSW 로 띄웠는데, MSW(464KB)가 앱보다 먼저 떠야
  렌더가 시작돼 CSR 이 부당하게 느려지므로 버림
- CSR 도 JS 실행 후에는 같은 내용을 그림을 헤드리스 Chrome `--dump-dom` 으로 확인함(상세 38,700B · '에어플로우 러닝화' 2회 등)
- 이미지는 양쪽 모두 인라인 SVG(data URI) — 이미지 크기 차이가 LCP 에 섞이지 않음
- 홈 경로가 다른 건 2026-08-12 루트 전환(`/` = 랜딩, `/home` = 쇼핑몰 홈) 때문. 같은 화면을 비교함
- **모든 측정 회차에서 CSS 요청 실패 0건·폰트 수신을 확인함**(아래 정정 이력의 무효 측정 재발 방지)

## 3. 웹폰트 서브셋 실험 — 가설 반증

시뮬레이션 수치를 보고 "LCP 가 2MB 웹폰트에 묶였다"는 가설을 세워 검증함.

- 변경: `globals.css` 1행의 `pretendardvariable.min.css` → `pretendardvariable-dynamic-subset.min.css`
  (같은 CDN·같은 v1.3.9. 글자 범위별 92개 묶음으로 나뉘어 화면에 쓰인 묶음만 받음)

| 페이지 | 폰트 | 폰트 전송 | 전체 전송 | FCP | LCP |
|---|---|---|---|---|---|
| 상세 | 전체 | 2,011KB (1개) | 2,567KB | 2,414ms | 2,414ms |
| 상세 | 서브셋 | 313KB (12개) | 881KB | 2,506ms | 2,506ms |
| 브랜드 | 전체 | 2,011KB (1개) | 2,549KB | 2,694ms | 2,700ms |
| 브랜드 | 서브셋 | 260KB (10개) | 810KB | 2,780ms | 2,793ms |
| 홈 | 전체 | 2,010KB (1개) | 2,527KB | 2,302ms | 2,302ms |
| 홈 | 서브셋 | 332KB (13개) | 861KB | 2,545ms | 2,545ms |

- **LCP 는 줄지 않고 0.1~0.24초 늦어짐 → 가설 틀림.** 폰트가 `swap` 이라 글자가 대체 폰트로 먼저 그려지므로
  폰트 크기가 LCP 를 막지 않음. 서브셋 판은 CSS 가 588B → 53KB 로 커지고, 이 CSS 가 렌더 차단 경로
  (HTML → Next CSS → `@import` 외부 CDN CSS)에 있어 오히려 첫 페인트가 늦어진 것으로 봄
- 전송량 −66%(약 1.7MB 절감)는 실재함 — 모바일 데이터 비용 측면의 이득. 다만 이번 목적(LCP)에는 해당하지 않음
- **결정: 적용하지 않음.** 폰트를 손보려면 서브셋이 아니라 외부 `@import` 사슬을 끊는 쪽(self-host + `preload`, `next/font`)을
  검토해야 함 — 이번 범위 밖

## 4. 대가 — JS 증가

- JS 190KB → 473KB(+283KB). Next 런타임·RSC 페이로드·하이드레이션 코드
- TBT 0~12ms → 7~65ms. 기준(200ms) 대비 낮아 체감 영향은 작다고 봄. 다만 "SSR 은 공짜"는 아님

## 한계 — 이 수치로 말할 수 없는 것

- **로컬 측정이다.** 실사용자 데이터(필드 데이터)·실제 검색 유입이 아님. "검색 유입이 늘었다"는 여전히 말할 수 없음
- **목 데이터다.** 실제 백엔드의 응답 시간이 빠져 있음. 실서버에선 SSR 은 서버에서 API 를 기다리는 만큼 TTFB 가 늘고,
  CSR 은 브라우저에서 같은 시간을 기다림. 서버↔백엔드가 같은 망이라 SSR 쪽이 유리할 것으로 보이나 **재지 않았음**
- CSR 은 Vite preview 프록시를 한 번 더 거침(로컬이라 수 ms 수준)
- 비교 대상 사이에 7~9월 변경이 있음(`62267ff` → `5dd240a`). 화면 구성이 완전히 같지는 않음
- 실측 스로틀링도 로컬 머신 성능에 좌우됨. 절대값보다 **같은 조건에서의 차이**로 읽을 것

## 정정 이력

### 1. 시뮬레이션 LCP 를 실측처럼 읽음 (첫 판의 결론 오류)

첫 판은 Lighthouse 기본값(`simulate`)으로 재서 "LCP 는 CSR·SSR 모두 3초대로 그대로"라고 썼다.
같은 회차의 관측값을 보니 전혀 달랐다.

| | 관측 LCP (스로틀 없음) | 시뮬레이션 LCP |
|---|---|---|
| CSR | 1,481ms | 3,081ms |
| SSR | 112ms | 3,130ms |

- 시뮬레이션은 스로틀 없이 한 번 로드한 뒤 요청 의존 그래프로 "느린 환경이면 이랬을 것"을 **추정**한다.
  관측 LCP 이전에 끝난 요청(여기서는 2MB 폰트)을 추정에 끌어들여 양쪽을 3초대로 뭉뚱그렸음
- 실측 스로틀링으로 다시 재서 31~42% 단축을 확인함. **모델의 추정치와 관측치가 크게 어긋나면 관측으로 다시 잰다**

### 2. 측정 스크립트가 엉뚱한 대상을 잼 (2건, 둘 다 결과 공개 전에 발견)

- **zsh 변수 분리** — zsh 는 따옴표 없는 변수를 공백으로 나누지 않고, `path` 는 `PATH` 와 묶인 예약 변수다.
  첫 HTML 비교에서 경로가 빠져 상세·브랜드 대신 랜딩 페이지를 재고 있었음 → 측정 스크립트를 bash 로 바꿈
- **이전 서버가 살아 있음** — 서브셋 빌드 후 새 서버가 포트 충돌로 뜨지 못했고, 옛 서버가 바뀐 빌드 폴더를 서빙해
  CSS 가 404 였다. 스타일 없는 페이지라 LCP 가 2.5초대로 "좋아 보였다". 프로세스 이름이 `next-server` 로 바뀌어
  이름 기반 종료가 걸리지 않았던 것 → 포트 기준으로 종료하고, **모든 회차에서 CSS 실패 0건·폰트 수신을 검사**하도록 함

## 재현 방법

```bash
# 후(SSR) — 배포와 같은 standalone 방식. `next start` 는 output: standalone 과 맞지 않아 SSR 목이 동작하지 않음
MOCK_API=1 npm run build
cp -R public .next/standalone/ && cp -R .next/static .next/standalone/.next/
(cd .next/standalone && MOCK_API=1 PORT=3000 HOSTNAME=127.0.0.1 node server.js)

# 전(CSR) — 전환 직전 커밋을 별도 작업 폴더로
git worktree add ../before 62267ff && cd ../before && npm ci
npx vite build   # VITE_ENABLE_MOCKS 를 켜지 않는다(MSW 제외)
VITE_API_PROXY_TARGET=http://127.0.0.1:3000 npx vite preview --port 4173

# 첫 HTML
curl -s http://127.0.0.1:3000/products/9001 | grep -o '<title>[^<]*</title>'

# Lighthouse (프로젝트 의존성에 추가하지 않고 1회 실행)
npx -y lighthouse@12.8.2 <url> --output=json --only-categories=performance \
  --throttling-method=devtools --chrome-flags="--headless=new"
```

- 서버를 다시 띄우기 전에 `lsof -ti tcp:3000` 으로 포트가 비었는지 확인할 것
- 결과 JSON 의 `network-requests` 에서 Stylesheet 실패가 없는지, Font 를 받았는지 확인할 것
- 스크립트는 bash 로 돌릴 것(zsh 변수 분리 차이)
