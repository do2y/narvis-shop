# 행동 이벤트 401 재전송 — 재시도를 안 하기로 한 코드에 예외 하나를 뚫은 이유

> E-1 수집에서 **AT 만료 구간의 배치가 통째로 사라지던** 문제와, 그 해결로 401 하나만
> 재전송하기로 한 판단의 기록. 2026-08-11.
>
> 코드에는 "재시도하면 중복·부하만 는다"는 반대 방향의 판단이 이미 주석으로 적혀 있었다.
> 그걸 뒤집은 게 아니라 **성질이 다른 한 가지를 갈라낸 것**이라, 왜 401만인지를
> 남겨두지 않으면 나중에 5xx까지 넓어지거나 통째로 되돌려진다.

## 배경 — 문서가 전제한 동작이 없었다

노션 「🧩 API 명세와의 정합 요구사항」(2026-08-10)이 짚은 어긋남이다.

E-1 명세는 오랫동안 **"500·401이면 SDK가 재전송한다"**를 전제로 쓰여 있었는데, FE 구현
(`src/shared/analytics/track.ts`)은 응답 상태를 아예 검사하지 않았다. `fetch(...).catch(() => {})`가
전부였다 — 네트워크 오류만 삼키고, 서버가 거부한 응답은 성공과 구분되지 않았다.

노션 E-1은 **현재 동작대로 개정**된 상태다(구 문구가 사실과 달랐으므로). 그리고 FE에
둘 중 하나를 고르라는 요청이 남았다.

## 왜 이게 실제로 데이터를 잃는가

`flush()`가 **전송 전에 큐를 비운다.**

```ts
export function flush() {
  clearTimer();
  const batch = queue;
  queue = [];          // ← 여기서 이미 비었다
  for (...) send(...); // ← 실패해도 돌아갈 곳이 없다
}
```

이 자체는 옳다 — 전송 중에 새 이벤트가 쌓이므로 큐를 붙들고 있으면 중복이 생긴다.
다만 **실패한 배치의 복구 경로가 없다**는 뜻이기도 하다. 잃으면 끝이다.

### 500과 401은 무게가 다르다

| | 빈도 | 성질 |
|---|---|---|
| **500** | 거의 없음 — BE가 토픽 발행 실패 시 DB 직접 적재로 폴백(08 D7) | 서버가 받았는지 알 수 없음 |
| **401** | **AT 수명 30분마다 구간이 열림** | 서버가 받고 명시적으로 거부 |

401이 문제다. `AUTH_TOKEN_EXPIRED` 정책(2026-08-07)은 *"FE가 A-4로 재발급한 뒤
재전송한다"*를 전제로 만들어졌는데 **그 전제가 구현되지 않았다.** 그래서 지금은
귀속을 지키려다 이벤트를 버리고 있었다. 활발한 사용자일수록 많이 잃는다 —
정작 데이터가 가장 중요한 구간이다.

## 선택지 둘, ①을 골랐다

문서가 제시한 것:

- **① FE가 401만 재전송** — A-4 재발급 후 그 배치를 한 번 다시 보낸다
- **② BE가 401 정책을 되돌림** — 만료 쿠키를 거부하지 않고 무시한 뒤 익명으로 적재

**②는 FE 작업이 없는 게 아니라 손실의 종류를 바꾸는 것이다.** 이벤트는 남지만 로그인
사용자의 행동이 익명으로 쌓인다. 귀속이 깨진 채 저장되면 나중에 복구할 방법이 없다.
①은 귀속과 이벤트를 둘 다 지킨다.

**재전송의 위험이 401에는 없다.** 기존 주석의 판단은 일반 재시도에 대해서는 맞지만,
401은 서버가 요청을 받고 거부한 것이라 적재가 일어나지 않았음이 확실하다. 게다가
`id`가 UNIQUE라 서버가 중복을 막는 이중 안전장치도 있다(계약 E-1). 5xx나 네트워크
오류처럼 "서버가 받았는지 모르는" 상태가 아니다.

## 구현에서 갈린 것 두 가지

### client.ts의 refresh를 재사용하지 않았다

그쪽은 재발급에 실패하면 **로그인 화면으로 리다이렉트한다**(`redirectToLogin()`).
수집은 배경 작업이라, 상품을 보던 사용자가 이벤트 전송 실패 때문에 갑자기 로그인
화면으로 튕기게 된다. `track.ts`가 애초에 `api` 인스턴스를 피한 것과 같은 이유다.

`retry.ts`의 `refreshToken()`은 성공 여부만 boolean으로 돌려주고 리다이렉트하지 않는다.
실패하면 그 배치는 잃는 것으로 끝낸다 — 로그인 상태가 정말 끝난 것이라 다시 보내도
또 401이다.

### 재전송은 1회뿐

두 번째 401은 재발급이 됐는데도 거부됐다는 뜻이라 더 보내도 결과가 같다.
루프가 되지 않는 것을 테스트로 고정했다.

### keepalive 경로는 대상이 아니다

`pagehide`·`visibilitychange`에서 나가는 배치는 탭이 닫히는 중이라 재발급을 기다릴
시간이 없다. 막지는 않았지만(코드가 복잡해진다) 실질적으로 평시 flush만 살아난다.
이 구간까지 살리려면 서버 쪽에서 만료를 관대하게 다루는 ② 계열이 맞다.

## 넓히지 말아야 할 것

⚠️ **이 예외를 5xx로 넓히면 원래 주석이 경고하던 중복·부하가 실제로 생긴다.**

`shouldRetryBatch(status)`가 401 하나만 통과시키고, 그 범위를 테스트가 붙들고 있다.
`it.each([202, 400, 403, 429, 500, 502, 503])`가 전부 false여야 한다 — 이게 깨지면
누가 범위를 넓혔다는 뜻이다.

기존 "재시도하면 중복·부하만 는다"는 주석은 **지우지 않고 남겼다.** 401만 예외인
이유를 그 옆에 적어야, 나중에 "재시도 로직이 있네" 하고 확장하는 일을 막을 수 있다.

## 남은 것

노션 E-1의 🔴 미결 항목은 이 결정으로 닫힌다. BE 쪽 추가 작업은 없다 —
①은 FE 단독으로 완결된다.
