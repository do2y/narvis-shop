# 발표에서 말하기 좋은 것 — 프론트 기여도 기준 정리

> 작성일 2026-08-12.
> **선정 기준은 "재미있는가"가 아니라 "프론트가 실제로 판단했는가"다.**
> 서버가 한 일을 프론트 성과로 말하면 질문 한 번에 무너진다.
> 각 항목에 **프론트 기여도**와 **말하면 안 되는 것**을 함께 적었다.
>
> 상세 내용은 `presentation-chat-session-design.md`(채팅 세션)와
> `presentation-frontend-draft.md`(전체 초안) 참조.

---

## 0. 이 문서를 쓰는 법

발표 준비할 때 순서는 이렇다:

1. **§1 등급표**에서 무엇을 말할지 고른다 (A등급부터)
2. **§3 프레이밍**에서 그 소재를 **어떻게 말할지** 확인한다 (여기가 핵심)
3. **§4 함정**에서 하면 안 되는 말을 확인한다
4. 시간이 남으면 §5 예상 질문

## 1. 소재 등급표 — 프론트 기여도 순

| 등급 | 소재 | 프론트 기여 | 시연 난이도 | 비고 |
|---|---|---|---|---|
| **A** | **멀티탭 세션 조정** (락·방송 2종·저장소 분리) | **100%** | 중 (탭 2개) | 서버가 대신할 수 없는 영역 |
| **A** | **대화 복원** (새로고침·탭 복구) | **100%** | **하 (새로고침 1번)** | 시연이 가장 쉬움 |
| **A** | **승계 실패 UX** (3지선다 배너·발급 차단) | **100%** | 중 (실패 유도 필요) | 판단이 가장 잘 드러남 |
| **A** | **SSR 경계 판단** (전부 서버로 안 보낸 이유) | 100% | 하 (HTML 소스) | 지표 3번 유일 대응 |
| **B** | **조건 칩** (AI 결과를 조작 가능하게) | 90% | **하 (칩 클릭)** | 서비스 가치와 직결 |
| **B** | **성능 가설 반증** (측정으로 3번 뒤집힘) | 100% | 중 (수치 자료) | 태도가 좋게 읽힘 |
| **B** | **계약을 테스트로 옮긴 것** | 100% | 하 (테스트 실행) | 협업 사례 |
| **C** | 승계 호출 시점 판단 | 판단만 | 하 | 단독으론 약함 |
| **C** | httpOnly 쿠키 전환 | 공동 | 중 | BE 협의 사항 |
| **D** | ~~게스트→회원 승계 자체~~ | **서버** | — | **배경으로만 쓸 것** |
| **D** | ~~게스트 장바구니 승계~~ | **서버** | — | **말하지 말 것** |

> **A등급 4개 + B등급 1~2개**면 15분 발표가 채워진다.
> D등급은 **"왜 이 문제가 생겼는지" 설명하는 배경**으로만 쓰고, 성과로 말하지 않는다.

## 2. A등급 소재 — 무엇을 말할 것인가

### 2-1. 대화 복원 ⭐ 시연이 가장 쉽다

**한 줄**: 새로고침해도 대화가 남는다. **그런데 영구 저장으로 하면 안 됐다.**

| 항목 | 내용 |
|---|---|
| **왜 프론트 몫인가** | 서버는 `sessionId`만 알고 **말풍선을 보관하지 않는다.** 대응하는 API 자체가 없다 |
| **판단 ①** | 저장 범위를 **sessionStorage(탭 단위)**로. localStorage면 영구히 남는데 **서버 맥락 TTL은 10분**이라 어긋난 상태가 길어진다 |
| **판단 ②** | **복원 → 저장 순서 강제.** 없으면 빈 스토어가 저장된 대화를 덮어쓴다 (`restored` ref) |
| **판단 ③** | 저장 시점을 **스토어 구독**으로. `done`에만 쓰면 스트리밍 중 탭이 닫힐 때 답변이 통째로 날아간다 |
| **판단 ④** | **빈 대화는 저장하지 않는다.** 다른 탭이 시작한 대화를 덮어쓸 여지가 생긴다 |

**근거**: [useChatPersistence.ts:14-15](src/shared/chat/useChatPersistence.ts#L14-L15)(순서) ·
[:36-39](src/shared/chat/useChatPersistence.ts#L36-L39)(구독) ·
[chatPersistence.ts:8-13](src/shared/chat/chatPersistence.ts#L8-L13)(탭 단위 근거) ·
[:37-42](src/shared/chat/chatPersistence.ts#L37-L42)(빈 대화)

**PPT 문구**
- 저장소는 **편한 곳이 아니라 수명이 같은 곳**에
- 서버가 10분 기억한다 → 화면도 그보다 오래 남기지 않는다
- 복원보다 저장이 먼저 돌면 **빈 값이 대화를 덮어쓴다**

**시연**: 대화 3턴 → **새로고침** → 그대로 남아 있음. 10초면 끝난다.

---

### 2-2. 멀티탭 세션 조정 ⭐ 기여도가 가장 높다

**한 줄**: 멀티탭은 UI 문제가 아니라 **공유 메모리가 없는 분산 문제**였다.

| 판단 | 내용 |
|---|---|
| **저장소를 4계층으로** | 세션(localStorage 25초·탭 공유) / 방·대화(sessionStorage·탭별) / 화면(메모리) |
| **락 진입 후 재확인** | 없으면 탭 N개가 순서대로 들어와 각자 발급 — **락을 쓴 의미가 사라진다** |
| **락 범위를 좁힘** | SSE 스트림까지 감싸면 그동안 다른 탭의 발급이 전부 막힌다 |
| **방송 2종 분리** | `session`(티켓 갱신) vs `ownership`(주인 교체) — 하나면 **"새 티켓"과 "내 자격 무효"를 구분 못 함** |
| **순서 고정** | `publish` → `ownership`. 반대면 방금 심은 유효 티켓을 받는 탭이 지운다 |
| **전송을 막지 않음** | 깨지는 건 수십 ms뿐인데 막으면 **멀쩡한 대화까지 끊긴다** |

**근거**: [sessionCoordinator.ts:201-203](src/shared/chat/sessionCoordinator.ts#L201-L203)(재확인) ·
[:54-66](src/shared/chat/sessionCoordinator.ts#L54-L66)(방송 2종) ·
[:276-284](src/shared/chat/sessionCoordinator.ts#L276-L284)(순서)

**PPT 문구**
- 멀티탭은 **FE의 분산 문제**다
- 락은 짧게 — **오래 걸리는 걸 감싸면 락이 병목**이 된다
- "새 티켓이 왔다" ≠ "내 자격이 무효다"

---

### 2-3. 승계 실패 UX ⭐ 판단이 가장 잘 드러난다

**한 줄**: 조용히 넘어가지 않기로 했다.

**처음(잘못된 것)** → 실패 시 `sessionId`만 비우고 조용히 새 세션
→ **화면엔 대화가 있는데 AI는 기억 못 하는** 상태. 에러도 안 뜸

**고친 것** → 세션 발급 자체를 **차단**(`SessionClaimPendingError`)하고 3지선다 배너
(다시 시도 / 기억 없이 계속 / 지우고 새로 시작)

> **핵심 문장**: *"막으려던 건 '조용히' 맥락이 끊기는 것이지, 사용자의 선택이 아니다."*

**한 번 더 놓쳤다가 잡은 것** — 처음엔 `ApiError`만 실패로 잡았는데
**네트워크 단절·타임아웃**은 안 걸려서 배너 없이 넘어갔다.
**없애려던 조용한 실패가 다른 문으로 돌아온 것.**
→ [claimOnLogin.ts:49-51](src/shared/chat/claimOnLogin.ts#L49-L51) · 테스트로 고정 [claimOnLogin.test.ts:63-78](src/shared/chat/claimOnLogin.test.ts#L63-L78)

**PPT 문구**
- **조용한 실패가 시끄러운 실패보다 나쁘다**
- 예외를 좁게 잡으면 **없애려던 문제가 다른 문으로 돌아온다**

---

### 2-4. SSR 경계 판단

**한 줄**: SSR은 켜고 끄는 스위치가 아니라 **경계를 긋는 일**이었다.

- 기준: **"공개 라우트인가"** — 상품·브랜드·홈은 SSR / mypage·checkout·seller는 안 함
- 안 한 이유: 가드·세션 복원이 **클라이언트 기준**이라 옮기면 이중 관리
- 함정 3개의 공통점: **셋 다 에러가 안 난다**
  - `initialData`를 모든 키에 → "정렬이 안 먹는다"
  - `useSearchParams` → Suspense → **빈 HTML**(`/login`이 9KB)
  - 타임아웃 없는 서버 fetch → **CI 빌드가 멈춤**

> 상세는 `presentation-frontend-draft.md` 슬라이드 1-1 참조.

## 3. 프레이밍 — 같은 사실도 이렇게 말해야 한다

> **이 절이 이 문서에서 제일 중요하다.**
> 소재를 고르는 것보다 **어떻게 말하는지**가 발표의 성패를 가른다.

| ❌ 이렇게 말하면 | ⭕ 이렇게 말한다 | 왜 |
|---|---|---|
| "게스트 승계를 구현했습니다" | "승계를 **언제 부를지, 실패하면 어떻게 할지**를 정했습니다" | 승계 자체는 서버가 한다. 질문 한 번에 무너진다 |
| "챗봇 2개를 공통 모듈로 만들었습니다" | "공통화 기준을 **화면이 비슷한가가 아니라 수명이 같은가**로 잡았습니다" | 전자는 "재사용했다"로만 들린다 |
| "대화를 저장했습니다" | "**어디까지 저장할지를 서버 TTL과 맞췄습니다**" | 저장은 누구나 한다. 판단이 안 보인다 |
| "멀티탭 버그를 고쳤습니다" | "**공유 메모리가 없는 분산 문제**로 접근했습니다" | 버그 수정이 아니라 설계로 읽히게 |
| "테스트 243개를 짰습니다" | "**손으로 재현할 수 없는 상황**이 있었습니다" | 숫자 자랑으로 읽히면 가장 약해진다 |
| "SSR로 성능이 좋아졌습니다" | "SSR은 **스위치가 아니라 경계**였습니다" | 성능은 **측정한 적이 없다** |
| "예외 처리를 꼼꼼히 했습니다" | "에러를 띄우는 게 아니라 **다음 행동을 줍니다**" | 전자는 내용이 없다 |

### 프레이밍의 공통 원칙

**"무엇을 만들었다"가 아니라 "무엇을 정했다"로 말한다.**

만든 것은 코드를 보면 알지만, **왜 그렇게 정했는지는 본인만 안다.**
발표에서 값어치 있는 건 후자다.

## 4. 말하면 안 되는 것 (질문 한 번에 무너지는 지점)

| ❌ 금지 | 이유 | 대신 |
|---|---|---|
| "게스트 장바구니 승계를 구현했다" | **서버가 `guest_id` 쿠키로 자동 처리.** FE는 `withCredentials`만 보장 | 배경 설명으로만 언급 |
| "SSR로 성능이 개선됐다" | **LCP·검색 유입을 측정한 적 없음** | "HTML에 본문이 들어가는 구조를 갖췄다" |
| "검색 노출이 늘었다" | 서치콘솔로 확인한 바 없음 | 말하지 않는다 |
| "관리자 페이지를 만들었다" | **라우트가 없음** | "우선순위에서 뺐고, 가드는 미리 만들어뒀다" |
| "프론트 가드로 막았다" | 가드는 UX 필터라 **우회 가능** | "최종 방어선은 백엔드다. 설계상 의도다" |
| "커버리지 N%" | **측정한 적 없음** | 테스트 개수만 말하거나 언급 안 함 |
| "승계 실패는 거의 안 난다" | **빈도를 측정한 적 없음** | "실패 종류가 5가지라 처방을 나눴다" |

### 한계를 먼저 말하는 게 유리한 지점

발표에서 **스스로 밝히면 강점**이 되고, **물어봐서 나오면 약점**이 되는 것들:

- **접근성** — aria는 넣었지만 바텀시트 키보드 조작·차트 대체 표는 못 함
- **Web Locks 지원 범위** — degrade 경로는 만들었지만 어떤 브라우저가 타는지 미조사
- **멀티탭 통합 테스트** — 단위 테스트는 있지만 탭 2개 띄우는 검증은 **수동**
- **SSR 효과** — 구조는 갖췄지만 **수치로 재지 않음**

## 5. 예상 질문 대비

| 질문 | 답변 |
|---|---|
| **"그거 서버가 하는 거 아닌가요?"** (승계) | **"네, 승계 자체는 서버가 합니다.** 제가 정한 건 호출 시점과 실패 처리입니다. 서버는 어디서 로그인했는지 모르니까요" |
| **"멀티탭을 서버에서 처리하면?"** | 세션 발급은 서버가 멱등으로 처리해줍니다. 프론트가 푼 건 **호출 횟수와 탭별 방 구분**입니다. 서버는 탭을 구분할 수 없습니다 |
| **"대화를 서버에 저장하면 되지 않나요?"** | 서버는 맥락을 10분만 들고 있고 말풍선은 보관하지 않습니다. 그리고 **10분보다 오래 화면에 남기면 안 된다**고 판단했습니다 |
| **"왜 localStorage가 아니라 sessionStorage?"** | 서버 맥락 TTL이 10분이라 영구 저장하면 어긋난 상태가 길어집니다. 탭 수명이 세션 수명과 가장 가깝습니다 |
| **"Web Locks 지원 안 되면?"** | 300ms 대기 후 캐시 재확인으로 저하됩니다. 최악이 중복 발급 1회라 손해가 작다고 봤습니다. **다만 어떤 브라우저가 이 경로를 타는지는 조사 못 했습니다** |
| **"테스트는요?"** | 채팅 모듈만 85개 통과합니다. **다만 전부 단위 테스트고 탭 2개 띄우는 통합 검증은 수동입니다** |
| **"왜 25초인가요?"** | 티켓 TTL이 30~60초라 만료 직전 걸 재사용하지 않으려고 짧게 잡았습니다 |
| **"AI가 이상한 답을 하면?"** | 조건을 칩으로 노출해서 **사용자가 직접 지울 수 있게** 했습니다. 블랙박스로 두지 않는 게 핵심 판단이었습니다 |

## 6. 시간대별 구성 추천

| 시간 | 구성 | 비고 |
|---|---|---|
| **5분** | 대화 복원 → 멀티탭 | 시연 중심. 복원으로 시작하면 즉시 눈에 보임 |
| **10분** | 기능 개요 → **SSR 경계** → **멀티탭 + 승계 실패** → 테스트 | 지표 대응 최소 |
| **15분** | 위 + 조건 칩 · 성능 반증 | 권장 |
| **20분+** | `presentation-frontend-draft.md` 전체 구성 따름 | — |

### 순서를 짤 때의 원칙

1. **시연 가능한 것을 앞에** — 대화 복원처럼 눈에 보이는 것으로 시작하면 뒤의 추상적인 이야기가 붙는다
2. **추상 → 구체 착지** — 락·방송 같은 이야기 뒤에는 반드시 **화면**을 보여준다
3. **마무리는 "틀렸던 이야기"로** — 성능 가설 반증이나 승계 실패처럼
   *"내 판단이 틀렸고 그걸 확인했다"*로 끝나면 **겸손하되 근거 있는 태도**로 읽힌다

## 7. 한 문장으로 남길 것

발표가 끝나고 심사위원 머리에 하나만 남는다면 이것:

> **"프론트엔드에서 제일 어려웠던 건 화면을 그리는 게 아니라,
