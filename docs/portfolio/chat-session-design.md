## 한 줄 요약

> **채팅 세션은 화면 상태가 아니라 분산 상태였다.**
> 사용자 한 명이 탭 여러 개를 열고, 그 중 하나에서 로그인한다.
> 이때 **"무엇을 공유하고 무엇을 나눌지"**를 가르는 게 이 설계의 전부였다.

## 1. 문제 정의 — 왜 이게 어려운 문제였나

### 쇼핑에서 멀티탭은 예외가 아니라 정상 패턴이다

- 상품을 비교하려고 탭을 여러 개 여는 건 쇼핑몰에서 **가장 흔한 사용 방식**
- 그런데 채팅은 **세션(서버 맥락)을 가진 기능**이라, 탭이 늘어나면 세션이 서로 간섭함
- 게다가 우리 서비스는 **게스트도 채팅을 쓸 수 있음** → 로그인하는 순간 신원이 바뀜

### 겹쳐서 생기는 네 가지 난점

| # | 난점 | 왜 어려운가 |
|---|---|---|
| 1 | **탭 간 공유 메모리가 없다** | 같은 사용자인데 탭끼리 서로의 존재를 모름 |
| 2 | **동시 진입 시 N개 탭이 동시에 발급**(thundering herd) | 탭 3개를 한 번에 열면 세션 발급이 3번 나감 |
| 3 | **"세션"과 "대화방"의 수명이 다르다** | 로그인 자격은 공유해야 하지만 대화 내용은 탭마다 달라야 함 |
| 4 | **게스트→회원 전환이 중간에 끼어든다** | 한 탭에서 로그인하면 **다른 탭이 든 게스트 자격이 그 순간 무효**가 됨 |

> **핵심 인식**: 3번과 4번이 이 문제의 본질임.
> 1·2번은 흔한 동시성 문제지만, 3·4번은 **"무엇을 공유 단위로 볼 것인가"라는 설계 판단**이었음.

## 2. 설계의 뼈대 — 수명이 다른 것을 같은 저장소에 두지 않는다

### 이 슬라이드에서 제일 강조할 표

각 축의 **수명이 달라서** 저장소를 넷으로 나눴음. 하나로 합쳤으면 전부 깨졌음.

| 축 | 저장소 | 수명 | 공유 범위 | 왜 여기인가 |
|---|---|---|---|---|
| **세션 + 티켓** | `localStorage` | **25초** | **탭 전체 공유** | 신원은 사용자 단위라 탭이 공유해야 함 |
| **대화방(threadId)** | `sessionStorage` | 탭 | **탭별 독립** | 탭마다 다른 대화를 해야 함 |
| **대화 내용** | `sessionStorage` | 탭 | 탭별 독립 | 서버 맥락 TTL(10분)과 수명을 맞춤 |
| **화면 상태** | Zustand(메모리) | 마운트 | 없음 | 새로고침에 남을 이유가 없음 |

**근거(코드 확인)**
- 세션 캐시 25초 — [sessionCoordinator.ts:43](src/shared/chat/sessionCoordinator.ts#L43) `TICKET_TTL_MS = 25_000`
- 방 id는 sessionStorage — [threadId.ts:8-13](src/shared/chat/threadId.ts#L8-L13)
- 대화는 sessionStorage — [chatPersistence.ts:8-16](src/shared/chat/chatPersistence.ts#L8-L16)

### 25초라는 숫자의 근거 (물어보면 답할 것)

티켓 TTL이 **30~60초**인데 캐시는 **25초**로 더 짧게 잡음.
→ **만료 직전 티켓을 재사용하지 않게** 하려는 것.
스트림 401 재발급 경로가 따로 있어서 보수적으로 잡아도 손해가 없음.

### 대화를 "탭 단위"로 잡은 이유 — 이게 판단이다

> localStorage(영구)로 두면 안 됐나? → **안 됨.**

- 서버 맥락 TTL이 **10분 sliding**
- 대화를 그보다 오래 남기면 **"화면엔 대화가 있는데 AI는 기억 못 하는"** 어긋난 상태가 길어짐
- **탭 수명이 세션 수명과 대체로 겹쳐서 그 간극이 가장 작음**
- 부수 효과로 좋았던 것: 새로고침·탭 복구(`Ctrl+Shift+T`)에는 대화가 **살아남음**

**PPT 문구**: *"저장소는 편한 곳이 아니라 **수명이 같은 곳**에 둔다"*

## 3. 멀티탭 — 중복 발급을 어떻게 막았나

### 락을 쓰되, 범위를 좁혔다

```
navigator.locks.request(발급 구간만)
  └ 락 진입 후 캐시를 "다시" 확인   ← 이게 핵심
      └ 있으면 그대로 반환 (다른 탭이 이미 발급함)
      └ 없으면 발급 → publish(캐시 + 브로드캐스트)
```

**락 진입 후 재확인이 핵심인 이유** — [sessionCoordinator.ts:201-203](src/shared/chat/sessionCoordinator.ts#L201-L203)

이게 없으면 탭 N개가 **순서대로 락에 들어와 각자 발급**함. 락을 쓴 의미가 사라짐.
"기다렸다가 들어왔으니 내 차례에 만들면 된다"가 아니라, **기다리는 동안 상황이 바뀌었는지 봐야 함.**

### 의도적으로 락을 안 건 곳

| 구간 | 락 | 이유 |
|---|---|---|
| 세션 발급·재발급 | **건다** | 중복 발급을 막아야 함 |
| **SSE 스트림 전체** | **안 건다** | 스트림은 길다. 감싸면 **그동안 다른 탭의 발급이 전부 막힘** |

**PPT 문구**: *"락은 짧게 — 오래 걸리는 걸 감싸면 락이 병목이 된다"*

### Web Locks가 없는 브라우저 (degrade)

- `navigator.locks` 미지원이면 **300ms 대기 후 캐시 재확인**으로 저하 — [sessionCoordinator.ts:162-169](src/shared/chat/sessionCoordinator.ts#L162-L169)
- 엄밀한 상호배제는 아니지만 **최악이 "중복 발급 1회"**라 손해가 작다고 판단
- 같은 태도가 저장소 접근에도 있음 — private mode에서 `localStorage`가 던지면 **조용히 흡수**.
  캐시는 최적화일 뿐이고 정확성은 락+브로드캐스트가 책임짐 ([:78-97](src/shared/chat/sessionCoordinator.ts#L78-L97))

## 4. 게스트 → 회원 — 이 발표의 핵심

### 4-1. 전제: 게스트도 채팅을 쓸 수 있게 했다

- 게스트 허용 범위: **탐색 · 챗봇 · 장바구니 담기** (구매·찜·마이페이지만 로그인 필요)
- 이유: **로그인을 먼저 요구하면 이탈**함. AI 채팅은 이 서비스의 검색이라 게스트에게 막으면 서비스를 못 보여줌
- 게스트 식별은 **`guest_id` 쿠키** — [sessions.ts:26](src/shared/chat/sessions.ts#L26)

### 4-2. 그래서 생긴 문제 — 로그인하면 대화가 끊긴다

```
게스트로 대화 5턴  →  로그인  →  ???
```

- 서버 입장에서 게스트와 회원은 **다른 신원**
- 아무것도 안 하면 로그인 후 **새 세션**이 생기고, AI는 방금 한 대화를 모름
- 사용자 입장: *"로그인했더니 AI가 갑자기 바보가 됐다"*

### 4-3. 해결 — CH-7 승계 (sessionId는 유지, 주인만 교체)

```
POST /api/chat/sessions/{sessionId}/claim
  → sessionId 그대로, 회원 신원의 새 티켓이 실려 옴
  → 대화 맥락이 끊기지 않음
```

**FE가 판단한 것 두 가지**

**① 언제 부를 것인가 — "채팅 화면에서 로그인했을 때만"**

- 서버는 "어디서 로그인했는지" 추측하지 않음. **FE가 이 API를 부르는 것으로 의도를 표현**함
- 판단 근거: *상세페이지나 장바구니에서 로그인한 사람이 20분 전 다른 탭의 게스트 대화를 붙여달라고 했을 리는 없다*
- 근거: [claimOnLogin.ts:8-21](src/shared/chat/claimOnLogin.ts#L8-L21)

**② 실패해도 로그인은 성공한 상태다 — 그래서 던지지 않는다**

- 장바구니 병합·귀속·쿠키 반납은 **로그인이 이미 끝낸** 상태
- 승계 실패는 **대화 맥락만** 못 잇는 것 → 로그인 흐름을 되돌리지 않음

### 4-4. 여기서 제일 고민한 것 — 실패했을 때 조용히 넘어갈 것인가

> **이 항목이 발표의 하이라이트.** 기술이 아니라 **판단**을 보여주는 지점.

**처음 구현(잘못된 것)**

```
승계 실패 → sessionId만 null로 비움 → 다음 전송에서 조용히 새 세션 생성
```

- 결과: **화면엔 로그인 전 대화가 그대로 남았는데 AI는 그 맥락을 모름**
- 사용자는 **이유를 알 수 없음**. 에러도 안 뜸

**고친 것 — 발급 자체를 막고 사용자에게 묻는다**

`SessionClaimPendingError`를 던져 다음 세션 발급을 **차단**하고, 3지선다 배너를 띄움
([sessionCoordinator.ts:29-34](src/shared/chat/sessionCoordinator.ts#L29-L34) · [:205](src/shared/chat/sessionCoordinator.ts#L205))

| 선택지 | 동작 |
|---|---|
| **다시 시도** | 승계 재시도 — 성공하면 맥락까지 되살아남 (유일한 복구 수단) |
| **기억 없이 계속** | 대화는 남기고 맥락만 포기 |
| **지우고 새로 시작** | 대화까지 비움 |

**설계 원칙 한 줄** — [ClaimFailureBanner.tsx:24-25](src/shared/chat/ClaimFailureBanner.tsx#L24-L25)

> **"내가 막으려던 건 '조용히' 맥락이 끊기는 것이지, 사용자의 선택이 아니다."**
> 알고 고른다면 맥락 없이 계속하는 것도 정당한 선택이라 길을 열어둠.

**말풍선은 지우지 않는다** — [claimOnLogin.ts:42-43](src/shared/chat/claimOnLogin.ts#L42-L43)
서버 맥락이 끊겨도 사용자가 하던 얘기는 보여야 **"로그인했더니 대화가 사라졌다"**가 안 됨.

### 4-5. 놓쳤다가 잡은 것 — 에러 종류로 거르면 안 된다

[claimOnLogin.ts:49-51](src/shared/chat/claimOnLogin.ts#L49-L51)

- 처음엔 `ApiError`(서버가 코드로 거절)만 잡았음
- 그런데 **네트워크 단절·타임아웃처럼 응답 자체가 없는 실패**도 "승계 못 함"은 똑같음
- 좁게 잡으면 그 경우 **배너 없이 조용히 넘어감** ← 없애려던 바로 그 문제가 되살아남
- **주석에 "실제로 그렇게 새던 것을 잡았다"고 기록해 둠**

**PPT 문구**: *"예외를 좁게 잡으면, 없애려던 문제가 다른 문으로 돌아온다"*

### 4-6. 새로고침에도 살아남게

승계 실패 상태를 **스토어(메모리)에만** 두면, 로그인 직후 `/chat`으로 이동하는 사이
새로고침이 끼면 배너와 재시도가 사라짐 → `claimFailedSessionId`를 **저장소에도** 남김
([chatPersistence.ts:27-33](src/shared/chat/chatPersistence.ts#L27-L33))

`sessionId`와 **따로 둔 이유**: 승계 실패 시 `sessionId`는 비워야 하지만
(구 게스트 티켓으로 스트림을 열면 AI가 403으로 막음) 재시도하려면 그 값을 알아야 함.

## 5. 두 축이 만나는 지점 — 다른 탭에서 로그인하면?

> **여기가 "게스트/회원"과 "멀티탭"이 교차하는 곳.** 발표에서 두 이야기를 잇는 다리로 쓸 것.

### 문제

```
탭 A: 게스트로 대화 중
탭 B: 로그인       ← 이 순간 탭 A가 든 게스트 티켓이 무효가 된다
탭 A: 메시지 전송  → AI가 403으로 막음
```

- 기존엔 그 티켓으로 **스트림을 연 뒤에야** 실패를 알았고,
  안내도 *"새로고침 후 다시 시도해 주세요"*라는 막연한 문구였음

### 해결 — 방송을 2종으로 나눴다

[sessionCoordinator.ts:54-66](src/shared/chat/sessionCoordinator.ts#L54-L66)

| 방송 | 의미 | 받는 탭의 행동 |
|---|---|---|
| `session` | 티켓이 갱신됐다 | 표시용 sessionId만 맞춤 |
| `ownership` | **주인이 게스트→회원으로 바뀌었다** | 자기가 든 구 게스트 티켓을 버림 |

**왜 하나로 안 되나** (문서에 명시해 둔 이유)

> 하나로만 알리면 받는 쪽이 **"새 티켓이 왔다"와 "내 자격이 무효가 됐다"를 구분할 수 없음.**
> 그러면 방송 도착 전에 시작된 전송이 구 게스트 티켓으로 나가 **403**을 맞음.

### 순서를 고정한 것 — 이것도 판단이다

[sessionCoordinator.ts:276-284](src/shared/chat/sessionCoordinator.ts#L276-L284)

```
publish(회원 티켓)  →  ownership 방송
    ↑ 반드시 이 순서
```

반대면 받는 탭이 **방금 심긴 유효한 회원 티켓까지 지워서** 재발급이 한 번 더 남.
받는 쪽도 방어함 — 캐시에 든 세션이 **승계된 그 세션이면 이미 회원 티켓이므로 그대로 둠**
([:142-153](src/shared/chat/sessionCoordinator.ts#L142-L153))

### 전송을 막지는 않았다

- `ownership`을 받아도 **전송 자체는 막지 않음**. 캐시만 비워서 다음 전송이 회원 신원으로 재발급받게 함
- 이유: 실제로 깨지는 건 방송 도착 전 **수십 ms**뿐인데, 막으면 **멀쩡히 이어질 대화까지 끊김**
- 코드 주석에도 *"실패하지도 않은 흐름을 끊지 않는다"*로 남김 ([:136](src/shared/chat/sessionCoordinator.ts#L136))

**PPT 문구**: *"완벽한 정합성이 아니라 **사용자가 이유를 알 수 있는 상태**를 목표로 했다"*

## 7. 배운 점 · 한계 (정직하게 말할 부분)

### 배운 것

1. **멀티탭은 UI 문제가 아니라 분산 문제였다.**
   공유 메모리가 없는 여러 클라이언트가 하나의 서버 자원을 공유하는 구조 — 서버 쪽 동시성 문제와 형태가 같음
2. **저장소 선택은 "어디가 편한가"가 아니라 "수명이 같은가"였다.**
   세션·방·대화·화면 상태의 수명이 전부 달라서 넷으로 나뉨
3. **조용한 실패가 시끄러운 실패보다 나쁘다.**
   에러 화면보다 *"화면엔 대화가 있는데 AI는 기억 못 하는"* 상태가 훨씬 나쁨

### 한계 (물어보면 이렇게)

- **Web Locks 브라우저 지원 범위를 조사한 기록이 없음** — degrade 경로는 만들어뒀지만
  실제로 어떤 브라우저가 degrade를 타는지는 확인 안 함
- **멀티탭 시나리오의 자동화 테스트는 없음** — 단위 테스트는 있지만
  실제 탭 2개를 띄우는 통합 검증은 **수동**임
- 티켓 TTL 30~60초 대비 캐시 25초 — **이 값이 계약 기재인지 FE 판단인지 재확인 필요**

### 다시 한다면

> **실패 UX를 기능과 동시에 설계했을 것.**
> 승계 기능(`59dd145`)을 먼저 만들고 실패 배너(`b6ffc48`)를 나중에 붙였는데,
> 커밋이 셋으로 나뉜 게 그 증거임. **"성공 경로만 먼저 만들면 실패 경로가 나중에 땜질이 된다."**

## 8. 발표 멘트 (통합본, 약 3분)

"채팅 세션 설계 이야기를 하겠습니다. 이게 프론트엔드 작업 중에 제일 오래 붙잡았던 부분입니다.

시작은 단순한 버그 제보였습니다. 탭을 두 개 열고 채팅하면 세션이 서로를 밀어냅니다. 처음엔 간단한 문제인 줄 알았는데, 파고들수록 이건 **브라우저 탭들 사이에 공유 메모리가 없는 분산 문제**더라고요. 서버 쪽 동시성 문제랑 형태가 같았습니다.

여기서 제일 중요했던 판단은 **'세션'과 '대화방'의 수명이 다르다는 걸 인정한 것**입니다. 로그인 자격은 탭끼리 공유해야 하지만, 대화 내용은 탭마다 따로여야 하잖아요. 그래서 저장소를 넷으로 나눴습니다. 세션은 로컬스토리지에 25초, 대화방과 대화 내용은 탭 단위 세션스토리지에, 화면 상태는 메모리에요. 대화를 탭 단위로 잡은 건 서버가 대화 맥락을 10분만 기억하기 때문입니다. 그보다 오래 남기면 화면엔 대화가 있는데 AI는 기억 못 하는 어긋난 상태가 길어집니다.

그런데 여기에 문제가 하나 더 겹쳤습니다. **저희는 게스트도 채팅을 쓸 수 있게 했거든요.** 로그인부터 요구하면 사람들이 나가버리니까요. 대신 게스트가 대화하다가 로그인하면, 서버 입장에선 신원이 바뀌어서 그동안 한 대화를 잃어버립니다. 로그인했더니 AI가 갑자기 바보가 되는 거죠. 그래서 승계 API를 붙여서, 세션 아이디는 그대로 두고 주인만 회원으로 바꾸게 했습니다.

**제일 고민한 건 이 승계가 실패했을 때였습니다.** 처음엔 그냥 조용히 새 세션을 만들었어요. 그랬더니 화면엔 로그인 전 대화가 남아 있는데 AI는 그걸 모르는 상태가 됐습니다. 에러도 안 뜨고 사용자는 이유를 알 수가 없었죠. 그래서 아예 세션 발급을 막고 배너로 물어보게 바꿨습니다. 다시 시도할지, 기억 없이 계속할지, 지우고 새로 시작할지요. 제가 막으려던 건 **'조용히' 맥락이 끊기는 것**이지 사용자의 선택이 아니라고 판단했습니다.

여기서 하나 놓쳤다가 잡은 게 있는데, 처음엔 서버가 코드로 거절한 경우만 실패로 잡았습니다. 그런데 네트워크가 끊기거나 타임아웃 나는 것도 승계 못 하는 건 똑같잖아요. 좁게 잡았더니 그 경우엔 배너가 안 떴습니다. 없애려던 조용한 실패가 다른 문으로 돌아온 거죠.

마지막으로, 두 문제가 만나는 지점이 있었습니다. **한 탭에서 로그인하면 다른 탭이 들고 있던 게스트 자격이 그 순간 무효가 됩니다.** 원래는 그걸 모르고 있다가 메시지를 보낸 뒤에야 403을 맞았어요. 그래서 브라우저의 탭 간 방송 기능을 썼는데, 여기서도 판단이 하나 필요했습니다. 방송을 한 종류로만 보내면 받는 탭이 '새 자격증이 왔다'랑 '내 자격증이 무효다'를 구분할 수가 없더라고요. 그래서 두 종류로 나눴습니다.

정리하면, 이 작업에서 배운 건 **조용한 실패가 시끄러운 실패보다 나쁘다**는 거였습니다. 에러 화면이 뜨는 것보다, 화면엔 대화가 멀쩡히 있는데 AI만 기억을 못 하는 상태가 훨씬 나쁩니다. 사용자가 뭘 잘못했는지도 모르니까요."

## 9. 시각 자료 (우선순위 순)

1. ⭐ **저장소 4계층 도식** — 이 발표의 뼈대. 탭 2개를 그리고 공유되는 것(localStorage)과
   탭별로 나뉘는 것(sessionStorage)을 색으로 구분 — **가장 먼저 만들 것**
2. ⭐ **탭 2개 시나리오 화면 녹화** — 개선 전(한쪽 로그인 → 다른 탭 403) / 개선 후(sessionId 유지, 방은 분리)
3. **승계 실패 배너 캡처** — 3지선다 버튼이 보이게
4. **게스트→회원 승계 흐름도** — 게스트 대화 5턴 → 로그인 → sessionId 유지, 티켓만 교체
5. 방송 2종 도식 (`session` vs `ownership`)

## 10. 예상 질문 대비

| 질문 | 답변 |
|---|---|
| **"서버에서 처리하면 안 되나요?"** | 세션 발급 자체는 서버가 멱등으로 처리해줍니다(같은 신원이면 같은 sessionId). 프론트가 푼 건 **호출 횟수와 탭별 방 구분**입니다. 서버는 탭을 구분할 수 없으니까요 |
| **"Web Locks 지원 안 되면요?"** | 300ms 대기 후 캐시를 재확인하는 방식으로 저하됩니다. 최악이 중복 발급 1회라 손해가 작다고 봤습니다. **다만 어떤 브라우저가 이 경로를 타는지는 조사 못 했습니다** |
| **"왜 25초인가요?"** | 티켓 TTL이 30~60초라 만료 직전 걸 재사용하지 않으려고 더 짧게 잡았습니다. 401 재발급 경로가 따로 있어서 보수적으로 잡아도 손해가 없습니다 |
| **"승계 실패가 자주 나나요?"** | **빈도는 측정 안 했습니다.** 다만 실패 종류가 5가지(403·404·409 2종·503)라 처방을 나눠야 했습니다 |
| **"테스트는 어떻게 했나요?"** | 단위 테스트 85개가 통과합니다. **다만 실제 탭 2개를 띄우는 통합 검증은 수동입니다** |
| **"BroadcastChannel 대신 storage 이벤트는요?"** | 검토했지만 BroadcastChannel이 의도가 명확합니다. storage 이벤트는 값 변경의 부수효과라 "무엇을 알리는지"가 코드에 안 드러납니다 |
