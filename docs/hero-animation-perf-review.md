# 홈 히어로 애니메이션 — 성능 점검

> 홈 히어로에 그라데이션 애니메이션을 넣은 뒤(`1cb4970`) 성능 부담을 확인한 기록.
> **결론: 코드 수정 없음.** CPU 4x slowdown 조건에서 60fps 유지를 확인했다.
> 점검일 2026-08-07.
>
> 코드만 읽고 세운 가설(글로우가 매 프레임 리페인트될 것)이 측정으로 반증됐다.
> 브라우저가 이미 레이어로 승격해 두고 있었다.

## 왜 봤나

히어로에 무한 반복 애니메이션 3개를 한꺼번에 넣었다 — 워드마크 그라데이션,
검색바 테두리 그라데이션, 배경 글로우. 전부 `infinite`라 페이지가 떠 있는 동안
계속 돈다. 홈은 첫 진입 화면이고 저사양 모바일 비중이 큰 자리라,
"보기에 괜찮다"와 별개로 프레임을 갉아먹는지 확인이 필요했다.

## 점검 대상

| 대상 | 위치 | 성격 |
|---|---|---|
| `animate-narvis-flow` | 워드마크(`Hero.tsx:70`) | `background-position` 7s linear infinite |
| `animate-narvis-flow` | 검색바 테두리(`Hero.tsx:78`) | 위와 같은 애니메이션 공유 |
| `animate-narvis-pulse` | 배경 글로우(`Hero.tsx:54`) | `opacity` 9s infinite + `blur-[60px]` |
| 배경 격자 | `Hero.tsx:49` | 애니메이션 없음(정적) |
| 예시 칩 | `Hero.tsx:113` | `backdrop-blur-sm`, 애니메이션 없음 |

## 세웠던 가설

**글로우가 가장 위험하다고 봤다.**

- 요소가 `900×420px`(모바일 `max-w-[140vw]`)에 `blur-[60px]`
- 블러는 페인트 단계라, 블러 반경만큼 확장된 영역을 실제로 래스터화해야 한다
- 거기에 `opacity`를 9초 주기로 무한 애니메이션한다
- opacity 자체는 합성 단계 속성이라 보통 공짜지만, **블러 결과가 레이어로 캐시되지 않으면
  매 프레임 60px 블러를 다시 그린다**

그래서 `will-change: opacity`로 레이어 승격을 강제하자고 제안했다.
반대로 `narvis-flow`는 리페인트 면적이 작아(한 단어 + 2px 링) 무해할 것으로 봤다.

## 측정 방법

- Chrome DevTools, 프로덕션 빌드(`npm run start`, localhost:3000)
- **CPU: 4x slowdown** — 저사양 모바일 재현
- 유휴 상태 10.53초 녹화 (스크롤·마우스 조작 없음)
- Rendering 패널의 Paint flashing / Layer borders 병행 확인

## 결과

### 글로우 — 가설이 틀렸다

| 확인 항목 | 결과 | 의미 |
|---|---|---|
| Paint flashing | 타원 **안 깜빡임** | opacity 변화가 리페인트를 유발하지 않음 |
| Layer borders | 주황 테두리 **그려짐** | 이미 별도 합성 레이어로 승격됨 |

블러가 걸린 요소라 브라우저가 알아서 레이어로 올려뒀고, opacity는 합성 단계에서만 처리된다.
**`will-change`는 불필요하다** — 이미 되어 있는 것을 중복 지시하면서 레이어 메모리만 더 쓴다.

> **교훈**: "블러 + opacity 애니메이션 = 매 프레임 리페인트"는 코드만 보면 그럴듯하지만,
> 브라우저의 자동 레이어 승격을 계산에 넣지 않은 추론이었다.
> `will-change`는 측정으로 리페인트를 확인한 뒤에 넣는 것이지, 예방적으로 넣는 게 아니다.

### 프레임 — 4x에서도 60fps 유지

- Frames 트랙이 2,850.8ms 구간 내내 **초록으로 균일**, 빨간 띠(장시간 프레임) 없음
- 저사양 모바일을 4배로 재현한 조건에서도 프레임 드랍이 없다

### Main thread 내역 (10.53초, CPU 4x)

| 항목 | 시간 | 비중 |
|---|---|---|
| Painting | 2,022 ms | ~19% |
| System | 968 ms | ~9% |
| Rendering | 803 ms | ~8% |
| Scripting | 640 ms | ~6% |
| Total | 10,529 ms | |

**Painting 19%는 스로틀링 수치라는 점을 감안해서 읽어야 한다.** 4x slowdown은 CPU 작업
시간을 통째로 4배 늘리므로 실측 환산 약 500ms, 10.5초 중 5% 수준이다.
여기에 React Developer Tools 확장(118.2ms)의 노이즈도 섞여 있다.

Painting을 쓰는 주체는 `narvis-flow` 쪽으로 보인다 — `background-position`은 합성이 안 되는
속성이라 매 프레임 리페인트가 필요하고, 이게 워드마크와 검색바 테두리 2곳에서 계속 돈다.
다만 리페인트 면적이 작아 프레임 예산 안에서 소화되고 있다.

### 애니메이션 없는 요소들

- **배경 격자** — `linear-gradient` 2장 + `mask-image`지만 한 번 그리고 끝. 정적 비용
- **칩 `backdrop-blur-sm`** — 5개 소형 요소, 애니메이션 없음.
  `backdrop-filter`는 뒤 레이어를 읽어야 해서 스크롤 시 비용이 있으나,
  칩이 글로우 영역 아래쪽 가장자리라 겹침이 적어 측정에 잡히지 않았다

## 조치

**없다.** 커밋 `1cb4970` 그대로 유지한다.

제안했던 `will-change-[opacity]`는 측정 결과 불필요한 것으로 확인돼 넣지 않았다.

## 측정의 한계

부풀려 읽지 않기 위해 적어둔다.

- **데스크탑 CPU 4x 스로틀링이지 실기기가 아니다.** 스로틀링은 CPU만 늦출 뿐
  GPU·화면 밀도·메모리 대역폭은 재현하지 못한다. 블러 비용은 특히 GPU에 좌우된다
- **확장 프로그램이 켜진 창에서 쟀다.** React Developer Tools가 118.2ms 잡혔다.
  정확히 하려면 시크릿 창에서 재는 게 맞다
- **유휴 상태만 쟀다.** 스크롤 중에는 칩의 `backdrop-blur`가 글로우 위를 지나며
  backdrop 재계산이 붙을 수 있는데, 이 시나리오는 측정하지 않았다
- 여유가 충분해 보여 실기기 검증까지는 가지 않기로 했다
