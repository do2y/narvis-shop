# 챗봇 아키텍처 — 스트림·세션·카드가 각각 다른 경로로 오는 이유

> 챗봇(구매자 SHOPPING / 판매자 SELLER)이 실제로 어떻게 동작하는지의 지도.
> 개별 사건 기록(`analytics-401-retry.md` 등)과 달리 **평상시 구조**를 적는다.
> 코드 주석에 흩어진 판단을 한자리에 모은 것이라, 구현과 어긋나면 코드가 정본이다.
>
> 구현: `src/shared/chat/*` · 계약 타입: `src/shared/types/chat.ts` ·
> 판매자 계약 원문: `FE-CONTRACT-SELLER-CHAT.md`

## 0. 한 줄 요약

**한 번의 대화 턴에 세 개의 다른 통신 경로가 관여한다.**

| 무엇 | 경로 | 왜 분리됐나 |
|---|---|---|
| 세션·티켓 발급 | BE(Spring) `POST /api/chat/sessions` | 신원 판정은 BE 몫 (JWT→brandId 도출) |
| 대화 스트림 | **AI 서버 직결** SSE (`llmSseUrl`) | nginx·Next 를 타지 않는다 |
| 상품 카드 | BE `GET /api/chat/lists/{listId}` | SSE 에 카드를 싣지 않는다(경로 B) |

이 셋을 하나로 착각하는 게 이 모듈에서 가장 흔한 오해다.
"채팅이 안 돼요"의 원인이 셋 중 어디인지부터 갈라야 한다.

---

## 1. 왜 SSE 가 인프라를 우회하나

배포 구조상 `/api/**` 는 nginx 가 Spring 으로 보낸다. 그런데 **채팅 스트림만은
그 경로를 타지 않는다.**

세션 발급 응답이 `llmSseUrl`(AI 서버 절대 URL)을 주고, `streamChat` 이 거기로
직접 `fetch` 한다. FE 는 URL 을 조립하지 않는다 — BE 설정값을 그대로 쓴다.

```ts
// streamChat.ts — URL 도 세션 발급 응답의 llmSseUrl 을 그대로 쓴다(BE 설정값)
export async function streamChat(sseUrl, ticket, body, onEvent, signal)
```

**따라오는 제약 2가지:**

1. **AI 서버가 이 앱 오리진에 CORS 를 열어줘야 한다.** 프론트 배포 도메인이
   바뀌면 AI 서버 설정도 같이 바뀌어야 한다 — nginx 를 고쳐도 소용없다.
2. **EventSource 를 못 쓴다.** POST + JSON body 라서. `fetch` 스트리밍으로
   직접 파싱한다.

### 와이어 포맷 — `event:` 줄이 없다

```
data: {"type":"token","data":{"text":"..."}}
```

한 줄 envelope 다. **이벤트 이름이 아니라 `payload.type` 으로 분기한다.**
`event:` 라인을 기대하는 코드를 쓰면 아무것도 안 잡힌다.

파서는 `\n\n` 로 청크를 끊고, 미완성 조각은 버퍼에 보류한다 —
SSE 는 청크 경계가 이벤트 경계와 일치한다는 보장이 없다.

## 2. 인증 — 로그인 토큰이 SSE 로 가지 않는다

AI 서버에 로그인 AT 를 보내지 않는다. 대신 **단명 `streamTicket`** 을 싣는다.

```
로그인 AT ──(BE 세션 발급)──> streamTicket ──(SSE Authorization: Bearer)──> AI 서버
```

**왜 2단계인가 (IDOR 방지):**

신원(`userId`·`sellerId`·`brandId`)과 `channel` 은 **SSE body 에 없다.**
세션 발급 단계에서 서버가 JWT→DB 로 도출해 **티켓 claim 에 박는다.**

> 셀러: `brandId` 는 클라이언트 주장이 아니라 서버가 JWT→DB 로 도출해 티켓 claim 에 박음
> — `types/chat.ts`

즉 FE 가 body 에 `brandId` 를 실어 남의 브랜드 데이터를 요청하는 게 **구조적으로
불가능**하다. SSE body 는 순수 대화 필드만 싣는다.

**티켓 TTL 은 30~60초.** 캐시 유효기간은 그보다 짧은 25초로 잡았다
(`TICKET_TTL_MS`) — 만료 직전 티켓을 재사용하지 않으려고.

## 3. 세션 조정(sessionCoordinator) — 멀티탭이 서로를 안 죽이게

`ensureSession()` 이 CH-1/CH-6 의 **유일한 호출 지점**이다.

### 락의 목적은 축출 방지가 아니라 중복 억제

> CH-1 은 멱등 발급이라 같은 신원·채널이면 서버가 같은 sessionId 를 돌려준다
> (멀티탭이 서로를 축출하지 않는다). 그래서 이 모듈의 목적은 축출 방지가 아니라
> **중복 호출 억제**다.

락은 `navigator.locks` 를 쓰고, 없으면 300ms 대기 후 캐시 재확인으로 저하한다.

**두 번 확인하는 게 핵심이다** (thundering herd):

```ts
const cached = readCache(channel);
if (cached) return cached;
return withLock(key, async () => {
  const again = readCache(channel);   // ← 락 안에서 재확인
  if (again) return again;            //   대기 중 다른 탭이 발급했을 수 있다
  ...
});
```

이게 없으면 탭 N 개가 순서대로 락에 들어와 각자 발급한다 — 락을 쓴 의미가 없다.

**락은 발급/재발급만 감싼다.** 장시간 SSE 스트림까지 감싸면 그동안 다른 탭의
발급이 막힌다.

### 탭 간 방송이 2종인 이유

`BroadcastChannel("jarvis:chat")` 으로 두 가지를 나눠 보낸다.

| 메시지 | 뜻 | 받는 탭의 조치 |
|---|---|---|
| `session` | 티켓이 갱신됐다 | 표시용 sessionId 만 맞춘다 |
| `ownership` | 세션 주인이 게스트→회원으로 바뀌었다 | 남은 구 게스트 티켓을 버린다 |

> 둘을 나누는 이유: 받는 쪽이 "티켓이 새로 왔다"와 "내 자격이 무효가 됐다"를
> 구분할 수 있어야 한다. session 하나로만 알리면 후자를 판단할 수 없어,
> 방송 도착 전에 시작된 전송이 구 게스트 티켓으로 나가 AI 에서 403 을 맞는다.

그리고 `claimSession` 은 **publish 를 먼저, ownership 방송을 나중에** 한다 —
순서가 바뀌면 방금 심은 유효한 회원 티켓을 받는 탭이 지워버린다.

## 4. 경로 B — 카드는 SSE 에 없다

**가장 자주 오해받는 지점.** SSE 는 카드 데이터를 나르지 않는다.
`products.ready` 로 **상관키만** 오고, FE 가 CH-5 로 목록을 따로 조회한다.

```
token…token → products.ready{listIds} → (FE가 GET /api/chat/lists/{id} × N) → done
```

- 구버전 `products` 이벤트(카드를 SSE 에 직접 싣던 **경로 A**)는 계약에서 폐기됐다.
- 계약은 `listIds`(배열)지만 **AI 가 아직 단수 `listId` 를 보낸다** — 둘 다 받는
  코드가 있고, 전환되면 `listId` 를 지운다.

**조회한 카드는 완전한 데이터다**(BE 가 상품명·가격·정가·이미지·rating 을 최신값으로
부착, HIDDEN·품절은 드롭). 그래서 상세 캐시 시딩용으로 쓰고,
**카드를 표시하려고 다시 조회하지 않는다.**

### 실패 시 패널을 건드리지 않는다

`listId` TTL 은 세션 TTL 과 같은 10분. 만료되면 404 다.

> 하나도 못 가져왔으면 패널을 건드리지 않는다 — 이전 턴의 카드가 그대로 남는다.
> 명세가 "오류 화면을 띄우지 말고 가지고 있던 카드를 그대로 보여주라"고 한 지점이다.
> 답변 자체는 정상 종료됐으므로 말풍선에도 실패로 표시하지 않는다.

TTL 만료는 재시도해도 계속 404 라 **"다시 시도"를 권하지 않는다.**

카드가 0개여도 `itemsDropped > 0` 이면 결과에 넣는다 —
"추천이 다 품절됐다"는 사실 자체가 안내거리라서.

## 5. SSE 이벤트 11종

`payload.type` 으로 분기. **CLAUDE.md 는 8+2 로 적고 있으나 실제로는 `report` 를
포함해 11종이다**(§9 참조).

### 공통 (3)

| type | 페이로드 | 비고 |
|---|---|---|
| `token` | `{text}` | append |
| `done` | `{finishReason, panel?}` | 구매자 `stop`·`zero_result` / 판매자 `panel` |
| `error` | `{code, message, requestId?, retryable?}` | **종결 이벤트** |

`error.retryable` 을 code 로 복원할 수 없는 이유:

> 같은 LLM_UNAVAILABLE 이라도 "미구성"(재시도 무의미)과 "일시 불가"(유효)가
> 섞이므로 emit 지점이 값을 정한다. 생략되면 재시도 가능으로 본다(구버전 호환).

`requestId` 는 사용자가 "오류 났어요"라고 신고했을 때 서버 로그에서 그 요청을
찾는 **유일한 키**다.

### 구매자 전용 (4)

| type | 페이로드 |
|---|---|
| `conditions` | `{chips}` — 제거 가능한 조건 칩 |
| `suggestions` | `{chips}` — 완화/되돌리기 제안 |
| `products.ready` | `{listIds?, listId?}` — 상관키(§4) |
| `action` | `ChatAction` (10종, §6) |

### 판매자 전용 (3)

| type | 페이로드 | 비고 |
|---|---|---|
| `meta` | `{lane}` | 첫 프레임 — 레이아웃·로딩 준비 신호 |
| `draft` | `SellerDraft` | 수정/삭제/등록 제안(HITL 승인 대기) |
| `report` | `SellerReport` | 분석 리포트, 정확히 1회 |

### `progress` — 채널마다 페이로드가 다르다 (1)

| 채널 | 페이로드 |
|---|---|
| 구매자 | `{stage, message?}` — 기계 판독 가능한 enum |
| 판매자 | `{text}` — 자유 문자열 |

**수신부가 반드시 분기해야 한다.** 쉐이프를 맞추는 건 후속 과제로 남아 있다.

**stage 어휘는 개방형이다.** 계약이 "FE 는 모르는 stage 를 무시한다"를 명문화해서
닫힌 유니온으로 두지 않았다 — AI 가 stage 를 추가할 때 FE 배포를 기다리지 않게.
`KNOWN_BUYER_PROGRESS_STAGES` 는 **자체 문구를 가진 것들일 뿐 허용 집합이 아니다.**

알려진 stage 7종: `analyzing` `mapping` `expanding` `searching` `relaxing` `reranking` `publishing`.
서버가 `message` 를 비우면 FE 가 stage 로 자체 문구를 매핑한다(`BUYER_PROGRESS_LABEL`, 부분 맵).

**⚠️ progress 도착을 전제하지 말 것.** 0회인 턴이 있다 —
첫 프레임이 `error` 이거나 스트림이 안 열린 경우.

**⚠️ `token` 이 progress 를 지우면 안 된다.**

> `publishing` 은 근거 token 이 나간 **뒤** `products.ready` 직전에 온다. 여기서 지우면
> 7종 중 그 한 종이 **영영 화면에 닿지 못한다.** 정리는 `done`·finally 가 맡는다.

그래서 화면에 표시 상태가 3가지다: 답변 전(말풍선 없이 상태만) / 답변 후(말풍선 밖 얇은 줄) /
진행 없음. **진행 표시를 답변 렌더링에 종속시키면 안 된다.**

### `resolveProgressText()` 의 `null` 은 "지우기"가 아니다

> null 반환 = "표시할 것이 없다"가 아니라 **"이 프레임은 무시하라"** 다. 호출부는 null 일 때
> 기존 문구를 **유지**해야 한다 — 덮어서 지우면 직전 단계 문구까지 사라져 진행 표시가
> 도리어 후퇴한다.

## 6. action 10종 — "이미 그 상태"는 성공이다

장바구니 3종(담기·삭제·수량변경) + 찜 2종(추가·해제) 각 성공/실패 = 10종.

**판단 기준으로 기억할 것:**

> "이미 그 상태"인 경우는 실패가 아니라 **성공**으로 온다 — 사용자 목표 상태가 같기 때문이다.
> (404 CART_ITEM_NOT_FOUND → CART_REMOVED, 409 WISHLIST_DUPLICATE → WISHLIST_ADDED,
>  404 WISHLIST_NOT_FOUND → WISHLIST_REMOVED)

### 재조회 판정은 화면이 아니라 계약 옆에 둔다

`isCartMutatingAction()` / `isWishlistMutatingAction()` (`shared/types/chat`)로만 판정한다.

> 재조회 대상을 화면이 아니라 계약 옆에 두는 이유: action type 이 늘어날 때
> 갱신해야 할 곳이 여기 하나이길 바라서다(**2종 → 10종 확장에서 실제로 겪은 문제**).

성공 시 `['cart']`·`['wishlist']` 무효화.
**찜 이벤트엔 productId 가 없다**(경로 B) → 목록 재조회만 가능하다.

### message 는 파싱하지 않는다

`action.message` 는 AI 가 조립한 **사용자 노출 안전 문구**다.
그대로 붙이고 하드코딩·파싱하지 않는다. 분기는 `type`·`reason` 으로만.

### 자동 재시도 금지

중복 담기를 막기 위해서다. 실패 시 **재시도 버튼**을 제공한다.
예외는 딱 하나 — 스트림 401(티켓 만료)은 **스트림 시작 전**이라 재발급 후 1회
재시도가 안전하다.

## 6-1. 실패 분류 — 어디서 깨졌는지로 나뉜다

**스트림이 시작됐는지**가 1차 분기다.

| 분류 | 타입 | 언제 |
|---|---|---|
| 시작 전 거부 | `StreamStartError`(status, code) | HTTP 응답 자체가 실패 |
| 시작 후 오류 | SSE `error` 이벤트 | 토큰이 흐르던 중 |
| 세션 만료 | 404 / `SESSION_NOT_FOUND` | 두 경로 모두에서 올 수 있다 |
| 승계 미해결 | `SessionClaimPendingError` | §9 |

### 시작 전 거부 — 재시도 버튼을 줄지가 갈린다

| status | 뜻 | 재시도 |
|---|---|---|
| 401 | 티켓 만료 | 자동 재발급 후 1회(사용자에게 안 보임) |
| 403 | scope 불일치(판매자 티켓으로 구매자 스트림 등) | **없음** — 같은 티켓이면 결과가 같다 |
| 409 `STREAM_IN_PROGRESS` | 같은 방에 활성 스트림 | **없음** — 즉시 재시도는 또 409 |
| 429 `RATE_LIMITED` | 과다 요청 | **없음** — 누르면 상황이 더 나빠진다 |
| 504 `UPSTREAM_TIMEOUT` | first-token 지연 | **있음** — 일시적 |

> 재시도해도 같은 결과가 뻔한 실패에는 버튼을 주지 않는다 — 누를수록 상황이 나빠지거나 무의미하다.

### 404 는 "다른 곳에서 종료됨"이 아니라 단순 만료

CH-1 이 멱등이라 다른 탭이 세션을 축출하는 일이 없다. 캐시를 비우고 재시도 버튼만 준다
(자동 재전송하지 않는다 — 중복 담기 방지).

판정 함수가 타입 2개를 보는 이유: **출처가 둘**이다. 스트림 fetch 는 `StreamStartError`(status),
티켓 재발급은 `ApiError`(code/status).

### 재시도는 마지막 왕복을 걷어내고 다시 보낸다

`dropLastExchange()` 가 마지막 assistant + 직전 user 를 제거하고 user 텍스트를 반환한다.
마지막이 assistant 가 아니면 `null`(confirm 턴 등은 재시도 불가).

## 7. 조건 칩 — 규약 문자열 왕복은 폐기됐다

칩의 X 제거는 **`conditionActions` 배열**로 보낸다.

```ts
conditionActions: [{ op: "remove", field: "priceMax" }]
```

- 예전엔 `[조건 제거] …` 같은 **규약 문자열**을 발화에 실어 보냈다 → 폐기(2026-07-28, #84).
- 이유: **어떤 칩을 지웠는지는 UI 만 아는 사실**이라 서버가 발화만으로 복원할 수 없다.
- `op` 는 `remove` 만 허용. **멱등하다** — 없는 필드를 지워도 성공 no-op.
- `field` 허용값 6종. conditions 가 내보내는 집합 == conditionActions 가 지우는 집합.

### ⚠️ `field` 는 칩을 유일하게 가리키지 않는다

**이 모듈에서 가장 물리기 쉬운 함정.** v0.32.14 부터 category·brand 는 **값당 칩 1개**로
나뉘어 **같은 field 가 여러 개 온다.**

```
칩을 특정하려면 (field, value) 쌍이 필요하다.
```

- **제거**: `field` 만 보고 지우면 카테고리 칩 하나를 눌렀는데 **카테고리가 전부 사라진다.**
- **React key**: `` `${field}:${value}` `` 를 써야 한다. field 단독은 중복 키가 되고,
  > 중복 키는 React 경고에서 끝나지 않고 리컨실리에이션을 어긋나게 해, 하나를 지우면
  > **엉뚱한 칩이 사라져 보이고** 등장 애니메이션도 남은 칩에서 다시 돈다.

`value` 는 항상 스칼라다. v0.32.14 이전엔 brand 에만 리스트가 실려 선언과 어긋나 있었다.

### `value` 를 생략하면 축 전체가 지워진다

| field | `value` 를 줬을 때 |
|---|---|
| `category`·`brand` | 그 값만 빼고 나머지로 재검색 |
| `priceMax`·`priceMin`·`ratingMin`·`keyword` | **서버가 무시하고 축 전체 제거**(값이 하나뿐인 축) |

서버가 모르는 값은 관대 무시(400 아님). 같은 축에 value 없는 액션이 섞이면 **전체 제거가 이긴다.**

### 낙관적 제거 + 사용자 말풍선 없음

화면에서 먼저 지운다 — 서버 왕복을 기다리면 **누른 뒤에도 칩이 남아 안 눌린 것처럼 보인다.**
다음 턴의 `conditions` 이벤트가 전체를 덮어쓰므로 어긋난 채 남지 않는다.

칩 제거만 있는 턴은 **사용자 말풍선을 남기지 않는다** — 제어 신호이지 발화가 아니다
(판매자 confirm 과 같은 처리). analytics `search` 도 쏘지 않는다.

**`message` 와 `conditionActions` 가 둘 다 비면 400.** 하나만 있으면 정상이다.

### 제안 칩(suggestions)은 방식이 다르다

완화·되돌리기 칩은 `conditionActions` 가 아니라 **label 을 그대로 message 로** 보낸다 —
label 이 사용자 발화 형태("6만원대까지 볼까요?")라 그대로 실으면 LLM 이 완화를 트리거한다.
`estCount === 0` 은 서버가 제외하지만 FE 도 방어적으로 거른다.

## 8. 대화 저장 — 왜 탭 단위(sessionStorage)인가

```ts
const KEY = "chat:session";   // sessionStorage
```

**대화는 DB 에 저장되지 않는다.** 과거 대화 조회 기능이 없다.

> 저장 범위를 탭으로 잡은 이유: 서버 맥락 TTL 이 10분(sliding)이라 그보다 오래
> 남겨 두면 화면엔 대화가 있는데 AI 는 기억하지 못하는 어긋난 상태가 길어진다.
> **탭 수명이 세션 수명과 대체로 겹쳐 그 간극이 가장 작다.**

- 새로고침·탭 복구(Ctrl+Shift+T)로 살아남고, 탭을 닫으면 사라진다.
- **빈 대화는 저장하지 않는다** — 다른 탭이 시작한 대화를 덮어쓸 여지가 생긴다.
- **읽어도 지우지 않는다** — 새로고침이 반복돼도 계속 복원돼야 한다.
- 로그인 왕복(CH-7 승계)도 **같은 저장소**를 쓴다. 저장 주체가 둘이면 서로 덮어써
  대화가 유실된다.
- "새 대화"는 저장소도 함께 비운다.

### threadId — sessionId 가 탭 간 공유라서 필요하다

`threadId` 는 **필수다(없으면 400)**. 역할 분담이 명확하다:

| | 무엇 | 저장소 | 범위 |
|---|---|---|---|
| `sessionId` | 접속(서버 맥락) | 코디네이터 캐시 | **탭 간 공유** |
| `threadId` | 방(대화) | sessionStorage | **탭마다 고유** |

세션이 공유되므로 **방 구분은 threadId 가 맡는다** — 그래야 여러 탭이 각자 독립 대화를 한다.

**스토어에 두지 않는 이유:**

> `reset()`(새 대화)이 initial 을 통째로 뿌려서 방 id 를 지켜낼 수 없다.
> "새 대화"는 방을 새로 만드는 것이지 **방 개념을 잃는 게 아니다.**

### "새 대화" = 새 방, 세션은 유지

```ts
abort → newThreadId(channel) → clearChat() → reset() → setThreadId
```

**세션을 새로 발급하지 않는다** — 그러면 다른 탭의 세션을 축출해 멀티탭이 깨진다(CH-1 호출 없음).

순서도 의미가 있다: **저장소를 먼저 비운다.** `saveChat` 은 빈 대화를 무시하므로(다른 탭
덮어쓰기 방지) `reset()` 만으로는 이전 대화가 저장소에 남아 **새로고침 때 되살아난다.**

### 저장 계층 4개

| 계층 | 저장소 | 수명 |
|---|---|---|
| 세션+티켓 캐시 | localStorage `jarvis:chat:session:{channel}` | 25초 |
| threadId | sessionStorage `jarvis:chat:thread:{channel}` | 탭 |
| 대화 내용 | sessionStorage `chat:session` | 탭 |
| 화면 상태 | zustand(메모리) | 마운트 |

복원은 **마운트 시 1회만.** 이후엔 스토어가 정본이고 저장만 따라간다 —
복원 전에 저장이 돌면 **빈 스토어가 저장된 대화를 덮어쓴다.**

### `claimFailedSessionId` 가 따로 있는 이유

승계 실패 시 `sessionId` 는 null 로 비워야 하지만(구 게스트 티켓으로 스트림을
열면 403), **재시도하려면 그 값을 알아야 한다.** 그래서 별도 필드에 남긴다 —
새로고침 후에도 배너와 재시도가 살아남는다.

## 9. 게스트 → 회원 승계(CH-7)와 그 실패

채팅 화면에서 로그인·가입한 직후 `claimSession()` 이 게스트 세션을 회원으로 승계한다.
성공하면 회원 티켓으로 갈아끼우고 다른 탭에도 전파한다.

### 실패하면 조용히 새 세션을 만들지 않는다

`SessionClaimPendingError` 가 이걸 강제한다.

> 자동으로 새 세션을 만들면 화면엔 이전 대화가 남았는데 AI 는 기억하지 못하는
> 어긋남이 생긴다. 호출부가 이 에러를 잡아 "승계 실패" 안내를 띄우고,
> **사용자가 재시도/새 대화를 고른 뒤에야** 발급이 재개된다.

`allowCreate = false` 로 전달되며, 이때는 404/403 폴백도 막힌다.

### 실패 코드로 분기하지 않는다 — 전부 같은 처리

계약상 실패는 5종이다: `403 SESSION_FORBIDDEN` · `404 SESSION_NOT_FOUND` ·
**`409 SESSION_ACTIVE`**(스트리밍 중) · **`409 SESSION_CLAIM_CONFLICT`**(회원이 이미 그 채널 세션 보유) ·
`503 SESSION_CLAIM_UNAVAILABLE`.

그런데 **호출부는 `catch` 하나로 전부 동일 처리한다.** 의도된 것이다:

> 에러 종류로 거르지 않는다 — ApiError(서버가 코드로 거절)뿐 아니라 **네트워크 단절·타임아웃처럼
> 응답 자체가 없는 실패**도 "승계 못 함"은 똑같다. 좁게 잡으면 그 경우 배너 없이 조용히
> 넘어가 버린다(**실제로 그렇게 새던 것을 잡았다**).

`409 SESSION_ACTIVE` 는 계약상 "스트리밍 종료 후 1회 재시도" 권장이지만 따르지 않는다 —
로그인 직후엔 스트림이 돌 여지가 거의 없고, 기다리면 화면 전환만 늦어진다.

### 실패 후 사용자 선택지 3개

| 배너 버튼 | 동작 |
|---|---|
| 다시 시도 | `claimSession` 재호출. **실패해도 배너 유지**(원하는 만큼 누를 수 있다) |
| 기억 없이 계속 | 배너만 걷는다 → 다음 전송에서 새 세션이 생긴다 |
| 지우고 새로 시작 | abort + 새 threadId + 저장소·스토어 비움 |

> 원래 막으려던 건 "**조용히**" 맥락이 끊기는 것이지, 사용자가 알고 고르는 건 막을 일이 아니다.

말풍선은 남긴다 — 서버 맥락이 끊겼어도 하던 얘기는 보여야 "로그인했더니 대화가 사라졌다"가
되지 않는다. 배너는 메시지 목록 **위에 고정**한다(대화 흐름 안에 두면 새 메시지가 쌓일 때
위로 밀려 미해결인데도 시야에서 사라진다).

### 세션 재발급 실패 2종

| 코드 | 뜻 | 조치 |
|---|---|---|
| `403 SESSION_FORBIDDEN` | 로그인/로그아웃으로 신원이 바뀜 | 새 세션(CH-1) |
| `404 SESSION_NOT_FOUND` | TTL 10분 만료 | 새 세션(CH-1) — **맥락은 끊긴다** |

둘 다 "이 sessionId 로는 더 못 쓴다"는 뜻이라 폴백이 같다.
CH-1 이 멱등이라 폴백이 다른 탭을 축출하지 않는다.

## 10. 판매자 전용 — meta · draft · report

### meta.lane — 첫 프레임에 레이아웃을 정한다

6종: `analysis`(통계 Q&A) · `product`(수정 제안) · `general` · `confirm` · `apply` · `refused`.

`analysis` 면 즉시 이전 리포트를 비우고 스켈레톤부터 시작한다. 보관함(`pendingReport`)도
함께 턴다 — 이전 스트림이 report 만 보내고 done 없이 끊겼다면 남아 있을 수 있는데,
**그게 다음 턴 결과로 새면 안 된다.**

### done.panel — 우측 패널 조치 3종

| panel | 동작 |
|---|---|
| `replace` | 교체(분석 리포트 커밋·diff 카드는 draft 도착 시 이미 켜짐) |
| `keep` | 유지 — 되묻기·거절·일반대화 |
| `refresh` | `['seller']` 무효화 후 목록 복귀 — 쓰기가 반영됐다 |

### draft (HITL 승인)

- `op === "create"` 면 입력창을 **초안 모드**로 전환한다 — 딴 주제로 넘어가
  초안이 방치되지 않게. 수정 턴에서 새 draft 가 오면 같은 코드가 다시 돌아
  draftId·타이머가 갱신된다(별도 분기 불필요).
- **승인은 `draftId` 만 보낸다** (`action:"confirm"`, message 없음).
  발화 ≠ 동의이므로.
- **화면은 `preview` 만 본다.** `changes` 가 실행 정본이고 preview 는 사람이 읽을
  형태로 서버가 옮겨 둔 것:

  > changes 로 그리면 "32,000원"에서 32000 을 역파싱하거나 카테고리 변환·할인율
  > 계산을 FE 가 떠안게 되고, **그 계산이 AI 와 어긋나는 날이 온다.**

  preview 를 고쳐 보내도 저장 값은 안 바뀐다.
- `DraftSection.kind` 는 **닫힌 유니온이 아니다** — 종류가 늘어도 FE 배포 없이
  서버만 바뀌게. 아는 값은 `source`·`warning`·`note` 3종이고 **모르는 kind 는
  렌더하지 않는다.**
- 등록 초안은 `productId` 가 null 이다(아직 상품이 없으니까) — 결과 매칭을
  productId 로만 하면 등록 결과가 카드에 영원히 반영되지 않는다.

### `draftId` 는 캐싱 금지

수정 턴마다 새로 발급되고 이전 것은 서버가 무효화한다.
옛 값으로 confirm 하면 실패한다 — **브라우저에 남은 카드로 수정 전 값이 등록되는 걸 막는 장치**다.

### 초안 TTL 은 FE 가 잰다

> 초안은 서버에서 10분 뒤 사라지는데 그 시점엔 SSE 스트림이 이미 끝나 있어
> **서버가 알려줄 경로가 없다.** 이게 없으면 판매자가 죽은 초안에 갇힌다.

`ActiveDraft` 는 **순수 FE 표시 상태**다 — 서버에 보내지 않는다(FE 가 보낸 값을 서버가
신뢰하면 위조가 가능해진다).

### 이미지 첨부는 "새로 첨부한 턴에만" 보낸다

첨부 즉시 업로드하는 구조라 FE 가 URL 을 계속 들고 있게 되는데, **후속 턴에도 실으면
AI 가 매 턴 사진을 다시 분석한다.**

> 턴1 에 "코튼 오버핏 셔츠"였던 상품명이 턴2 에 "면 셔츠"로 바뀌고 이미지 토큰도 매번 나간다.
> AI 는 첫 분석 결과를 서버에 갖고 있어 안 보내도 이어진다.

이 규칙 하나가 깨지면 **화면만 보고는 알아채기 어렵다**(응답이 그럴듯하게 오기 때문에) —
그래서 `attachment.ts` 로 분리해 테스트로 고정했다.

`uploading` 중에는 전송을 막는다 — 통과시키면 URL 없이 요청이 나가 **이미지 없는 초안이
만들어지고, 판매자는 사진을 올렸다고 믿는다.** 반대로 `failed` 는 막지 않는다(이미지 없이
보내는 선택은 판매자 몫).

`accept="image/*"` 로 넓게 받는다 — 업로드 전 canvas 가 WebP 로 변환하므로 HEIC(아이폰 기본)도
고를 수 있어야 한다. 좁히면 사진 앱에서 아예 선택이 안 된다.

### report — 받아도 바로 안 꽂는다

```ts
case "report":
  pendingReport = e.data;   // 보관만
```

> 커밋 신호는 `done{replace}` 다. 여기서 바로 반영하면 report 뒤에 error 로
> 끝나는 스트림에서 **실패한 턴의 리포트가 패널에 남는다**(계약 §3.2: error 종료 시 폐기).

되묻기·거절은 report 없이 `done{keep}` 으로 끝난다.

## 11. 화면 맥락(screen) — path 와 label 은 금지

우측 패널을 보며 "이거 담아줘"라고 할 때의 지시어를 해소하려고 화면 맥락을 보낸다.
**무엇이 어떻게 보이고 있었는지는 FE 만 아는 사실**이라서.

다만 계약이 **명시적으로 금지**하는 게 둘 있다:

| 금지 | 이유 |
|---|---|
| `path` | 경로에 검색어 등 개인정보가 실릴 수 있다 |
| `label`(한글 화면명) | AI 가 pageType→표시명 매핑을 config 로 갖는다. FE 가 관리하면 표현이 흔들린다 |

`pageType` 만 보낸다.

## 11-1. 함정 요약 — 이것만은 기억할 것

1. **`products.ready` 는 카드를 싣지 않는다.** 경로 A 는 폐기.
2. **`ConditionChip.field` 는 유일 키가 아니다.** 항상 `(field, value)` 쌍 — React key 도.
3. **`report` 는 도착 즉시 반영하지 않는다.** 커밋 신호는 `done{replace}`.
4. **progress 해석의 `null` 은 "무시"이지 "지우기"가 아니다.**
5. **`token` 이 progress 를 지우면 안 된다** — `publishing` 이 token 뒤에 온다.
6. **자동 재시도는 401(스트림 시작 전) 1회만.** 나머지는 전부 금지.
7. **`imageUrls` 는 새로 첨부한 턴에만.**
8. **`draftId` 캐싱 금지**, draft 는 **`preview` 만 렌더**.
9. **`recommendations[].index` 재정렬 금지** — "N번 적용해줘"의 그 N 이다.
10. **개방형 유니온 3곳**: `BuyerProgressStage` · `DraftSection.kind` ·
    `chartUnavailable.reason` — 전부 "FE 배포를 기다리게 하지 않으려는 것".
11. **CH-7 실패는 code 로 분기하지 않는다** — 네트워크 실패까지 포함해 전부 배너.
