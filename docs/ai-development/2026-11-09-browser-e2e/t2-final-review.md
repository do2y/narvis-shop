이 문서는 여섯 시나리오를 **비교해** T2 전체에서 확인된 사실과 남은 위험을 정리한다. 시나리오별 세부 절차·사건 기록은 각 문서가 정본이다.

**읽을 때 지켜야 할 구분**

| 구분 | 이 문서에서의 뜻 |
|---|---|
| **검증됨** | 실제 Chromium 에서 단언으로 확인하고 반복 실행으로 재현된 것 |
| **관찰** | 반복 재현됐지만 계약으로 고정하지 않은 것(환경·정책에 따라 달라질 수 있음) |
| **가설** | 관찰과 일치하지만 원인을 직접 확인하지 않은 것 |
| **미검증** | 이번에 확인하지 않은 것 |

- 테스트 통과는 **제품 전체의 안전성 입증이 아니다** — 아래 환경과 시나리오 안에서의 결과다
- 서버가 POST 를 **받았다는 것**과 서버 작업이 **실행됐다는 것**은 다르다 — 테스트 서버는 작업을 실행하지 않는다
- 결함 주입으로 만든 위험 동작은 **현재 제품의 결함이 아니다**

## 1. 검증 목적과 환경

**목적**: T1(Vitest·jsdom)에서 단위·컴포넌트 수준으로 고정한 채팅 동작이 **실제 브라우저의 사용자 시나리오**에서도 성립하는지 확인하고, 브라우저에서만 드러나는 장애를 찾는다.

| 항목 | 구성 |
|---|---|
| 브라우저 | Playwright 1.65.0 · Chromium 헤드리스(158) · 데스크톱 기본 크기 |
| 앱 | 프로덕션 빌드 `next build` + `next start` (운영은 standalone `node server.js`) |
| REST | 브라우저 → Next 로컬 프록시 → **테스트 백엔드**(127.0.0.1:4010). 실제 백엔드 요청 없음 |
| SSE | **테스트 SSE 서버**(교차 출처). 테스트가 프레임·정상 종료·소켓 끊김·HTTP 오류를 직접 조종 · 소켓 단위 기록 |
| 앱 요청 계측 | 테스트 전용 init script 로 `window.fetch` 를 감싸 앱의 호출 횟수를 셈(제품 코드 무변경) |
| 금지한 것 | Playwright `route()` 가로채기 — 켜면 CORS 사전 요청을 브라우저가 대신 응답해 교차 출처 검증이 공허해진다(하네스 구축 중 확인) |
| 동기화 | 고정 sleep 없음 — 서버 요청 도착 · 응답 · 화면 상태로 순서를 만든다 |

### 실패 방식별로 본 "앱이 다시 보냈는가"

여섯 시나리오에서 실패를 만든 방식이 서로 달랐다. 이를 한 표로 놓으면 FE 보호가 어디까지 성립하는지 보인다.

| 실패 방식 | 채널 | 앱 fetch | 서버 수신 | 근거 |
|---|---|---|---|---|
| 새로고침(페이지 해제) | 구매자 | 1 · 새로고침 뒤 자동 재전송 없음 | 1 | C2 |
| 스트림 도중 소켓 끊김(reset) | 구매자 | 1 | 1 | C1 |
| `done` 없이 정상 종료(clean) | 구매자 | 1 | 1 | C1 |
| 스트림 도중 소켓 끊김 | 판매자 승인 | 1 | 1 | D1b |
| **응답 헤더 전 끊김 · 재사용 연결** | 판매자 승인 | **1** | **2** | D1a(관찰) |
| 응답 헤더 전 끊김 · 새 연결(2조건) | 판매자 승인 | 1 | 1 | D1a(관찰) |
| HTTP 401 | 판매자 승인 | 1 · 재발급 0 | 1 | D2 |

**검증됨**: 위 표의 **실제로 검증한 조건에서** 정책을 벗어난 앱 수준 자동 재전송은 없었다.
- 범위 밖: **일반 발화의 스트림 시작 401** 은 정책상 티켓 재발급 후 **1회 재요청이 허용되는 경로**이며, 이번 브라우저 검증에 포함하지 않았다(T1 jsdom 에서만 확인). 위 결론은 그 허용된 재요청이 없다는 뜻이 아니다
- 위 표에 없는 실패 방식(구매자 채팅의 응답 헤더 전 끊김 · SSE `error` 이벤트 · 스트림 시작 4xx/5xx 등)도 범위 밖이다

**관찰**: 서버 수신 횟수는 앱 fetch 와 항상 같지 않다 — 응답 헤더 전 끊김에서 브라우저 계층이 같은 요청을 다시 보낸 경우가 있다(§5).

## 3. 회귀 계약과 관찰 테스트의 구분

| 종류 | 테스트 | 단언하는 것 | 단언하지 않는 것 |
|---|---|---|---|
| **회귀 계약** | C2a·C2b · B1 · A1(새 탭) · D1b · D2 · C1 reset·clean · 하네스 스모크 | 앱 fetch 횟수 · 사용자 화면(실패/처리 불명 안내, 버튼 유무, 말풍선 수) · 저장소 상태 · 요청 식별자 · 사건 순서 | 페이지 해제 중 저장 시점(C2, 진단 첨부만) |
| **관찰** (회귀 계약 아님) | A1 opener 탭 · D1a 3조건 | 재현 전제 + 사용자 안전 조건(D1a) | **sessionStorage 복사·threadId 공유(A1)** · **서버 수신 횟수(D1a)** — 관찰값으로 첨부 |

관찰 테스트는 현재 동작을 바람직한 것으로 **고정하지 않는다**. 정책이 정해지면 기대 결과를 정의해 회귀로 옮긴다.

**현재 구현의 관찰값을 단언에 쓴 곳**(정책 확정 아님): C1 의 오류 문구 두 가지, C2 의 중단 안내 문구 · "부분 문구 미표시". 정책(C2 후속 C·D)이 바뀌면 함께 바꿔야 한다.

## 4. 결함 주입 결과와 탐지력 한계

모두 **격리 worktree** 에서만 제품 코드를 바꿨고, 실행 직후 원복(`src` diff 0)했다. 기준선 통과를 먼저 확인했고, **실행 경로가 있는 조건만** 탐지로 셌다. 각 변이는 **1회** 실행이다 — 아래 수치를 합쳐 단일 탐지율로 쓰지 않는다.

| 시나리오 | 변이 | 제거한 보호 | 결과 |
|---|---|---|---|
| B1 | M1 · M2 | CH-5 결과 반영의 턴 소유권 · `endTurn` 소유권 | 2/2 단언 실패 |
| A1 | MA · MC | threadId · 대화 저장의 탭 단위 저장소 | 2/2 단언 실패(MA 는 저장소 단언을 뺀 사본에서도 SSE 본문 단언으로) |
| D1b | MD2 · MD3 · MD5 | 처리 불명 정리 · `unknown` 기록 · 요청 시작 판정 | 3/3 단언 실패 |
| D1b | MD1 | 승인 401 재전송 금지 | **비대상** — D1b 에서 401 조건이 실행되지 않음 |
| D2 | MD1 | 승인 401 재전송 금지 | 1/1 직접 단언 실패("앱 승인 fetch 1회") |
| C1 | MC1 ~ MC5 | 종결 이벤트 검사 · 네트워크 오류 분류 · 실패 쌍 제거 · 자동 재요청 금지 · 재시도 허용 판정 | 5/5 단언 실패(MC1 clean · MC2 reset 에서만 집계) |

무효로 처리한 실행: B1 첫 worktree(심볼릭 링크 `node_modules` 를 Turbopack 이 거부) 3건 · D1 MD2 첫 시도(변이 형식이 타입 좁히기를 깨 빌드 실패) 1건.
별도: C2 음성 대조 2건(테스트 측 인위적 조건) · 하네스 음성 대조 3건(CORS) — 제품 코드 변이가 아니다.

### 탐지력에 대해 확인된 것

- **화면만으로는 잡히지 않는 보호가 있다.** D2-MD1 과 C1-MC4(자동 재전송 추가)에서 최종 화면은 정상과 같거나 실패 안내가 그대로 떴다. 잡은 것은 **요청 횟수를 직접 세는 단언**이다 — 재전송 방지는 화면 단언만으로 지킬 수 없다
- **간접 탐지를 걸러냈다.** D2-MD1 첫 실행은 재전송 요청이 테스트 서버에서 매달려 "안내가 안 뜸"으로 실패했다. 탐지로 세지 않고, 추가 요청에도 응답하도록 테스트를 고쳐 직접 단언으로 다시 판정했다(C1 MC4 도 같은 계측)
- MD2(D1b) 는 처리 불명 안내 단언으로 잡혔고, 그때 생긴 재시도 버튼은 `confirm()` 진입 가드 때문에 실제 재전송을 만들지 않았다(진단 프로브, 3초 관찰 창) — 2차 방어선이 있다는 관찰이지 "없음"의 증명은 아니다

### 탐지력의 한계

- 각 변이 1회 · 반복·다른 변이 세트 미실행
- 변이 목록은 AI 가 제안했다 — 같은 맹점을 공유할 수 있다(T1 개발자 라운드 같은 독립 변이는 T2 에서 하지 않음)
- 재시도가 **다른 질문**을 보내는 결함(B4형), `confirm()` 진입 가드 제거는 현재 시나리오에 실행 경로가 없어 주입하지 않았다

## 5. 발견한 위험과 정책 위반 여부

| # | 내용 | 분류 | 정책 위반 | 근거 |
|---|---|---|---|---|

| R7 | **(후속)** 스트리밍 중 앱 안 화면 이동 후 복귀하면 끊긴 부분 답변이 중단 표시 없이 완료된 답변처럼 남음 | **재현(RED 10/10)** → 개발자 분류 **"상태 구분 누락 결함"** → B안 1단계로 **해결(GREEN 10/10)** | T1 정책(떠난 것은 오류 아님)은 지켰으나 C2 판단 기준(완료와 구분)을 어김 | C3 |

두 가지를 구분한다.

- **정책 위반**: T2 의 검증 조건에서 현재 제품 코드가 확인된 정책(T1)을 어기는 동작은 **재현되지 않았다**
  - → 후속: C3(R7)에서는 T1 정책 위반이 아니라 **상태 구분이 누락된 결함**이 재현됐고(개발자 분류), B안 1단계로 수정했다(§11)
- **남은 잠재 위험**: 정책 위반이 아니더라도 위험이 남아 있다
  - **프론트엔드 구현과 관련된 것** — R2(C2: 중단 안내가 페이지 해제 중 저장 타이밍에 기댐) · R3(A1: opener 탭의 threadId 공유) · R6(부분 답변 숨김). 정책이 정해지지 않았거나 구현 방식 자체가 환경에 기대는 부분이라, FE 쪽 후속 검토 대상이다(§8)

  - **정책 미정** — R5(문구)

## 7. 서버 계약 · 멱등성 — 미검증

| 질문 | 왜 중요한가 | 문서 |
|---|---|---|
| 같은 `draftId` 승인의 중복·동시 도착 처리, 원자성 | R1 의 중복 도착이 실제 중복 실행이 되는지를 결정 | 08 Q5 · Q8 · Q9 |
| 멱등성 키의 범위·수명 | 브라우저 재전송은 본문이 같으므로, `draftId` 멱등이 유효하다면 **두 번째 도착이 중복 처리로 이어지지 않는다**(도착 자체는 막지 못함) | 08 Q6 · Q9 |
| 응답 유실 시 결과 조회·복구 | 현재 FE 는 "처리 불명"으로 끝나고 판매자가 직접 확인 | 08 §3 · Q10 |
| 운영 프록시·LB·서버 재시도, keep-alive 타임아웃, HTTP 버전 | R1 조건이 운영에서 생기는지 | 08 Q11 |
| 승인 결과 action 의 `draftId` · 이벤트 순서 · 응답 의미 | 성공 판정이 불가능해 `closed` 로만 기록 중 | 08 Q1 ~ Q4 |
| 401 재발급 뒤 sessionId 유지 | 일반 발화 재요청 본문의 정합성 | 08 Q7 |
| 장바구니·찜 action 의 멱등성 | R4 가 실제 중복 담기가 되는지 | 07 I-2 |

**멱등성은 중복 도착을 막는 장치가 아니다.** 같은 요청이 두 번 도착하더라도 실제 작업이 한 번만 적용되게 하는 서버 측 보장이다 — R1 의 중복 도착은 멱등성이 있어도 그대로 일어날 수 있고, 멱등성은 그것이 **중복 처리로 이어지는지**를 결정한다.
운영 서버의 멱등성 구현 여부와 처리 결과는 **미검증**이다. **테스트 서버의 1회 수신·401 응답은 서버 멱등성이나 "처리되지 않았음"의 근거가 아니다.**

**코드 판독(후속)**: 위 질문에 대해 로컬 서버 레포 사본(AI 서버 · BE)을 읽은 결과가 [08 §5](../2026-10-31-chat-turn-test/08-server-questions.md#5-서버-코드-확인-결과-2026-11-10)에 있다(질문별 답은 §5.2, 서버 쪽 중복 실행 경로는 S1·S2).
**코드 판독이며 서버 실행 검증이나 운영 환경 확인은 아니다** — 위 표의 "미검증"은 실행 검증 기준이므로 그대로 둔다.
