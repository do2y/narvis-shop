# T2-D1 · 판매자 승인 요청 도중 연결이 끊기는 상황

> 2026-11-10 · 테스트 [e2e/d1-seller-approval-disconnect.spec.ts](../../../e2e/d1-seller-approval-disconnect.spec.ts) · 제품 코드 변경 없음

## 결론

- **D1b(응답 헤더·토큰 수신 뒤 스트림 도중 끊김) — 회귀 테스트로 확정.** T1 정책대로 자동 재전송 없음 · 처리 불명 안내 · 재시도 수단 없음 · 카드 잠금
- **D1a(응답 헤더 전 끊김) — 관찰 테스트 3조건(회귀 계약 아님).** 세 조건 모두 **앱의 승인 fetch 1회**와 사용자 안전 조건을 만족했다.
  다만 승인이 **이전 요청에 쓰던 연결로 나간 조건에서만** 같은 승인 POST 가 서버에 **두 번 도착**했다(20/20).
  연결 재사용과 관련이 있다는 관찰이며, Chromium 내부 구현이나 운영 환경에서도 같다고 **단정하지 않는다**
- **서버 수신은 처리 결과가 아니다.** 연결이 끊긴 뒤의 승인 성공·실패·중복 실행은 FE가 알 수 없고, 운영 서버의 멱등성은 **미확인**이다
  → 서버 협의 질문 [08 Q8~Q11](../2026-10-31-chat-turn-test/08-server-questions.md)

## 검증 목적과 T1 승인 재시도 정책

T1([03 §12·§13](../2026-10-31-chat-turn-test/03-validation.md))에서 정한 정책을 실제 브라우저·실제 연결 끊김에서 확인한다.

| 구분 | 정책 | 구현 |
|---|---|---|
| 요청 시작 전 실패 | 승인 상태 되돌림 · 다시 승인 가능 | `settleApproval` · `resend` 유지 |
| 요청 시작 후 실패(401 포함) | **자동 재전송 금지** | `useChat` 승인은 401 재발급·재전송 분기를 타지 않음 |
| 처리 여부 불명 | `unknown` · "처리됐는지 확인하지 못했어요" · `retryable:false` · 카드 잠금 | `settleResend` · `settleApproval` · `DraftApprovalNotice` |
| 사용자 명시적 재실행 | 같은 초안은 거부 · 같은 대상 새 초안은 경고 | `confirm()` 진입 가드 · `hasDuplicateRisk` |

"요청 시작"은 **fetch 호출 여부**(`requestStarted`)로 판정한다 — 서버 수신 여부가 아니다. 사전 조사에서 정책과 구현의 불일치는 없었다.

## 연결을 끊는 방식

HTTP 오류 응답(500 등)이 아니라 **테스트 SSE 서버가 소켓을 직접 끊는다.** 연결 식별은 헤더 값이 아니라 서버가 받은 **소켓 번호와 그 소켓 안에서의 요청 순번**으로 한다(하네스 계측).

| | 끊는 시점 | 브라우저 최종 오류 |
|---|---|---|
| D1a | 승인 요청 본문 수신 후, **응답 헤더 전** | `net::ERR_EMPTY_RESPONSE` |
| D1b | 200 헤더와 토큰 1개를 보낸 뒤 **스트림 도중** | `net::ERR_INCOMPLETE_CHUNKED_ENCODING` |

## D1a — 세 연결 조건의 실제 사건 순서 (대표 1회)

| 조건 | 서버 사건 순서 |
|---|---|
| **keep-alive** | `#1 열림 → 사전 요청(#1-0) → 초안 POST(#1-1) → 승인 POST(#1-2) → 테스트가 끊음(헤더 전) → #1 닫힘 → #2 열림 → 같은 승인 POST(#2-0) → 끊음 → #2 닫힘` |
| **keep-alive + 승인 직전 유휴 연결 닫음** | `#1 열림 → 사전 요청(#1-0) → 초안 POST(#1-1) → 테스트가 유휴 #1 닫음 → #1 닫힘 → #2 열림 → 승인 POST(#2-0) → 끊음(헤더 전) → #2 닫힘` |
| **Connection: close** | `#1 사전 요청 → #1 닫힘 → #2 초안 POST → #2 닫힘 → #3 열림 → 승인 POST(#3-0) → 끊음 → #3 닫힘` |

`#n-k` = n번 소켓의 k번째 요청(0 = 새 연결의 첫 요청). 두 번째 조건은 응답에 `Connection: close` 를 싣지 않는다 — keep-alive 정책은 그대로이고, 테스트가 승인 직전에 유휴 연결만 닫는다.

## 앱 fetch · 브라우저 논리 요청 · 서버 수신의 차이

| 층 | 무엇을 세나 | 방법 |
|---|---|---|
| 앱 fetch | 앱 코드가 승인 `fetch` 를 부른 횟수 | 테스트 전용 init script 로 `window.fetch` 를 감싸 계측(제품 코드 무변경) |
| 브라우저 논리 요청 | 브라우저가 페이지에 노출한 요청 수 | Playwright `request` 이벤트 |
| 서버 수신 | 테스트 서버에 실제로 도착한 승인 POST | SSE 서버 기록(소켓 단위) |

## D1a — 20회 관찰 결과 (조건별, 매번 같음)

| 조건 | 유효 실행 | 앱 fetch | 논리 요청 | **서버 수신** | 수신별 소켓 내 순번 | 최종 오류 |
|---|---|---|---|---|---|---|
| keep-alive | 20/20 | 1 | 1 | **2** | 2 → 0 | `ERR_EMPTY_RESPONSE` |
| keep-alive + 유휴 연결 닫음 | 20/20 | 1 | 1 | **1** | 0 | `ERR_EMPTY_RESPONSE` |
| Connection: close | 20/20 | 1 | 1 | **1** | 0 | `ERR_EMPTY_RESPONSE` |

- 같은 승인 POST 가 다시 도착한 것은 **첫 승인 POST 가 재사용 연결로 나간 조건뿐**이었다. 재도착한 요청은 본문·`draftId`·`threadId`가 같았다
- 앱 fetch·논리 요청이 1회이므로 재전송은 JS 아래 계층에서 일어났다. Chromium 의 "재사용 연결이 응답 전에 끊기면 다시 보낸다"는
  알려진 동작과 일치하지만 **소스 수준에서 확인하지 않았다**
- **유효 실행 판정**(유휴 연결 닫음 조건): 첫 승인 POST 가 ① 새 연결의 첫 요청이고 ② 테스트가 닫은 연결보다 나중에 열린 연결이어야 한다.
  아니면 `invalid-comparison` 으로 표시하고 비교에서 뺀다. 이번 20회는 모두 유효
- 서버 수신 횟수는 **단언하지 않는 관찰값**이다(첨부 `D1a-<조건>.json`)

### 동기화와 종료 조건 (고정 대기 없음)

서버에 승인 POST 가 올 때마다 응답 헤더 전에 끊고, **브라우저가 그 논리 요청을 `requestfailed` 로 종결한 시점**을 "더 이상의 재전송 없음"의 경계로 본다.
종결된 요청은 브라우저가 다시 보낼 수 없고, 그 뒤의 요청은 앱의 새 fetch 여야 하므로 계측에 잡힌다. 서버 수신이 5회를 넘으면 관찰을 중단한다(안전장치).
종결 이후에 브라우저 밖(프록시 등)에서 다시 보내는 경우는 이 경계로 잡지 못한다.

## 결함 주입 (격리 worktree, D1b 대상, 각 1회)

스크래치패드 `git worktree`(기점 `bacbb48` + 미커밋 하네스·D1 테스트 복사)에서만 제품 코드를 바꿨다. worktree 기준선 D1b 통과를 먼저 확인했고,
각 주입 뒤 `git checkout` 으로 원복(`src` diff 0 확인), worktree 는 제거했다. **주입 결함은 현재 제품의 결함이 아니다.**

| 변이 | 제거한 보호와 원래 역할 | D1b 에서 그 경로가 실행되나 | 결과 | 실패한 단언 |
|---|---|---|---|---|
| MD1 | 승인은 401 이어도 재발급·재전송하지 않음(`if (resend?.kind === "confirm") throw err`) | 줄은 실행되나 **401 조건이 실행되지 않아 동작이 같다** | 통과(생존) | — **탐지력 근거에서 제외 · D2(승인 401) 후속 검증** |
| MD2 | `settleResend` 의 승인·요청 시작 분기 — 처리 불명 문구로 바꾸고 재시도를 숨김 | 실행됨 | ✘ 검출 | 처리 불명 안내 기대 2, 실제 1 |
| MD3 | `settleApproval` 의 요청 시작 후 `unknown` 기록 | 실행됨 | ✘ 검출 | 처리 불명 안내 기대 2, 실제 1 |
| MD5 | `requestStarted = true` 표시(요청 시작 판정) 자체 | 실행됨 | ✘ 검출 | 처리 불명 안내 기대 2, 실제 0 |

MD2 첫 시도는 변이 형식(`&& false`)이 타입 좁히기를 깨 **빌드 실패** — 환경 오류로 세지 않고, 타입 좁히기를 유지하는 형식(`&& Math.random() < 0`)으로 다시 주입했다.

### 관찰된 위험 동작 (worktree 전용 진단 프로브, 커밋 안 함)

D1b 는 첫 실패 단언에서 멈추므로, 변이별로 화면에 남는 버튼을 사용자처럼 눌러 서버에 승인이 다시 오는지 따로 봤다.

| 변이 | 원복 전 화면 | 남은 버튼을 누르면 |
|---|---|---|
| 기준선 | 처리 불명 안내 2 · 재시도 0 · 적용 0 | 누를 버튼 없음 |
| MD2 | 말풍선: 일반 오류 + **다시 시도** / 카드: 처리 불명 | 승인 재전송 **없음**(3초 관찰 창) — `confirm()` 진입 가드가 `unknown` 초안을 거부. 눌러도 사라지기만 하는 버튼 |
| MD3 | 말풍선: 처리 불명 / 카드: **적용 복귀** | 적용 → **승인 POST 서버 재도착(2회)** |
| MD5 | 일반 오류 + **다시 시도 + 적용** | 다시 시도 → **승인 POST 서버 재도착(2회)** |

- **MD2**: D1b 가 잡은 것은 **처리 불명 안내 단언 실패**다. 일반 오류 문구와 **일반 재시도 버튼 노출**은 D1b 단언이 아니라 위 프로브에서 관찰한 위험이다
  (D1b 는 안내 단언에서 먼저 멈춘다). 승인 POST 재전송은 **관찰되지 않았다** — 진입 가드가 2차 방어로 막았다(3초 창 안의 관찰, "없음"의 증명은 아니다). **중복 승인 실행 사례가 아니다**
- **MD3 · MD5**: 사용자가 남은 버튼을 누르자 **같은 승인 POST 가 테스트 서버에 다시 도착**한 것까지 확인했다. 테스트 서버는 승인을 처리하지 않으므로
  **실제 서버가 승인을 중복 처리하는지는 확인하지 않았다**

### 결함 주입의 한계

- 각 1회 실행. 반복하지 않았다
- **앱 수준 자동 재전송(MD1 = 401 재전송)은 D1b 로 검증할 수 없다** — 401 은 스트림 시작 전 거부라 D1b 의 경로가 아니다. 별도 시나리오(D2: 승인 401) 필요
- `confirm()` 진입 가드 제거는 D1b 에 다시 누를 경로가 없어 주입하지 않았다

## 서버 수신과 실제 승인 실행의 차이

서버가 요청을 받은 뒤 연결이 끊겼다는 사실만으로는 승인이 **처리됐는지 · 실패했는지 · 두 번 처리됐는지** 판단할 수 없다.
테스트 서버는 승인을 처리하지 않는다. keep-alive 조건의 "서버 수신 2회"는 **같은 승인이 서버에 두 번 도착할 수 있다**는 뜻이며,
실제 서버가 두 번 실행하는지는 서버의 `draftId` 멱등성에 달려 있다 — **운영 서버의 멱등성은 확인하지 않았다**(08 Q5·Q6·Q8·Q9).

## 반복 실행 중의 `ECONNREFUSED`

| | 내용 |
|---|---|
| 관찰 사실 | Next 서버 로그에 `TypeError: fetch failed` · `connect ECONNREFUSED 127.0.0.1:4010` — D1 80회 반복 중 1회, 최종 전체 실행(10건) 중 1회. 어느 테스트도 실패하지 않았다. 로그에 요청 경로는 남지 않는다 |
| 원인 추정(미확인) | 앞 테스트의 테스트 백엔드(4010)가 내려간 뒤, 이전 페이지가 늦게 보낸 `/api` 요청을 Next 로컬 프록시가 전달하려다 거부당한 것으로 본다. 어느 테스트·어떤 요청인지는 특정하지 않았다(D1 고유 현상인지도 미확인) |
| 영향 | 테스트 결과에는 영향이 없었다. **원인이 특정되지 않은 관찰 사항**으로 남긴다 — 위 추정을 확인하려면 요청 경로를 남기도록 하네스를 보강해야 한다 |

## 환경 한계

- Chromium 헤드리스 · loopback **HTTP/1.1** · TLS 없음 · `next start` · 데스크톱. HTTP/2 · TLS · ALB/nginx 경유 · Firefox·WebKit 미검증
- 목 백엔드·목 SSE 서버 — 승인 처리·멱등성·서버 재시도는 모델링하지 않음
- 유휴 연결 닫음 조건의 남은 경쟁: 서버가 닫은 직후 브라우저가 알아채기 전 그 소켓으로 보내면 첫 시도가 서버에 닿지 않고 새 소켓으로 재전송될 수 있고,
  이는 서버에 "새 소켓의 첫 요청"으로만 보여 사후 판정으로 구별할 수 없다. 20회에서 그 증거는 없지만 없었다고 증명하지도 못한다
- 판매자 화면이 부르는 `GET /api/seller/orders` 는 하네스에 등록하지 않아 404(범위 제외 — 결과에 영향 없음)
- 수정(update) 초안만 다뤘다. 등록·삭제 초안은 같은 confirm 경로지만 브라우저에서 따로 확인하지 않았다
