**사용한 프롬프트 (요지)**
> 실제 저장소의 코드·테스트·문서와 대조하고, 일치하지 않는 부분은 보고해라. 이전 작업을 이미 이해했다고 가정하지 마라.
> (…) 우선 Phase 0과 Phase 1만 수행해라. 내 승인 전에는 코드 수정, 테스트 추가, 패키지 설치, 설정 변경, 커밋, PR 생성을 진행하지 마라.

**AI의 제안**
- 저장소와 T1 기록 대조 — 테스트 수(509건)는 일치. 개발자가 전달한 맥락의 "별도 독립 검증"은 실제로는 **개발자 변이 라운드(D1~D8)** 이며 문서가 87/87 과 합치지 않는다는 표현 차이를 보고
- 브라우저 전용 위험 후보: 스트리밍 중 새로고침 · 탭 복제의 sessionStorage 복사 · 실제 소켓 끊김의 오류 분류 · Web Locks · StrictMode
- Playwright 미설치 · `route.fulfill` 은 스트리밍 불가로 추정 → 조종 가능한 테스트 SSE 서버 제안. P0: C2 → B1 → A1 → D1 → D2 → C1

**검토 결과**
`route.fulfill` 스트리밍 불가는 추정으로 남겼다가 설치 후 타입 정의(`string|Buffer`)로 확인함.

**개발자의 결정**
Playwright·Chromium 설치, 테스트 전용 SSE 서버, 운영 빌드(`next start`) 기본 · StrictMode 만 dev 서버, CI 유지, 실제 백엔드·AI 서버 요청 금지.

## #2 · 2026-11-09 · 하네스 구축 — Playwright 가 CORS 사전 요청을 대신 응답했음 📌

**작업 목적**
설정 · SSE 서버 · 스모크 1건만 구현하고 교차 출처 CORS 까지 검증.

**사용한 프롬프트 (요지)**
> 스모크 테스트에서는 실제 브라우저의 전송 → SSE 응답 → 상품 카드 표시까지 확인하고, 교차 출처 CORS/preflight 처리도 검증하세요.

**AI의 제안 · 실행에서 드러난 것**
- 첫 실행에서 SSE POST 는 왔는데 **사전 요청이 서버에 기록되지 않음** → playwright-core 소스에서 "요청 가로채기가 켜져 있으면 모든 사전 요청을 대신 허용 응답"하는 코드 확인. `route()` 를 쓰는 한 CORS 검증이 공허함
- REST 목을 브라우저 가로채기 대신 **테스트 전용 HTTP 백엔드**로 옮기는 구조 변경 제안
- 음성 대조 N1(사전 요청 거부) 첫 실행이 **30초 타임아웃**으로 끝남 → 탐지로 세지 않고, 요청 도착을 단언으로 기다리게 테스트를 고친 뒤 N1~N3 모두 단언 실패로 검출

**검토 결과**
테스트가 통과했어도 그 통과가 무엇을 검증했는지는 별개라는 점이 하네스 단계에서 이미 드러남. AI 가 처음 짠 대기 방식(`nextStream()` 만 기다림)은 실패 원인을 말하지 못하는 테스트였음.

**개발자의 결정**
테스트 백엔드 구조 승인 · `next start` 유지(standalone 차이는 한계로 기록) · 하네스만 별도 커밋.

> 결함이 확인되더라도 프로덕션 코드를 바로 수정하지 마세요.

**AI의 제안 · 실행에서 드러난 것**

**개발자의 결정**
opener 탭은 **잠재적 설계 결함 후보** · 현 사용자 경로(noopener)의 결함 아님 · 관찰 테스트는 회귀 계약 아님.

## #8 · 2026-11-10 · D1 연결 조건 비교 — 헤더가 아니라 소켓으로 판정

**사용한 프롬프트 (요지)**
> 헤더 설정만으로 새 연결이라고 단정하지 말고 실제 소켓 또는 연결 식별 기록을 통해 확인해주세요. (…) 새 소켓 사용이 확인되지 않은 실행은 유효한 비교 결과로 계산하지 마세요.

**AI의 제안 · 실행에서 드러난 것**
- 하네스에 소켓 식별·사건 기록·`connectionClose`·`closeIdleSockets` 추가 → keep-alive(재사용) 2회 · 유휴 연결 닫음 1회 · Connection: close 1회(각 20/20, 무효 실행 0)
- 결함 주입: MD1(401 재전송 금지)은 D1b 경로에서 401 이 실행되지 않아 **비대상** · MD2 첫 시도는 AI 가 쓴 변이 형식(`&& false`)이 타입 좁히기를 깨 **빌드 실패** → 환경 오류로 제외 후 재주입
- 진단 프로브로 MD2 의 재시도 버튼은 `confirm()` 가드 때문에 실제 재전송을 만들지 않음을 관찰(3초 창)

**개발자의 결정**
D1b 회귀 확정 · D1a 3조건 관찰 유지(수신 횟수는 계약 아님) · MD2 는 "중복 승인 실행 사례가 아님"으로 기록 · 서버 질문 Q8~Q11 추가.

## #9 · 2026-11-10 · D2 — 간접 증상으로 잡힌 탐지를 거부 📌

**작업 목적**
판매자 승인 401 에서 재발급·재전송이 없는지, D1 에서 비대상이던 MD1 을 다시 검증.

**사용한 프롬프트 (요지)**
> 변이가 살아남았다는 이유만으로 현재 제품이 안전하다고 결론 내리지 마세요.

**AI의 제안 · 실행에서 드러난 것**
- MD1 첫 실행은 실패했지만 실패 지점이 "처리 불명 안내 0" — 재전송된 요청에 테스트 서버가 응답하지 않아 **매달린 간접 증상**
- 진단 프로브로 MD1 은 재발급 후 같은 승인을 다시 보내고, 재전송에도 401 이 오면 **최종 화면이 정상과 같음**을 확인 → 화면 단언으로는 잡을 수 없는 보호
- 추가 요청에도 즉시 401 을 주도록 테스트를 고쳐 "앱 승인 fetch 1회" 단언에서 직접 실패하게 함

**개발자의 결정**
수정 후 결과만 MD1 의 탐지 근거로 사용 · 첫 실행은 탐지 횟수에 세지 않음.
