# T2-D2 · 판매자 승인 요청이 401 로 거부되는 상황

> 2026-11-10 · 테스트 [e2e/d2-seller-approval-401.spec.ts](../../../e2e/d2-seller-approval-401.spec.ts) · 제품 코드 변경 없음

## 결론

- **회귀 테스트.** 승인 요청이 HTTP 401 로 거부돼도 **티켓 재발급·승인 재전송 없이** 처리 불명으로 안내하고 같은 승인의 재실행을 막는다 — T1 정책(I-6)과 일치. 기준선 20/20
- D1 에서 비대상이었던 **MD1(승인 401 재전송 금지 제거)을 D2 에서 직접 탐지**했다 — "앱의 승인 fetch 1회" 기대 1, 실제 2.
  MD1 에서 **최종 화면은 정상 코드와 같았지만 승인 POST 가 한 번 더 발생**했다. MD1 은 격리 worktree 에서만 만든 변이이며 **현재 제품 코드의 결함이 아니다**
- 테스트 서버의 401 은 "수신 + 거부 응답"까지다. **운영 서버에서 401 이 났을 때 승인이 실행되지 않았다고 단정하지 않는다**

## 검증 목적과 T1 정책

T1 I-6([03 §12](../2026-10-31-chat-turn-test/03-validation.md))에서 정한 "승인은 401 이어도 자동 재전송하지 않는다"를 실제 브라우저·실제 HTTP 401 로 확인한다.

### 일반 발화의 401 복구와 판매자 승인 401 처리의 차이

| | 일반 발화 · 칩 제거 | 판매자 승인 |
|---|---|---|
| 스트림 시작 401 | `refreshTicket` 으로 티켓 재발급 → **같은 본문으로 1회 재요청** | 재발급·재요청 분기를 타지 않고 곧바로 실패 처리([useChat.ts](../../../src/shared/chat/useChat.ts) `if (resend?.kind === "confirm") throw err`) |
| 이유 | 요청이 서버에서 처리되기 전 거부라고 보고 복구 | 요청을 이미 보냈다(`requestStarted`). 401 이 "처리 전 거부"라는 근거가 서버 코드 확인이 아니라 계약 문서뿐이고, 다시 나간 승인은 등록·수정·삭제를 실행한다 |
| 실패 정리 | 재요청도 실패하면 실패 말풍선(재시도 가능) | `settleResend` 가 처리 불명 문구·`retryable:false` 로 정리 → `settleApproval` 이 `unknown` 기록 → 카드 잠금 |

AT 만료용 `/api/auth/refresh`(axios 인터셉터)는 SSE 401 과 별개 경로다.

### 승인 전 fresh 티켓과 401 이후 재발급 금지

- **승인 직전**: 캐시를 건너뛰고 새 티켓 1회(`ensureSession(..., { fresh: true })`) — 만료 직전 티켓으로 거부될 일을 줄이려는 **정상 발급**
- **401 이후**: 재발급하지 않는다 — 재발급은 곧 재요청 준비이기 때문이다

## 실제 HTTP 요청·응답 사건 순서

401 은 HTTP 오류 응답(`{"success":false,"error":{"code":"TOKEN_EXPIRED"}}`)이다 — D1 의 연결 끊김과 다르다. Playwright 가로채기 없이 테스트 SSE 서버가 실제로 응답한다.

| 구간 | 사건 순서(단언) |
|---|---|
| 부팅·초안 턴 | `인증 refresh 1회 → 판매자 세션 발급 1회` (정상) |
| **승인** | `사용자 적용 클릭 → 티켓 발급(승인 직전 fresh) → 서버 승인 POST 수신 → 서버 401 응답 → 화면 처리 불명 안내 → 사용자 초안 닫기` |

승인 POST 는 이전 요청에 쓰던 연결로 도착했다(서버 소켓 기록). 401 은 응답 헤더를 받은 경우라 D1a 와 달리 브라우저 계층 재전송도 없었다.

### 횟수 (기준선)

| 항목 | 결과 | 근거 |
|---|---|---|
| 사용자 적용 클릭 | 1 | — |
| 앱의 승인 fetch | **1** | 테스트 전용 init script 의 `window.fetch` 계측(제품 코드 무변경) |
| 서버 승인 POST 수신 | **1** | SSE 서버 기록 |
| 브라우저가 받은 승인 응답 | `[401]` | Playwright `response` 이벤트 |
| 승인 **전** 티켓 발급 | 1 (정상) | 테스트 백엔드 사건 기록 |
| 승인 401 **후** 티켓 재발급 · 인증 refresh | **0** | 같은 기록 — 사건 순서 단언 |

승인 요청 본문: 최상위 `action:"confirm"` · 올바른 `draftId`, `message` 없음.

### 동기화 — 고정 대기 없음

앱이 401 에 재요청한다면 그 재요청은 바깥 catch(처리 불명 안내) **이전**에 일어난다. 그래서 **처리 불명 안내가 화면에 뜬 시점**을 "앱의 재전송 결정이 끝난 시점"으로 보고 그 뒤에 횟수를 단언한다.
또 첫 승인 이후 도착하는 SSE 요청에는 서버가 즉시 401 을 준다(아래 "테스트 약점과 수정").

## 처리 불명 안내와 승인 재실행 방지 (단언)

- "요청이 처리됐는지 확인하지 못했어요…" — 말풍선 · 초안 카드 두 곳
- "적용" 버튼 사라짐 · 성공 표시 없음 · `closed` 문구 없음 → 상태 `unknown`
- "다시 시도" 없음 · 남은 동작은 "상품 목록 보기" · "초안 닫기" · 입력 가능
- "초안 닫기" 뒤에도 앱 승인 fetch 1 · 서버 수신 1

## MD1 결함 주입 (격리 worktree)

스크래치패드 `git worktree`(기점 `a134deb` + 미커밋 D2 테스트 복사)에서만 제품 코드를 바꿨다. worktree 기준선 통과를 먼저 확인했고, 실행마다 `git checkout` 으로 원복(`src` diff 0 확인), worktree 는 제거했다.
**MD1 은 이 worktree 에서만 만든 변이이며 현재 제품 코드의 결함이 아니다.**

| 항목 | 내용 |
|---|---|
| 변경 | `if (resend?.kind === "confirm") throw err;` 제거 |
| 원래 역할 | 판매자 승인이 401 이어도 재발급·재요청 분기를 타지 않게 막는다(I-6) |
| D2 에서 그 분기가 실행되나 | **예** — `StreamStartError(401)` 이라 재발급 분기에 진입한다 (D1b 에서는 401 이 아니라 동작이 같아 비대상이었다) |
| 변이 시 실제 동작(진단 프로브) | `티켓 → 승인#1 → 401 → **티켓 재발급** → **승인#2(본문 동일)** → 401` — 서버 승인 POST 수신 2회 |
| 같은 프로브, 정상 코드 | "승인#2 도착" 단언 실패(기대 3, 실제 2) — 정상 코드는 재전송하지 않는다 |
| **수정된 D2 결과** | ✘ **"앱의 승인 fetch 1회" 기대 1, 실제 2** 에서 실패(1.2초). 처리 불명 안내 단언은 **통과** |

**MD1 에서 최종 UI 는 정상 코드와 같았다.** 재전송된 승인#2 도 401 로 끝나면 화면은 처리 불명 안내로 끝난다 — 화면만으로는 승인 POST 가 한 번 더 나갔다는 사실을 알 수 없다.
그래서 이 보호는 **요청 수를 직접 세는 단언**(앱 fetch · 서버 수신 · 사건 순서)으로만 지킬 수 있다.

진단 프로브는 worktree 전용으로 썼고 커밋하지 않았다. 결함 주입은 **1회 검증**이다.

### 첫 MD1 실행에서 발견한 테스트 약점과 수정 이유

| | 내용 |
|---|---|
| 첫 실행(수정 전 테스트) | ✘ 실패 — 그러나 실패한 단언은 "처리 불명 안내 기대 2, 실제 0" |
| 원인 | 재전송된 승인#2 에 **테스트 서버가 응답하지 않아 매달렸다** → 안내가 뜨지 않음. 재전송을 직접 짚은 단언이 아니라 매달림이 만든 **간접 증상**으로 실패했다 |
| 문제 | 서버가 재전송에도 즉시 응답하는 환경이었다면 화면은 정상과 같아, 그 단언은 재전송을 잡지 못한다 |
| 수정 | 첫 승인 이후 도착하는 SSE 요청에도 서버가 **즉시 401** 을 주게 했다 — 매달림을 없애 재전송 여부를 직접 단언이 판정하게 함. **기존 단언은 빼지 않았다** |
| 수정 후 | 기준선 20/20 · MD1 은 "앱 승인 fetch 1회" 단언에서 직접 실패 |

첫 실행 결과는 탐지 횟수로 따로 세지 않고, 수정 후 결과를 MD1 의 탐지 근거로 쓴다.

## 서버 수신과 실제 승인 처리 결과의 차이

테스트 서버는 승인을 처리하지 않는다 — 요청을 받고 401 을 돌려줄 뿐이다. 따라서
- 기준선의 "서버 수신 1회 · 401" 은 **FE 가 다시 보내지 않았다**는 근거이지, 운영 서버에서 승인이 실행되지 않았다는 근거가 아니다
- MD1 의 "서버 수신 2회" 는 **같은 승인이 서버에 두 번 도착**했다는 뜻이며, 실제 서버가 두 번 실행하는지는 서버의 `draftId` 멱등성에 달려 있다
- 운영 서버의 승인 처리 결과 · 멱등성 · 결과 조회는 **미검증**이다([08 Q5·Q6·Q8~Q10](../2026-10-31-chat-turn-test/08-server-questions.md))

## 미검증 범위

- **실제 HTTP 401 + `TOKEN_EXPIRED` 본문만** — 다른 401 코드·본문 없는 401 미검증
- **수정(update) 초안에 한정** — 등록·삭제 초안은 같은 confirm 경로지만 브라우저에서 따로 확인하지 않음
- **Chromium 헤드리스 · loopback HTTP/1.1 · 테스트 서버 · `next start`** — HTTP/2 · TLS · 다른 브라우저 · ALB/nginx 운영 경로 미검증
- **일반 발화의 401 재발급·1회 재요청은 브라우저 미검증**(T1 jsdom 만)
- **운영 서버의 승인 처리 결과와 멱등성 미검증**
- **MD1 결함 주입은 1회**(수정 후 테스트 기준)
- "재전송 없음" 판정 경계는 처리 불명 안내 표시 시점 — 그 이후나 브라우저 밖에서의 요청은 범위 밖

## 후속 과제

- 일반 발화의 401 복구(재발급 + 1회 재요청)를 브라우저에서 확인
- 등록·삭제 초안, 다른 401 본문 변형
- D1·D2 에 중복된 판매자 준비 코드의 하네스 공통화(하네스 정리 후보)
- 서버 답변(08) 이후 결과 조회·멱등성 계약에 맞춘 기대 결과 재정의
