# T2-C3 · 스트리밍 중 앱 안의 다른 화면으로 이동했다가 복귀

> 2026-11-10 · 테스트 [e2e/c3-navigate-away-mid-stream.spec.ts](../../../e2e/c3-navigate-away-mid-stream.spec.ts)
> **현재 상태: 해결 — B안 1단계 적용 후 GREEN 10/10.** 아래 "결론"~"실행 기록"은 수정 전(RED 10/10) 재현 기록이며 그대로 보존한다. 수정 결과는 [수정 후 — B안 1단계](#수정-후--b안-1단계-2026-11-10).

## 결론

- **재현됨.** 답변 도중 앱 안의 다른 화면(`/home`)으로 이동했다가 돌아오면, 끊긴 부분 답변이 **중단 표시 없이 일반 답변 말풍선으로** 남는다.
  새로고침해도 같은 모습으로 복원된다. 실패 안내 · 재시도 버튼 · 타이핑 표시가 모두 없다 — Chromium 에서 10/10
- **원인은 C2 와 다르다.** C2 는 페이지 해제 중 `TypeError` → 실패 표시 저장이라는 **타이밍**에 기댄 경로였다. C3 는 언마운트 abort 가
  `AbortError` 분기로 가서 **설계상 실패를 남기지 않는** 경로다 — 타이밍과 무관하게 매번 같다
- **정책 기준이 서로 부딪친다.** T1 정책(P-a "화면을 떠난 것은 오류가 아니다")은 지켜졌고, T2-C2 의 판단 기준(P-b "끊긴 답변은 완료된 답변과 구분돼야 한다")은 깨졌다.
  현재 구현에는 실패 말풍선 말고 "중단" 표시 수단이 없어 두 기준을 동시에 만족할 수 없다
- **결함 여부와 수정 방향은 개발자 결정 대기.** 이 문서는 재현과 원인까지다. 테스트는 P-b 를 단언하므로 현재 RED 이며, 통과시키기 위해 단언을 바꾸거나 `test.fail()` 로 감추지 않았다

## 검증 목적

C2 후속 분석에서 코드로 예측한 "언마운트 abort 뒤 부분 답변이 표시 없이 남는다"를 실제 브라우저에서 확인한다.
C2(새로고침 = 문서 교체)와 달리 **클라이언트 내비게이션 = 같은 문서 · 컴포넌트 언마운트** 경로라 독립적인 검증이다.

## 환경

T2 공통 하네스 — Chromium 헤드리스 · `next build` + `next start` · 테스트 백엔드 · 테스트 SSE 서버 · 앱 fetch 계측(테스트 전용 init script). 고정 sleep 없음.
`/home` 서버 렌더링이 부르는 `/api/categories` 는 계약 모양의 빈 목록으로 응답했다. 등록하지 않은 API 호출 0건.

## 절차

1. `/chat` 에서 질문 전송 → SSE 서버가 진행 1개 · 토큰 2개만 보내고 스트림을 열어 둔다
2. 부분 답변이 화면에 보일 때까지 대기
3. 헤더 로고 링크(`Narvis 홈`)로 `/home` 이동 — **클라이언트 내비게이션**
4. 재현 전제 확인: SSE 서버에서 클라이언트가 연결을 끊었음(`clientClosed`) · fetch 계측이 이어져 있음(같은 문서)
5. 브라우저 뒤로 가기로 `/chat` 복귀 → 복원된 질문 말풍선이 보일 때까지 대기 → 화면·저장소 관찰
6. 새로고침 → 다시 관찰

### C2 와의 관계

| | C2 새로고침 | C3 앱 안 이동 |
|---|---|---|
| 문서 | 교체(페이지 해제) | 유지(컴포넌트 언마운트) |
| 끊기는 예외 | `TypeError: network error` | `AbortError` |
| 분기 | catch 기본 분기 → 실패 표시 | `isAbortError` → 아무것도 안 함 |
| 결과 | 중단 안내로 복원(해제 중 저장 **타이밍에 기댐**) | 완료처럼 남음(**설계상 매번**) |
| 공통 원인 | 메시지에 **완료 여부를 나타내는 상태가 없다** — "`error` 없음"이 "완료"와 "중단"을 구별하지 못한다 |

두 경로의 근본 원인은 같다(완료 상태 부재). C2 는 그 공백을 해제 중 저장이 우연히 메우고, C3 는 메우는 경로가 없다.
C2 후속 분석의 B안(완료 상태 명시 저장)은 두 경로를 함께 다룰 수 있는 후보다 — 단 **취소(언마운트·새 대화) 경로의 상태를 무엇으로 둘지**가 핵심 결정이 된다.

## 수정 후 — B안 1단계 (2026-11-10)

### 무엇을 바꿨나

assistant 말풍선에 진행 상태(`streaming` · `complete` · `failed` · `interrupted`)를 두고, 화면 판정(실패 말풍선 · 재시도)은 지금처럼 `error` 로 한다.
설계 근거와 경로별 전이는 [C2c 기록의 시사점](c2c-reload-during-card-fetch.md#c3-개선b안에-주는-시사점)과 코드 주석이 정본이다 — 여기서는 반복하지 않는다.

| 전이 | 위치 |
|---|---|
| 상태 타입 · 조건부 전이 액션 · 실패 시 `failed` | [store.ts](../../../src/shared/chat/store.ts) |
| 시작 `streaming` · 화면 이동 abort 시 `interrupted`(error 없음) | [useChat.ts](../../../src/shared/chat/useChat.ts) |
| `done` 에서 `complete`(현재 턴만) | [chatEventHandler.ts](../../../src/shared/chat/chatEventHandler.ts) |
| 복원 정규화 `streaming` → `interrupted` | [chatPersistence.ts](../../../src/shared/chat/chatPersistence.ts) `normalizeRestoredMessages` |
| 살아 있는 턴이면 복원 건너뜀(StrictMode 재마운트 · 카드 조회 중 복귀) | [useChatPersistence.ts](../../../src/shared/chat/useChatPersistence.ts) |
| 상태 줄 "응답이 중단됐어요"(`role="status"`, 실패 스타일·재시도 없음) | [MessageList.tsx](../../../src/shared/chat/MessageList.tsx) |

정책 조건 유지: 화면 이동을 네트워크 실패로 다루지 않음(P-a) · 자동 재전송 없음 · 새 대화의 초기화 그대로 · 판매자 승인·잠금 정책 무변경.

### C3 테스트의 P-b 보강

P-b 판정("부분 답변이 보이면 같은 화면에 중단 표시가 하나 이상")의 **의미는 그대로**, 인식 대상에 `role="status"` 의 "응답이 중단됐어요" 를 **추가**했다.
수정 전 판정은 기존 실패 문구와 재시도 버튼만 셌기 때문에, 제품을 고쳐도 RED 가 유지됐다(예상대로 확인).

### 실제 해결 원인 — 복원 정규화

판단 근거:
- 정규화만 끈 조건에서 RED 4/4, 다른 B안 변경은 그대로였다
- 그 조건의 저장값은 이동 전 · `/home` · 복귀 후 · 새로고침 후 **모두 `streaming`** 이었다
- 화면 이동 abort 의 `interrupted` 전이는 **메모리에서만** 일어났다 — 저장 구독(`useChatPersistence`)이 채팅 화면 언마운트와 함께 해제된 뒤, 한 틱 미뤄진 abort 가 실행되기 때문이다
  (B안 적용 상태의 관찰에서도 `/home` 시점 저장값은 `streaming` 이었다)
- 복귀하면 복원이 저장값으로 메모리를 덮어쓰므로, 브라우저 C3 경로를 실제로 지키는 것은 **복원 시점의 판정**이다

abort 전이는 Vitest(`[S4]`)로 확인되지만 이 브라우저 경로에서는 결과를 좌우하지 않는다. 저장 시점(페이지 해제·언마운트 직후)에 기대지 않고 **복원 시점에 판정**한다는 B안의 설계 의도가 실험으로 뒷받침됐다.
