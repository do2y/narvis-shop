# T2-C2c · `done` 뒤 추천 카드 조회 중 새로고침

> 2026-11-10 · 테스트 [e2e/c2c-reload-during-card-fetch.spec.ts](../../../e2e/c2c-reload-during-card-fetch.spec.ts) · 제품 코드 변경 없음 · **관찰 테스트(회귀 계약 아님)**

## 결론

- **C2 후속 분석의 가설("카드 조회 실패 안내가 해제 중 덧붙어 저장된다")은 재현되지 않았다**(0/10)
- 대신 다음을 관찰했다(10/10): 새로고침으로 카드 조회가 끊기면, 복원된 화면에 **새 답변 + 이전 턴의 카드**가 **안내 없이** 함께 보인다.
  같은 상황이 세션 안에서 일어나면(CH-5 실패) 앱은 "이전 결과를 그대로 두었어요"를 덧붙이는데, 새로고침 경로에서는 그 안내가 없다
- 이 구간의 기대 표시는 정책으로 정해지지 않았다 — **결함으로 확정하지 않는다.** C3 개선(B안)에서 "완료 시점"을 정할 근거로 쓴다
- 안전 조건은 지켜졌다: 자동 재전송 없음 · 새로고침 뒤 CH-5 재조회 없음 · 늦게 온 이전 응답이 화면을 바꾸지 않음 · 입력 가능

## 목적 — 두 완료 시점 구분

| 시점 | 현재 코드에서 일어나는 일 |
|---|---|
| ① SSE `done` 수신 | 진행 표시 정리 · `onDone`. **턴은 끝나지 않는다** — `run` 이 `turn.settle()`(CH-5 조회 대기)을 기다린다 |
| ② 카드 조회·화면 반영 완료 | `pushResult` 로 카드 반영(또는 실패 안내 덧붙임) → `finally` 의 `endTurn` 으로 응답 중 상태 해제 |

①과 ② 사이에 새로고침하면 무엇이 남는지가 질문이다.

## 절차

B1 하네스 방식(테스트 백엔드가 CH-5 응답을 붙잡음)과 C2 방식(새 문서 시작 순간의 저장값 포착)을 재사용했다. 하네스 변경 없음.

1. 턴1: 답변 → `products.ready{A}` → `done` → 카드 A 표시 → 턴 종료(전송 가능)
2. 턴2: 진행(`publishing`) → 답변 → `products.ready{B}` → `done`. **CH-5 B 는 서버에 도착한 채 붙잡힘**
3. 재현 전제 확인: 답변 B 표시 · 전송 잠김(턴이 카드 조회를 기다리는 중)
4. 새로고침 → 복원된 질문이 보일 때까지 대기 → 관찰
5. 붙잡아 둔 CH-5 B 응답을 풀어 정리 → 다시 관찰

## 해석

| 관찰 | 근거 · 해석 |
|---|---|
| 해제 중 카드 실패 안내가 저장되지 않음 | CH-5 는 axios(XHR) 경로이고 실패는 `.catch(() => null)` 뒤 안내를 덧붙인다(코드). 그 처리가 해제 전에 실행되지 않은 것으로 보인다 — **원인 미확인**(가설). C2 에서 SSE fetch 의 reject 처리가 해제 전에 매번 실행된 것과 대비된다 |
| 답변 B 는 "완료"로 복원 | `done` 까지 받은 답변 텍스트는 완성본이다. 이 구간에서 불완전한 것은 **카드**이지 답변 텍스트가 아니다 |
| 새 답변 + 이전 카드 · 안내 없음 | 세션 안의 CH-5 실패는 "이전 결과를 그대로 두었어요" 로 알린다(명세 CH-5: 오류 화면 대신 가진 카드 유지). 새로고침 경로는 그 안내를 남길 기회가 없다 — **답변이 말하는 카드와 보이는 카드가 다를 수 있다** |

해제 중 비동기 처리가 경로마다(SSE fetch reject / XHR 실패) 다르게 끝났다는 점은, 해제 타이밍에 기대는 저장(C2)이 일반화될 수 없다는 근거를 하나 더 보탠다.

## C3 개선(B안)에 주는 시사점

- **답변 텍스트의 완료 시점은 `done`** 으로 보는 것이 맞다 — `done` 뒤에 끊겨도 텍스트는 완성본이다
- **카드의 완료 여부는 메시지 상태와 별개**로 다뤄야 한다 — 카드 조회 중 끊긴 상태를 메시지 하나의 "완료/중단"으로 표현하면, 완성된 답변을 "중단"으로 잘못 표시하거나(과잉) 카드 누락을 숨긴다(과소)
- 상세 설계는 후속 보고(B안 제안) 참조

## 검증 한계

- Chromium 헤드리스 · `next start` · 데스크톱. 다른 브라우저 미검증
- 카드 목록 1개(`listIds` 1개) · 턴1 카드가 있는 경우만. 첫 턴(이전 카드 없음 · 인기상품 시딩)에서의 새로고침 미검증
- 해제 중 XHR 실패 처리의 실행 여부를 직접 계측하지 않았다(가설)
- 앱 안 화면 이동(C3 경로)으로 이 구간을 끊는 경우는 미검증
