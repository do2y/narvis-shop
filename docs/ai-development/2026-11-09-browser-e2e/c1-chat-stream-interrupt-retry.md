# T2-C1 · 일반 채팅 스트림 도중 끊김과 수동 재시도

> 2026-11-10 · 테스트 [e2e/c1-chat-stream-interrupt-retry.spec.ts](../../../e2e/c1-chat-stream-interrupt-retry.spec.ts) · 제품 코드 변경 없음

## 결론

- **회귀 테스트(reset · clean 두 조건).** 스트림이 도중에 끊기면 **자동 재시도 없이** 실패를 안내하고, 사용자가 "다시 시도"하면
  **같은 질문을 같은 방(threadId)·같은 접속(sessionId)으로 한 번** 보낸다. 실패 턴은 정리되고 질문 말풍선은 중복되지 않으며, 새 답변으로 정상 복구된다 — T1 정책과 일치
- 결함 주입 MC1~MC5 를 각 1회 주입해 **모두 단언 실패로 탐지**했다(실행 경로가 있는 조건에서만 집계). 주입 결함은 현재 제품의 결함이 아니다
- 두 조건의 **오류 문구가 다르다** — 현재 구현의 관찰값으로 기록하며 장기 정책으로 확정하지 않는다
- 요청이 서버에 닿은 뒤의 실패라, 수동 재시도는 서버가 이미 실행한 작업을 다시 요청할 수 있다(I-2) — **서버 측 실행은 확인하지 않았다**

## 원래 C1 정의와 검증 범위

Phase 1 정의: "일반 질문 스트림이 **중간에** 끊긴 뒤 재시도" — 위험은 오분류·다른 질문 재전송, 확인은 오류 문구와 "재시도 시 같은 질문 1회", 비고 "문구 분기 관찰 필요".
그래서 스트림 도중 끊김을 끊는 방식 두 가지로 나눴다.

| 조건 | 서버 동작 | 브라우저 |
|---|---|---|
| **reset** | 200 헤더 + 진행·토큰 2개 뒤 **소켓 강제 종료** | `net::ERR_INCOMPLETE_CHUNKED_ENCODING` |
| **clean** | 200 헤더 + 진행·토큰 2개 뒤 **`done`/`error` 없이 정상 종료** | 네트워크 실패 없음 |

**응답 헤더 전 끊김(C1a)은 원래 정의 밖이라 다루지 않았다**(개발자 결정).

### 정책(T1)과 구현

| 항목 | 정책 | 구현 |
|---|---|---|
| 자동 재시도 | 금지(중복 담기 방지) — 재시도는 버튼으로만 | 일반 발화의 자동 재요청은 **스트림 시작 401** 하나뿐. 네트워크 끊김은 별개 정책 |
| 재시도 | 마지막 실패 (user, assistant) 쌍을 지우고 같은 발화를 다시 보낸다(B1~B4) | `canRetry` → `dropLastExchange` → `send(text)` |
| 분류 | done/error 없는 종료 → "중간에 끊겼어요" | 소켓 끊김은 `TypeError` → 기본 분기 |

## 실제 HTTP/SSE 사건 순서 (단언)

```
사용자 전송 → 서버 SSE 수신#1 → 화면 부분 답변 → 서버 끊음(reset) / done 없이 종료(clean)
 → 화면 실패 안내 → 사용자 "다시 시도" → 서버 SSE 수신(재시도) → 화면 새 답변 → 다음 메시지 전송
```

| 항목 (20회, 매번 같음) | reset | clean |
|---|---|---|
| 실패 시점 앱 fetch | 1 | 1 |
| 실패 시점 서버 수신 | 1 | 1 |
| 수신별 소켓 내 순번(첫 / 재시도 / 다음) | 1 / **0** / 1 — 끊긴 소켓 대신 새 소켓 | 1 / 2 / 3 — 같은 소켓 재사용 |
| 재시도 때 세션·티켓 추가 발급 | 0 (25초 캐시) | 0 |

두 조건 모두 응답 헤더를 받은 뒤의 끊김이라 D1a 같은 브라우저 계층 재전송은 관찰되지 않았다. 서버 수신 횟수는 관찰값이다(단언은 앱 fetch 로).

## 핵심 회귀 계약 (단언)

| 계약 | 확인 |
|---|---|
| **자동 재시도 없음** | 실패 안내 시점 앱 fetch 1 · 사용자 재시도 전 추가 요청 없음(사건 순서) |
| **수동 재시도는 같은 질문 · 같은 방** | 재시도 요청의 `message` · `threadId` · `sessionId` 가 첫 요청과 같다 · 클릭 1회에 fetch 1회 |
| **실패 턴 정리 · 중복 말풍선 없음** | 재시도 직후 실패 안내 사라짐 · 질문 말풍선 1개 유지 |
| **정상 복구** | 새 답변 표시 · 다시 시도 없음 · 저장소 `[질문, 새 답변]`(error 없음) · 전체 앱 fetch 2 · 이후 새 메시지 전송 가능 |
| 실패를 성공처럼 보이지 않음 | 실패 안내 표시 · 부분 문구가 일반 답변 말풍선으로 없음 · 타이핑 표시 없음 · 다시 시도 1 |
| 실패 뒤 입력 | 막히지 않음 |

### 동기화 — 고정 대기 없음

앱이 자동 재요청을 한다면 그 요청은 실패 안내(바깥 catch) **이전**에 나간다. 그래서 끊은 뒤 "실패 안내 표시"와 "서버에 처리하지 않은 요청 도착" 중
먼저 오는 쪽을 기다리고, 추가 요청이 오면 같은 방식으로 끊고 `server:extra-request-before-user-retry` 로 기록한다. 요청 수는 **소비하지 않고 센다**
(`nextStream()` 을 경쟁에 걸면 남은 대기자가 수동 재시도 요청을 가로챈다). 사건 순서 단언에 이 항목이 없어야 한다.
이 계측은 결함 주입 MC4 에서 재전송 요청이 매달려 "안내가 안 뜸"이라는 간접 증상으로만 드러나지 않게 하려고 넣었다(기존 단언 제거 없음).

## 부분 응답의 화면 · 저장소 상태

| 시점 | 화면 | 저장소(`chat:session`) |
|---|---|---|
| 실패 직후 | 실패 안내만 — 부분 문구 **안 보임** | 마지막 assistant 에 부분 문구 + `error` |
| 재시도 성공 뒤 | 새 답변 | `[질문, 새 답변]` — 부분 문구는 실패 턴과 함께 지워짐 |

## reset 과 clean 의 문구 차이 (관찰값 — 정책 아님)

| 조건 | 현재 문구 |
|---|---|
| reset | "응답을 받지 못했어요. 다시 시도해 주세요." |
| clean | "응답 연결이 중간에 끊겼어요. 다시 시도해 주세요." |

사용자에게는 같은 "도중에 끊긴" 상황인데 끊긴 방식에 따라 문구가 갈린다(Phase 0 가설 3 확인). 둘 다 재시도 가능하고 정해진 문구 정책이 없어 결함으로 단정하지 않는다.
테스트는 현재 문구로 분기 오분류를 확인한다 — 문구 정책이 정해지면(C2 후속 D) 그 단언의 기대 문구를 함께 바꿔야 한다.

## 결함 주입 (격리 worktree, 각 1회)

스크래치패드 `git worktree`(기점 `f26c2ab` + 미커밋 C1 테스트 복사)에서만 제품 코드를 바꿨다. worktree 기준선 2/2 통과를 먼저 확인했고,
각 변이는 **타입 검사 통과를 확인한 뒤** 실행했다(빌드 오류를 탐지로 세지 않기 위해). 실행 직후 원복해 `src` diff 0 을 확인했고 worktree 는 제거했다.
**주입 결함은 현재 제품의 결함이 아니다.**

| 변이 | 원래 보호 · 변경 | 실행 경로가 있는 조건 | 결과 · 실패한 단언 | 관찰된 위험 동작 |
|---|---|---|---|---|
| **MC1** | `streamChat` — 종결 이벤트 없이 끝나면 `StreamInterruptedError`. 그 throw 제거 | clean (reset 은 read 단계에서 먼저 예외 → 통과, 비대상) | clean ✘ "실패 안내 표시" 대기 단언 | 부분 답변이 **일반 답변 말풍선으로 남고** 실패 안내·다시 시도 없음(실패 스냅샷) |
| **MC2** | `useChat` catch — 사용자 취소(AbortError)만 실패를 남기지 않음. `|| err instanceof TypeError` 추가 | reset (clean 은 `StreamInterruptedError` → 통과, 비대상) | reset ✘ "실패 안내 표시" 대기 단언 | 위와 같음 — 끊긴 답변이 완료처럼 보임 |
| **MC3** | `retry` — `dropLastExchange` 로 실패 쌍을 지운 뒤 다시 보냄. 지우지 않고 읽기만 | 둘 다 | 둘 다 ✘ 재시도 직후 "실패 안내 0" 기대, 실제 1 | 실패 턴이 남은 채 같은 질문이 새로 추가됨(질문 중복) |
| **MC4** | `useChat` 안쪽 catch — 401 이 아닌 오류는 그대로 던짐. 같은 본문으로 `streamChat` 1회 재요청 | 둘 다 | 둘 다 ✘ **"앱 fetch 1회 — 자동 재시도 없음" 기대 1, 실제 2** (약 1초) | 사건 순서: 끊김 → **사용자 재시도 전 추가 요청** → 실패 안내. 서버가 같은 질문 2회 수신 · 그 뒤에도 다시 시도 버튼이 남아 사용자가 누르면 세 번째 요청이 나갈 수 있음 |
| **MC5** | `canRetry` — 마지막 실패에만 재시도 허용. 항상 false | 둘 다 | 둘 다 ✘ "다시 시도 1" 기대, 실제 0 | 실패 뒤 복구 수단이 사라짐 |

MC1·MC2 의 탐지 단언("실패 안내 표시")은 그 보호가 지키려는 사용자 결과 자체다 — 실패 안내가 끝내 나오지 않아 실패한 것이며, 화면 상태는 실패 스냅샷으로 따로 확인했다.
MC4 는 위 계측 덕에 재전송 요청이 매달리지 않아 **횟수 단언에서 직접** 실패했다.

### 결함 주입의 한계

- 각 1회. 반복하지 않았다
- MC1 은 reset, MC2 는 clean 에서 실행 경로가 없어 그 조건의 통과는 탐지력 근거로 세지 않는다
- 재시도가 **다른 질문**을 보내는 결함(B4형)은 단일 턴 시나리오로 구분할 수 없어 주입하지 않았다 — 다중 턴 시나리오가 필요하다

## 서버 중복 실행 위험 (I-2)

두 조건 모두 요청이 **서버에 도착한 뒤**의 실패다. 수동 재시도는 같은 질문을 다시 보내므로, 서버가 첫 요청을 이미 실행했다면(예: "담아줘") 다시 실행될 수 있다.
정책상 허용되는 동작이며 기존 이슈 [I-2](../2026-10-31-chat-turn-test/07-issues.md)에 해당한다. 테스트 서버는 요청을 받고 응답할 뿐 작업을 실행하지 않으므로,
**요청이 두 번 도착한 사실과 서버 작업이 두 번 실행되는지는 별개**이며 후자는 확인하지 않았다.

## `search` 수집 이벤트 — 미검증

테스트 백엔드의 `/api/events` 에서 `search` 수집 이벤트가 **0건**으로 관찰됐다(전 실행). 수집의 전송 시점·경로를 확인하지 않았으므로
"재시도가 검색 수집을 다시 보내는가"(I-1 인접)는 **미검증**이다 — 0건을 "수집하지 않는다"로 해석하지 않는다.

## 범위 밖

- C1a — 응답 헤더 전 끊김
- SSE `error` 이벤트로 끝나는 실패, 스트림 시작 오류(4xx·5xx)
- 다중 턴에서 위쪽 실패 재시도(B4형), 이미지 첨부 발화 재시도
- 일반 발화의 401 재발급·1회 재요청(브라우저 미검증)
- Chromium 헤드리스 · loopback HTTP/1.1 · 테스트 서버 · `next start` · 데스크톱 — 다른 브라우저 · HTTP/2 · 운영 경로 미검증
