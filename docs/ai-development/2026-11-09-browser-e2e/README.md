> 앞선 과제: [T1 — 채팅 턴 오케스트레이션 테스트](../2026-10-31-chat-turn-test/README.md)

## 한 줄

T1이 jsdom에서 확인한 채팅 동작이 **실제 브라우저의 사용자 시나리오**에서도 성립하는지 검증한다.
테스트 개수가 아니라, 브라우저에서만 드러나는 장애를 재현하고 검증 범위를 분명히 남기는 것이 목표다.

**작업 성격**: NARVIS 프로젝트 종료 후 개발자가 **개인적으로** 진행한 검증이다. Claude Code 를 활용해 테스트를 설계·실행하고,
결함 주입(격리 worktree)으로 **테스트가 실제 결함을 잡는지**를 확인했다. 검증 범위·정책 기준·결함 분류·커밋은 개발자가 결정했다(1인 프로젝트, 별도 리뷰어 없음).

## 하네스 구조와 그 근거

```
Chromium ──/api/**──▶ Next(next start, 로컬 프록시) ──▶ 테스트 백엔드 127.0.0.1:4010
         ──SSE(교차 출처, Authorization)──────────────▶ 테스트 SSE 서버 127.0.0.1:임의 포트
```

- **실제 백엔드·AI 서버에는 요청하지 않는다.** `/api`는 `API_PROXY_TARGET`이 테스트 백엔드이고, 등록하지 않은
  경로는 404로 끝내며 기록한다. `MOCK_API`는 끈다 — 켜면 Next 내장 목이 세션 발급을 가로채 테스트가 조종할 수 없다
- **SSE 서버는 자동으로 응답하지 않는다.** 테스트가 프레임·정상 종료·소켓 끊김·시작 거부를 직접 정한다.
  Playwright `route.fulfill` 은 body 를 한 번에 보내(1.65.0 `string|Buffer`) 스트림 중간 상태를 만들 수 없다
- **브라우저 `route()` 가로채기를 쓰지 않는다.** 1.65.0은 가로채기가 하나라도 켜져 있으면 **모든 CORS 사전 요청을
  브라우저 안에서 허용 응답으로 대신 처리한다**(`playwright-core` `isInterceptedOptionsPreflight`).
  스모크 첫 실행에서 사전 요청이 서버에 닿지 않는 것으로 드러났고, 그래서 REST 목을 테스트 백엔드로 옮겼다(개발자 승인)
- **고정 sleep 없음.** 요청 도착은 `expect.poll`, 화면은 웹 퍼스트 단언으로 기다린다.
  `nextStream()`만 기다리면 CORS가 막힐 때 타임아웃으로 끝나 원인을 말하지 못한다(음성 대조 N1에서 확인 후 수정)

## 검증 한계 (전 시나리오 공통)

- **Chromium 헤드리스만.** Firefox·WebKit·실제 모바일 기기 미검증
- **운영은 standalone(`node server.js`), 테스트는 `next start`.** 같은 빌드 산출물이지만 `next start`는
  standalone 설정에서 경고를 낸다. 실행 방식 차이에서 오는 동작 차이는 검증하지 않았다(개발자 결정: 현 단계 유지)
- **nginx를 거치지 않는다.** 운영의 `/api`는 nginx → spring, 여기선 Next 로컬 프록시 → 테스트 백엔드
- **실제 AI 서버의 CORS 설정은 검증하지 않는다.** 확인하는 것은 "FE가 올바른 사전 요청을 보내고 허용될 때만 진행한다"까지
- 목 서버가 1회 요청을 받았다는 것은 **FE가 다시 보내지 않았다**는 근거일 뿐, 서버 멱등성의 근거가 아니다
- 테스트 백엔드 포트 4010 고정 → 직렬 실행(workers=1) 전제

## 실행

```sh
npm run test:e2e                          # 빌드 → next start → 전체 실행
npm run test:e2e -- e2e/c2-reload-mid-stream.spec.ts --repeat-each=10
```
