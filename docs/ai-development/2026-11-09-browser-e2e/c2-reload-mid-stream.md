# T2-C2 · 스트리밍 중 새로고침

> 2026-11-09 · 테스트 [e2e/c2-reload-mid-stream.spec.ts](../../../e2e/c2-reload-mid-stream.spec.ts) · 제품 코드 변경 없음

## 결론

- **초기 가설은 기각한다.** "새로고침하면 부분 답변이 오류 표시 없이 완료된 답변처럼 복원된다"는 현재 Chromium에서 **0/40** 재현
- **제품 결함으로 분류하지 않는다**(개발자 결정). 관찰된 동작 — 오류 안내 + 다시 시도 — 을 회귀 테스트로 고정한다
- **단, 이 동작은 설계된 것이 아니다.** 페이지 해제 중의 비동기 예외 처리와 저장 타이밍에 기댄다.
  다른 브라우저·강제 종료 환경에서 같다고 **일반화하지 않는다**

## 가설과 근거 (Phase 1, 코드 판독)

- `useChatPersistence`가 토큰마다 대화를 sessionStorage에 저장하지만 `isStreaming`은 저장하지 않는다
- `MessageList`는 타이핑 표시를 `isStreaming`일 때만 그린다
- → 새로고침하면 반쯤 잘린 답변이 표시 없이 남을 것이다

## 재현 절차

1. `/chat`에서 질문 전송 → SSE 서버가 `progress`와 토큰 일부만 보내고 스트림을 열어 둔다
2. 부분 응답이 **화면과 sessionStorage 양쪽에 있음**을 단언(재현 전제)
3. 새로고침 → 복원된 질문 말풍선이 보일 때까지 대기, 이전 SSE 연결이 브라우저에서 끊겼음을 서버 쪽에서 확인
4. 화면·저장소 관찰. 저장 시점은 `addInitScript`로 **새 문서가 시작되는 순간**(앱 스크립트 실행 전) 값을 포착

변형: C2a(토큰 일부 수신) · C2b(진행 표시만, 빈 말풍선).

## 관찰 결과 (Chromium 158 헤드리스, 각 20회)

| 시점 | 화면 | `chat:session` 마지막 assistant |
|---|---|---|
| 새로고침 전 | 부분 문구 · 타이핑 표시 · 오류 없음 | `{text:"…이유를 "}` 오류 없음 |
| 새 문서 시작 순간 | — | **`error:"응답을 받지 못했어요…"`, `retryable:true` 추가됨** |
| 복원 후 | **오류 안내 + 다시 시도 1개** · 부분 문구 **안 보임** · 입력 가능 · SSE 재전송 없음 | 위와 같음 |

40/40 같은 결과(C2a 20 · C2b 20).

## 원인 (코드 경로)

1. 새로고침이 진행 중인 `fetch`를 끊는다 — `reader.read()`가 **`TypeError: network error`** 로 끝난다
   (임시 프로브로 확인 후 삭제. `AbortError`가 아니다)
2. [useChat.ts](../../../src/shared/chat/useChat.ts) catch 에서 `isAbortError`·`StreamInterruptedError`가 아니므로
   기본 분기 → `failLastAssistant("응답을 받지 못했어요. 다시 시도해 주세요.")`, `retryable` 기본값 true
3. 스토어 구독([useChatPersistence.ts](../../../src/shared/chat/useChatPersistence.ts))이 이를 동기적으로
   sessionStorage에 쓴다 — **페이지 해제 전에 끝났다**
4. 복원 후 [MessageList.tsx](../../../src/shared/chat/MessageList.tsx)는 `msg.error`가 있으면 안내만 그리고 본문은 그리지 않는다

새로고침을 다루는 코드는 없다. 언마운트 정리의 주석은 "사용자가 떠난 것은 오류가 아니다"라고 하지만,
새로고침은 그 경로(AbortError)를 타지 않고 네트워크 오류로 분류된다.

## 사용자 영향

- 중단된 답변이 완료된 답변처럼 보이지 않는다 · 입력이 잠기지 않는다
- 받은 부분 답변이 화면에서 사라진다(저장소에는 남음)
- 사용자가 스스로 새로고침했는데 "응답을 받지 못했어요"로 안내된다
- 재시도는 같은 질문을 다시 보낸다. 요청은 이미 서버에 닿았으므로 서버가 그 턴을 실행했을 수 있다 —
  [I-2](../2026-10-31-chat-turn-test/07-issues.md)에 이르는 새 경로. **FE만으로는 안전성을 보장할 수 없다**

## 회귀 테스트가 지키는 약속

| # | 약속 | 단언 |
|---|---|---|
| 1 | 전제: 부분 응답이 화면·저장소에 있는 상태에서 새로고침 | 문구 표시 · 저장값 일치 · 저장값에 오류 없음 |
| 2 | 완료된 답변처럼 보이지 않음 | 부분 문구가 일반 말풍선으로 없음(C2a) · 진행 문구 없음(C2b) · 타이핑 표시 없음 · 저장된 마지막 응답이 실패 상태 |
| 3 | 중단을 알 수 있는 안내 | 안내 문구 표시 · 다시 시도 1개 |
| 4 | 입력 가능 | 글자를 넣으면 전송 활성 |
| 5 | 자동 재전송 없음 | SSE 요청 1회 · 세션·티켓 발급 횟수가 새로고침 전과 같음 |

**저장 시점은 단언하지 않는다**(진단 첨부만). 그것은 메커니즘이지 사용자 결과가 아니다 —
타이밍에 기대지 않는 방식(후속 B)으로 고치면 그 값은 달라져도 위 약속은 그대로여야 한다.

정책이 바뀌면 함께 바뀌어야 하는 단언: 부분 답변을 보존하기로 하면(후속 C) 약속 2의 "부분 문구 없음",
문구를 구분하기로 하면(후속 D) 약속 3의 안내 문구.

## 테스트 신뢰성 — 음성 대조

| 심은 고장 (테스트 측 임시 수정, 실행 후 원복·diff 확인) | 결과 |
|---|---|
| N-C2-1 새로고침 직전 `error`가 담긴 저장을 테스트가 **인위적으로** 막음(해제 중 저장이 빠진 상황을 흉내) | C2a: 단언 실패 — 부분 문구가 일반 말풍선으로 남음(기대 0, 실제 1) · C2b: 단언 실패 — 복원된 응답에 실패 표시 없음 |
| N-C2-2 약속 5 직전에 재전송 발생(다시 시도 클릭) | 10/10 단언 실패 — SSE 요청 기대 1, 실제 2 |

⚠️ **N-C2-1은 인위적 조건에서의 결과다.** 테스트가 `Storage.prototype.setItem`을 덮어써 저장을 막은 것이지,
실제 브라우저·환경에서 저장이 빠지는 것을 관찰한 것이 아니다. 이 결과가 말하는 것은 두 가지뿐이다:
(1) 테스트가 "완료처럼 보이는 복원"을 단언으로 검출한다, (2) 화면 결과가 해제 중 저장 하나에 달려 있다.
실제 환경에서 그 저장이 빠지는 경우가 있는지는 **확인하지 않았다** — 실제 Chromium 관찰은 40/40 저장 성공이다.

## 검증 한계

- Chromium 헤드리스·`next start`만. Firefox·WebKit·standalone·dev(StrictMode) 미검증
- **탭 닫기 후 복구 · 브라우저 강제 종료 · 모바일 백그라운드 종료 · bfcache 미검증** — 해제 중 저장이 보장되지 않는 환경이다
- 약속 5는 "복원 완료 + 입력 확인" 시점까지의 관찰이다. **그 뒤에 일어나는 지연 재전송은 잡지 못한다**
  (고정 대기 없이 "일어나지 않음"을 증명할 수 없다. N-C2-2는 즉시 재전송만 검출함을 보여줌)
- 목 SSE 서버는 연결이 끊긴 뒤 서버가 작업을 계속하는지를 모델링하지 않는다
- 화면 위치는 문구·역할로 찾는다 — 메시지 컨테이너 식별자(`data-testid`)가 없어 "안내가 그 턴의 말풍선에 붙었는가"는
  저장소 순서(user → assistant)로 보완했다
