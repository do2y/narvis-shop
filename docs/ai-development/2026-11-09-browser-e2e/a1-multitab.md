# T2-A1 · 멀티탭 독립성

> 2026-11-09 · 테스트 [e2e/a1-multitab.spec.ts](../../../e2e/a1-multitab.spec.ts) · 제품 코드 변경 없음

## 결론

- **opener 없이 연 두 탭**에서 sessionId 공유 · threadId 분리 · 동시 SSE 의 독립 진행 · 한 탭의 새 대화가 다른 탭
  스트리밍에 영향 없음 · 화면과 sessionStorage 격리를 확인했다 → **회귀 테스트로 분류**(개발자 결정)
- **opener 가 남는 새 창**에서는 sessionStorage 가 복사되어 원래 탭과 **같은 threadId 로 질문이 전송됐다**(10/10).
  → **잠재적 설계 결함 후보로 기록한다.** 단,
  - 현재 제품의 확인된 새 탭 경로는 `noopener` 다 — **현 사용자 경로에서 재현된 결함이 아니다**
  - 서버 측에서 대화 이력·문맥이 실제로 섞이는지는 **검증하지 않았다**(목 서버)
  - 관찰 테스트로 유지하되 **회귀 계약이 아니다** — 이 동작을 바람직한 것으로 고정하지 않는다

## 검증 목표와 설계상 보장

설계([chat.md](../../architecture/chat.md) §3 · 저장 계층):

| 값 | 저장소 | 설계상 범위 |
|---|---|---|
| sessionId(+티켓) | localStorage `jarvis:chat:session:{channel}` · 25초 | 탭 간 공유 |
| threadId | sessionStorage `jarvis:chat:thread:{channel}` | "탭마다 고유" |
| 대화 내용 | sessionStorage `chat:session` | 탭 |

chat.md는 "탭 2개를 실제로 띄운 검증은 수동"이라고 적었다 — A1이 그 자동화다.
설계 문서는 **탭 복제를 다루지 않는다**(아래 "opener 탭").

## 재현 순서 (회귀 테스트)

같은 BrowserContext 의 두 페이지 = 실제 브라우저의 두 탭(localStorage·BroadcastChannel·Web Locks 공유, sessionStorage 각자).
고정 대기 없이 SSE 서버의 요청 도착과 테스트가 보내는 프레임으로 순서를 만든다. 사건 기록을 단언했다.

```
A1 SSE 도착 → (탭 B 를 새로 엶) → B SSE 도착 → A·B 동시 스트리밍(프레임 교차)
 → A1 완료 → A 새 대화 → A2 SSE 도착 → B 완료 → A2 완료
```

## sessionId 공유 · threadId 분리의 근거

| SSE 요청 | sessionId | threadId |
|---|---|---|
| A1 | 공통 | A 탭의 첫 방 (= A 의 sessionStorage 초기값) |
| B | 공통 | A 와 다름 (= B 의 sessionStorage 값) |
| A2 (A 의 새 대화) | 공통 | A1·B 와 모두 다름 (= A 의 최종 sessionStorage 값) |

- **sessionId 공유는 값이 아니라 발급 횟수로 증명했다.** 목 백엔드는 계약(CH-1 멱등)대로 늘 같은 sessionId 를
  돌려주므로 값 비교만으로는 FE 가 공유했는지 서버가 같은 값을 줬는지 구분할 수 없다.
  전 과정의 세션 발급은 **1회** — B 는 발급하지 않고 A 가 심은 localStorage 캐시를 썼다
- B 는 열릴 때 대화 저장소가 비어 있었고, 마운트 시 자기 threadId 를 만들었다
- A 의 새 대화 뒤에도 B 의 threadId 는 바뀌지 않았다

## 두 SSE 의 동시 진행과 탭별 상태 독립성

| 시점 | 확인 |
|---|---|
| B 시작 뒤 | A 가 다음 토큰을 계속 받아 표시 · A 의 SSE 연결이 끊기지 않음(서버 측) · 두 탭 모두 전송 잠김 |
| A 완료 뒤 | B 가 다음 토큰 표시 · B 진행 문구 유지 · B 전송 잠김 유지 · B 의 SSE 유지 |
| A 새 대화 + 새 질문 뒤 | 위와 같음 |

전송 잠김은 글자를 넣은 뒤 확인했다 — 빈 입력도 버튼을 잠그므로 "응답 중"만이 잠금 사유가 되게 했다.

## 화면 · sessionStorage

- 화면: A 에 B 의 질문·답변·카드 없음 / B 에 A 의 질문(이전·새 대화)·답변·카드 없음
- `chat:session`: A = `[A 새 질문, A 새 답변]`(새 대화로 이전 대화 비워짐) / B = `[B 질문, B 답변 전체]` + B 카드.
  서로 상대 카드를 포함하지 않음

저장소 비교만으로 독립성을 주장하지 않는다 — 근거의 중심은 위 표의 SSE 유지·화면 갱신·잠김 상태다.

## 결함 주입 (격리 worktree, 각 1회)

스크래치패드 `git worktree`(기점 `2551023`)에서만 제품 코드를 바꿨다. 기준 실행 2/2 통과로 환경 정상을 먼저 확인했고,
각 주입 뒤 원복, worktree 는 제거했다. 환경 오류는 없었다.

| 주입 | 결과 |
|---|---|
| **MA** threadId 를 localStorage 에 저장(탭 간 공유) | ✘ 단언 실패. 먼저 걸린 곳은 sessionStorage 를 직접 읽는 **구현 단언**이었다. 그래서 테스트 사본에서 저장소 단언 6개를 빼고(사본 기준 실행 통과 확인) 다시 돌렸고 → **SSE 본문 단언(`B threadId ≠ A threadId`)에서 실패**. 이 실행에서 화면 단언은 전부 통과 — threadId 공유는 화면이 아니라 서버로 가는 요청에서만 드러난다 |
| **MC** 대화 저장을 localStorage 로 | ✘ 단언 실패 — B 화면에 A 의 질문이 나타남 |

**한계**: 각 1회 실행이다. 반복·다른 변이 세트는 돌리지 않았다. MA·MC 는 인위적으로 주입한 결함이며 현재 제품의 결함이 아니다.

## opener 탭의 sessionStorage 복사 (관찰 — 회귀 계약 아님)

| 생성 방식 | opener | sessionStorage | threadId | 화면 |
|---|---|---|---|---|
| 새 탭(주소 직접 입력과 같음) | — | 비어 있음 | 마운트 시 새로 만듦 | 빈 대화 |
| **제품 경로** — 카드 "상세 보기 (새 탭)", `rel="noopener noreferrer"` | 없음 | 복사 안 됨 | `/chat` 이동 시 새로 만듦 | 빈 대화 |
| **opener 가 남는 새 창**(`window.open`) | 있음 | **열릴 때 복사됨** | **A 와 같음** | A 의 대화가 보임 |

opener 탭에서 질문하자 **A 와 같은 threadId 로 SSE 요청이 나갔다**(10/10).

### 현재 제품 경로와 잠재적 위험의 구분

- **현재 경로**: 제품 코드에 `window.open` 이 없고 새 탭 링크는 `noopener` 다 → 확인된 사용자 경로에서는 재현되지 않는다
- **잠재적 위험**: 브라우저 메뉴의 "탭 복제"도 sessionStorage 를 복사하는 경로로 알려져 있으나 **Playwright 로 누를 수 없어
  직접 확인하지 않았다**(`window.open` 은 명세상 같은 복사가 일어나는 근사). 그렇게 열린 두 탭은 같은 threadId 로 각자 다른
  대화를 이어가게 된다. 서버가 그 방에서 두 흐름을 어떻게 처리하는지(이력·문맥 혼합)는 **확인하지 않았다**
- 관찰 테스트는 복사·공유 여부를 단언하지 않는다. 탭 복제 지원 정책과 threadId 충돌 방지 방식이 정해지면 기대 결과를 정의한다

## BroadcastChannel · Web Locks — 이번에 검증하지 않았다

| 구성요소 | 역할 | 이번 흐름 |
|---|---|---|
| localStorage 세션 캐시 | sessionId 를 탭 간 공유 | **실제로 작동한 공유 경로** |
| BroadcastChannel `jarvis:chat` | 발급·재발급·승계 시 다른 탭의 표시용 sessionId 동기화(`session`), 로그인 시 구 게스트 티켓 폐기(`ownership`) | B 가 열리기 전에 A 의 발급이 끝났고 그 뒤 발급이 없어 **작동하지 않음** |
| Web Locks | 여러 탭의 동시 발급을 1회로 직렬화 | 발급 경쟁이 없어 **작동하지 않음** (동시 첫 전송은 별도 후보 A4) |

## 검증 한계

- Chromium 헤드리스 · `next start` · 데스크톱 기본 크기. 탭은 같은 BrowserContext 의 페이지로 표현
- 백그라운드 탭 스로틀링·동결, 실제 "탭 복제" 메뉴, 창 간 이동 미검증
- **세션 캐시 TTL(25초) 안의 흐름만** — 만료 뒤 B 가 재발급하는 경로는 범위 밖
- 목 백엔드·목 SSE 서버 — 서버의 같은 threadId 처리, 실제 CH-1 멱등성, 세션 TTL(10분) 동작은 모델링하지 않음
- 게스트만. 로그인·승계(ownership 방송)와 판매자 채널은 범위 밖

## 하네스 픽스처 수정 (별도 커밋)

A1 관찰 중 카드 픽스처 productId 가 계약(숫자 문자열)과 달라(`a-list-p1`) 상세 라우트가 조회 없이 404 를 내는 것을 발견했다.
`chatList` 가 목록 id 에서 결정적으로 만든 숫자 문자열(FNV-1a 32비트 해시 + 두 자리 순번)을 쓰도록 고쳤다. 단언 변경 없음.

- 범위: 최대 429,496,729,599(12자리) — int64·JS 안전 정수(2^53) 범위 안. 2^53 을 넘는 실제 규모 id 의 정밀도 문제는 다루지 않는다
- 고유성: **보장되지 않는다** — 두 목록 id 의 해시가 같으면 충돌한다. 현재 픽스처 목록 id 5개
  (`e2e-list-1` · `b1-old-list` · `b1-new-list` · `a-list` · `b-list`)는 해시가 모두 달라 충돌이 없음을 계산으로 확인했다(2026-11-10)
수정 뒤 카드 링크 탭은 상세 SSR 이 `GET /api/products/{숫자}` 를 **테스트 백엔드로** 보낸다(미등록 404) — 서버 측 조회도
실제 백엔드로 새지 않는다는 근거가 하나 늘었다. 관찰값은 수정 전후 같다.
