# AI 활용 개발 기록

생성형 AI를 개발 보조 도구로 활용하면서 **AI에 어떤 작업을 맡겼고, 결과를 어떻게 검증했으며, 개발자로서 어떤 판단을 내렸는지** 기록하는 곳.

Claude Code를 활용해 기존 구현을 분석하고 테스트를 설계·실행해 왔다. 단위 테스트 검증(T1)에 이어, NARVIS 프로젝트 종료 이후에는 실제 브라우저 E2E 테스트 검증(T2)을 개인 검증 작업으로 진행하고 있다.

이 작업의 목적은 단순히 테스트 수를 늘리는 것이 아니라, **AI가 작성한 테스트가 실제 결함을 탐지하는지 확인하고, 검증 과정에서 발견한 문제와 기술적 판단의 근거를 남기는 것**이다.

AI는 코드 분석, 테스트 설계·구현, 실행 결과 정리 등을 지원한다. 개발자는 검증 범위와 기대 동작을 결정하고, 코드·테스트·실행 결과를 대조해 AI의 제안과 결론을 검토한다.

## 원칙 — 기술 내용은 복제하지 않는다

- **기술 설명의 정본은 기존 문서다.** 구조는 `architecture/`, 사고는 `troubleshooting/`, 수치는 `performance/`에 기록한다. 이 폴더에는 AI 활용 과정과 검증·판단 기록을 남기고, 기술적 세부 내용은 관련 문서로 연결한다.
- 같은 내용을 두 군데 작성하지 않는다. 한쪽만 수정되어 내용이 어긋날 수 있기 때문이다. → [claude-md-drift.md](claude-md-drift.md)
- **AI가 생성한 코드나 테스트 통과 결과를 그대로 성과로 간주하지 않는다.** 테스트가 실제 결함을 탐지하는지, 검증 조건이 적절한지, 결론이 관찰 범위를 벗어나지 않는지 확인한다.
- **확인된 사실과 가설, 미검증 사항을 구분한다.** AI의 분석도 코드·테스트·실행 결과로 확인되지 않았다면 확정하지 않는다.
- 확인하지 않은 효과(개발 시간 단축, 생산성 향상 등)를 수치로 주장하지 않는다.

## 파일 규칙

- 파일명 `YYYY-MM-DD-<주제>.md` (예: `2026-11-03-sse-parser-test.md`)
- 한 기록 = 한 작업. 여러 세션에 걸쳐도 같은 작업이면 한 파일에 이어 작성한다.
- 계획·검증 자료가 필요한 여러 단계 과제는 같은 이름의 **폴더**로 관리한다. (`YYYY-MM-DD-<주제>/README.md`가 입구)
- 관련 기술 문서 끝에 역링크 한 줄을 추가하는 것은 선택 사항이다.

## 템플릿

```md
# <작업 제목>

> 날짜 · 도구(Claude Code) · 관련 커밋/PR

## 작업 목적
- 이 작업을 시작한 이유와 검증하려는 문제

## AI에 맡긴 것
- AI에 요청한 작업과 범위
- AI가 수정하거나 결정하지 못하도록 제한한 사항

## AI가 낸 것
- 산출물 요약
- 기술적 세부 내용은 관련 문서로 링크

## 개발자가 검증한 것
- 코드·테스트·실행 결과와 대조한 내용
- AI가 틀렸거나 놓친 지점
- 가설과 실제 관찰이 달랐던 부분

## 결과와 판단
- 확인된 결과와 검증 방법
- 미검증 사항 및 후속 작업 여부
- 최종적으로 선택한 방향과 근거

## 관련 문서
- [기술 문서](../architecture/....md)
```
