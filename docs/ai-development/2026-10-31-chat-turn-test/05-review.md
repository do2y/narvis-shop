## 3. H1 분석

### 3.1 정확한 원인

`retry`는 **화면의 메시지 목록에서 요청을 거꾸로 복원**함 — "마지막 실패 말풍선 + 바로 앞 user 말풍선"을 떼어 그 user 텍스트를 다시 보냄.

```
retry()  →  dropLastExchange()          (store.ts:199-213)
              ① 마지막 assistant(실패) 제거   ← 무조건 먼저 지움
              ② 바로 앞이 user 면 제거하고 { text, imageUrls } 반환
                 아니면 null 반환
         →  null 이면 아무것도 안 함      (useChat.ts:392-397)
```

칩 제거·승인 턴은 `run(..., userText: null)`로 실행되어 **user 말풍선을 만들지 않음**([useChat.ts:196-203](../../../src/shared/chat/useChat.ts#L196-L203)).
그래서 ②에서 앞 메시지가 직전 턴의 assistant가 되어 `null` → 재전송 없이 ①의 삭제만 남음.
버튼은 `retryable`이 false가 아니면 그려지므로(기본 true, [store.ts:192](../../../src/shared/chat/store.ts#L192)) 사용자는 누를 수 있음.

**근본 원인**: 실패한 턴의 **실제 요청**(body)이 어디에도 남지 않고, 재시도가 "말풍선 = 요청"이라는 가정에 기대고 있음. 그 가정이 말풍선 없는 턴에서 깨짐.

### 3.2 요청 구조 비교

| 턴 | 진입점 | body (공통: sessionId·threadId) | user 말풍선 | 재시도가 복원하는 것 |
|---|---|---|---|---|
| 일반 발화 | `send(text, _, {imageUrls})` | `message`, `screen?`, `imageUrls?` | 있음 | text·imageUrls ✅ (`screen`은 재시도 시점 화면으로 새로 실음) |
| 칩 제거 | `removeCondition(field, value)` → `send("", [action])` | `message:""`, `conditionActions:[{op:"remove",field,value}]` | **없음** | ❌ 없음 |
| 판매자 승인 | `confirm(draftId)` | `action:"confirm"`, `draftId` (message 없음) | **없음** | ❌ 없음 |

### 3.3 사용자 화면에서 일어나는 일

| 턴 | 실패 직후 | "다시 시도" 후 |
|---|---|---|
| 칩 제거 | 칩은 이미 지워져 있음(낙관적) + 실패 말풍선 | 말풍선만 사라짐. **화면은 "칩 제거됨", 서버는 조건 그대로.** 다음 발화가 지워진 줄 아는 조건으로 검색되고, 응답의 `conditions` 이벤트가 칩을 되살림 — 사용자 입장에선 지운 칩이 돌아옴 |
| 등록 승인 (`ProductCreateCard`) | 카드가 오류 상태 + 카드 안에 **"다시 시도"** 버튼(이것도 `retry`에 연결) | 실패 말풍선이 사라지며 `streamError`가 풀려 카드가 **검토 상태로 복귀**("등록" 버튼 재노출). 재시도가 된 줄 알았는데 아무 일도 없음 — 사용자가 "등록"을 다시 눌러야 함 |
| 수정 승인 (`ProductDiffCard`) | 카드는 `settled` 전이라 "적용" 버튼 그대로 | 말풍선만 사라짐. 카드 "적용"으로는 다시 할 수 있음 |

### 3.4 기대 동작 (AI 제안 — 개발자 확정 필요)

- "다시 시도"는 **실패한 그 요청을 그대로** 다시 보냄 — 칩 제거는 같은 `conditionActions`, 승인은 같은 `draftId`
- 말풍선 없는 턴은 재시도에서도 user 말풍선을 만들지 않음
- 칩 제거 재시도에서 낙관적 제거를 **다시 적용하지 않음**(이미 지워져 있음)
- 재시도할 수 없는 경우엔 버튼을 보이지 않음 — 지금처럼 눌러도 아무 일 없는 버튼을 남기지 않음

### 3.5 중복 실행 위험 — "무조건 재전송"이 안전한가

**실패 종류별로 "서버가 처리했는지"가 다름.**

| 실패 종류 | 서버 처리 여부 | 현재 `retryable` | 근거 |
|---|---|---|---|
| 세션·티켓 확보 실패, 승계 대기, 404 만료 | **안 함** (AI 서버에 요청이 가지 않음) | 승계 대기만 false | [useChat.ts:236-237](../../../src/shared/chat/useChat.ts#L236-L237) |
| 스트림 시작 거부 (4xx/5xx 응답) | **안 함** (파이프라인 진입 전 거부) | 상태별 | `describeStreamStartError` |
| SSE `error` 이벤트 | 일부 했을 수 있음 — **서버가 `retryable`로 판단해 줌** | 서버 값 | 계약 CH-2 |
| **종결 없이 끊김** (`StreamInterruptedError`) | **불명** — 서버가 끝까지 처리하고 응답만 잘렸을 수 있음 | true (기본) | [useChat.ts:287-290](../../../src/shared/chat/useChat.ts#L287-L290) |
| **기타 네트워크 오류** | **불명** — 요청은 갔는데 응답을 못 받았을 수 있음 | true (기본) | [useChat.ts:296-298](../../../src/shared/chat/useChat.ts#L296-L298) |

**턴 종류별 재전송 안전성**

| 턴 | 서버 쪽 멱등성 | "불명" 실패 후 재전송 |
|---|---|---|
| 칩 제거 | **멱등** — `op:remove`는 없는 조건을 지워도 no-op ([chat.md](../../architecture/chat.md) §7 · 타입 주석) | 안전. 검색이 한 번 더 돌 뿐 |
| 판매자 승인 | **멱등이라고 계약에 적혀 있음** — 같은 draftId 재전송은 `already_done` "이미 처리된 승인 요청입니다 — 중복 실행하지 않았습니다"(HTTP 200) | 서버가 계약대로면 안전. ⚠️ 근거 문서가 **archive**([seller-chat-contract.md](../../archive/contracts/seller-chat-contract.md) §4.3)라 현재 서버 동작은 **확인 필요**. 또 `already_done`은 `action` 이벤트가 아니라 안내 문구라 **카드가 "등록 완료"로 바뀌지 않을 수 있음**(미확인) |
| 일반 발화 ("이거 담아줘") | **멱등 아님** | **위험 — 그리고 이건 H1과 별개로 지금도 존재함.** 현재 재시도는 끊김·네트워크 오류에서도 버튼을 주고, `dropLastExchange` 주석의 전제("실패한 턴은 서버에 닿지 않았으므로")는 이 두 경우에 성립하지 않음 ([store.ts:209-211](../../../src/shared/chat/store.ts#L209-L211)) |

**AI 의견**: H1 수정 자체는 두 턴 모두 서버 멱등(승인은 확인 필요)이라 "같은 요청 재전송"이 안전함.
반면 **일반 발화의 "불명" 실패 재전송**은 H1과 별개 문제로, 범위를 넓히지 말고 **별도 과제**로 분리할 것을 제안함. (코드 판독 결과이며 테스트·실측으로 재현하지 않았음)

**AI 추천: A.** 근거 — (1) 두 턴 모두 서버 멱등(승인은 확인 필요)이라 같은 요청 재전송이 안전함 (2) 말풍선 버튼과 등록 카드 버튼이 같은 `retry`를 쓰므로 한 곳 수정으로 둘 다 고쳐짐 (3) 저장된 대화에서도 동작함.
**결정 전 개발자가 확인할 것**: 승인 멱등(`already_done`)이 현재 AI 서버에서도 유효한지 — 유효하지 않다면 승인 턴은 **B**(원래 버튼으로)가 안전함.

### 3.8 수정 후 회귀 테스트 (A 기준 제안)

1. 칩 제거 턴 실패 → 재시도 → **같은 `conditionActions`** 재전송 · user 말풍선 없음 · 실패 말풍선 1개만 제거 · 칩 재제거(중복 적용) 없음
2. 승인 턴 실패 → 재시도 → `action:"confirm"`, **같은 `draftId`** 재전송
3. 일반 발화 재시도는 종전과 같음 (S3 유지)
4. `retryable:false` 실패(승계 대기 등)는 재시도해도 요청 없음 — 버튼이 숨겨지는 경우의 방어
5. 저장 → 복원 후에도 재시도 정보가 살아 있음 (A만 해당)
6. 재시도 정보가 **성공한 턴에는 남지 않음** — 다음 실패가 옛 요청을 재전송하지 않도록
7. 새 변이로 위 테스트 검증 (기존 15개와 **별도 집계**)

## 6. 개발자 제안 시나리오 A·B

> **시나리오 제안: 개발자** (사용자 행동을 생각하며 직접 제안) · **분석·프로브 실행: Claude Code**
> 프로브는 현재 코드의 동작을 **관찰**한 것이며 저장소 테스트가 아님. UI에서의 도달 가능성은 코드 판독으로 판단했고 브라우저로 확인하지 않음.

### A. 스트리밍 중 새 대화

**기존 테스트와 겹치는 곳**: C1(언마운트 중단) · N1(새 대화의 저장소 정리) — **진행 중 턴이 있을 때의 새 대화는 어느 테스트도 다루지 않음.**
"새 대화" 버튼은 스트리밍 중에도 비활성화되지 않음([NewChatButton.tsx](../../../src/shared/chat/NewChatButton.tsx)) → UI에서 도달 가능.

| 프로브 | 상황 | 관찰 | 판정 |
|---|---|---|---|
| A1 | 이전 턴이 **추천 카드 조회 대기 중**(R4 구간)일 때 새 대화 | 새 대화의 결과 패널에 **이전 턴의 카드가 들어옴** (`results: 0 → 1`) | **결함 재현** — 조회 promise가 턴 종료와 무관하게 스토어에 씀 |
| A2 | 이전 턴이 **세션 확보 대기 중**일 때 새 대화 → 곧바로 새 질문 | 이전 턴이 뒤늦게 끝나며 `finally`가 **새 턴의 `isStreaming`을 false로 풀어버림** → 응답 중인데 또 보낼 수 있게 됨 → 실제로 3번째 전송이 나가고, 새 턴의 답 "새 답"이 **엉뚱한 말풍선**(3번째 턴)에 붙음 | **결함 재현** — 세션 확보는 티켓 TTL(30~60초)이 지나면 매번 네트워크를 타므로 대기 구간이 실재함 |
| A3 | 이전 턴이 **토큰 수신 중**일 때 새 대화 + 새 질문 (같은 틱) | 같은 양상 — 새 턴 진행 중인데 `isStreaming` false | 재현. 단 같은 틱 조건이라 UI에선 드묾(사용자 클릭은 별도 이벤트라 그 사이 정리가 끝날 가능성이 큼) |
| — | 중단 후 **늦게 온 SSE 토큰** | A3에서 중단된 스트림의 토큰은 더 오지 않음(읽기가 AbortError로 끝남) | 이 프로브의 가짜 스트림 기준. 실제 fetch도 같다고 보지만 **브라우저 미확인** |

**공통 원인 (AI 분석)**: 턴에 "이 턴이 아직 현재 턴인가"라는 식별이 없음. 끝난 턴의 `finally`·카드 조회가 **공유 스토어를 무조건** 갱신함.
**H1과의 관계**: 별개 결함임. 다만 아래 B와 같은 뿌리(턴·대상 식별 부재)라 함께 설계하는 것이 자연스러움 → §7.

### B. 재시도 버튼 연속 클릭

**기존 테스트와 겹치는 곳**: R1은 `send`의 가드만 봄. S3는 재시도 1회만. **재시도에 대한 중복 방지는 어느 테스트도 다루지 않음.**

| 프로브 | 상황 | 관찰 | 판정 |
|---|---|---|---|
| B1 | 실패 후 `retry()` **같은 틱 2회** | 요청은 1회(가드가 막음). 그러나 **방금 재전송한 턴의 말풍선 2개가 지워짐** → 응답은 받았지만 화면엔 아무것도 없음 | 재현. 2번째 `retry`의 `dropLastExchange`가 가드보다 **먼저** 실행됨. UI에선 첫 클릭 직후 버튼이 사라져 같은 버튼 연타로는 도달 어려움 |
| B2·B3 | 재전송한 턴이 **진행 중**일 때 `retry()` | 진행 중 턴의 말풍선이 지워지고, 그 턴의 토큰이 **이전 성공 답변 뒤에 이어붙음** ("첫 답 + 늦은 토큰") | 재현. `dropLastExchange`가 "마지막이 **실패한** assistant"인지 확인하지 않고 role만 봄 ([store.ts:203](../../../src/shared/chat/store.ts#L203)) |
| **B4** | 실패한 질문 뒤에 **성공한 질문**이 있을 때, 위쪽 실패 말풍선의 "다시 시도"를 누름 | **누른 질문이 아니라 마지막 성공 질문이 재전송**되고 그 답이 교체됨. 위쪽 실패 말풍선은 그대로 | **재현 · UI 도달 가능** — 실패 말풍선은 대화가 이어져도 버튼을 유지하고([MessageList.tsx:104](../../../src/shared/chat/MessageList.tsx#L104)), 모든 버튼이 대상 없이 같은 `retry()`를 부름. 마지막 질문이 "이거 담아줘"였다면 **성공한 담기가 한 번 더 실행됨** |

> B4는 개발자의 시나리오 B를 분석하던 AI가 "다른 위치의 재시도 버튼"으로 **확장**한 것 — 시나리오 자체는 개발자 제안, 이 변형은 AI 발견.

**공통 원인 (AI 분석)**: `retry()`가 **무엇을** 재시도하는지 모름 — 버튼이 대상을 넘기지 않고, `retry`는 "마지막 교환"을 대상으로 가정하며, 그게 실패한 턴인지·진행 중인지 확인하지 않음.

## 7. H1 수정 설계안 v2 (승인 대기)

### 7.1 범위 — 무엇을 같이 고치나

H1(말풍선 없는 턴)·B1~B4(재시도 대상·중복)는 **모두 `retry()` 한 함수의 결함**이라 한 번에 고치는 것이 최소 범위임. A(새 대화 경합)는 다른 경로(`run`의 정리)라 **별도 변경으로 분리**할 것을 제안.

### 7.2 요청 유형별 재시도 안전성 — "다시 보낼 수 있다 ≠ 다시 실행해도 된다"

재시도가 안전하려면 **(실패 시 서버가 처리했는지)** 와 **(같은 요청이 두 번 처리돼도 괜찮은지)** 를 함께 봐야 함.

| | 서버 미도달 확정<br>(시작 거부·세션 실패·승계 대기·404) | 도달 여부 불명<br>(끊김·네트워크 오류) | 서버가 판단<br>(SSE `error`) |
|---|---|---|---|
| **칩 제거** (멱등) | 재전송 안전 | 재전송 안전 — 같은 조건 제거는 no-op | 서버 `retryable` |
| **판매자 승인** (멱등 *주장*) | 재전송 안전 | **근거 확인 전엔 안전하다고 보지 않음** (7.3) | 서버 `retryable` |
| **일반 발화** (멱등 아님) | 재전송 안전 | **위험** — 담기 등이 이미 실행됐을 수 있음. **현재 코드도 재시도 허용** | 서버 `retryable` |

### 7.3 판매자 승인 멱등성 — 현재 근거

| 근거 | 내용 | 신뢰도 |
|---|---|---|
| [archive/contracts/seller-chat-contract.md](../../archive/contracts/seller-chat-contract.md) §4.3 | 같은 draftId 재전송 → `already_done` "이미 처리된 승인 요청입니다 — 중복 실행하지 않았습니다"(HTTP 200). 서버가 "존재→소유→멱등→TTL" 순으로 검사 | **보관 문서**. 작성 이후 서버 변경 여부 미확인 |
| FE 코드 | 멱등을 전제하는 코드·테스트 없음 | — |
| 서버 코드 | 이 저장소 밖 — **확인 안 함** | — |

추가 확인 필요: `already_done`은 `action` 이벤트가 아니라 안내 문구라, 재전송이 `already_done`으로 끝나면 **등록 카드가 "완료"로 바뀌지 않을 수 있음**(FE는 `PRODUCT_UPDATED` action으로만 카드를 확정함 — [chatEventHandler.ts](../../../src/shared/chat/chatEventHandler.ts) `action` 절).
→ **AI 제안**: 근거가 확인되기 전까지 승인 턴은 **"서버 미도달 확정" 실패에서만** 재시도 버튼을 줌. 불명 실패에선 버튼 대신 "등록 여부를 상품 목록에서 확인해 주세요" 안내.

### 7.4 일반 발화의 중복 실행

- H1과 별개로 **현재도 존재**: 끊김·네트워크 오류 후 재시도 버튼 → "이거 담아줘"가 두 번 실행될 수 있음 (코드 판독, 서버 측 재현은 안 함)
- B4는 이걸 **성공한 턴에서도** 일으킴 → 7.5의 대상 고정으로 함께 막힘
- "불명 실패에서 일반 발화 재시도를 막을지"는 UX 비용이 큼(대부분의 끊김은 무해한 질문) → **별도 과제로 분리 제안**. 서버의 액션 멱등 키 같은 협업이 필요할 수 있음

### 7.5 설계 (A안 축소판 — 최소 범위)

**저장 정보와 보안·복원**

- 남기는 것: 칩의 `field`·`value`(사용자가 고른 필터값) 또는 `draftId`(서버 발급 UUID)뿐. **body 전체를 저장하지 않음** — sessionId·threadId·티켓·화면 맥락·이미지 URL은 저장하지 않고 재시도 시점에 새로 구함(옛 sessionId는 만료됐을 수 있음)
- 이미 sessionStorage에 대화 원문이 저장되고 있어(탭 단위) 민감도 증가는 작다고 판단. 같은 오리진 스크립트는 원래 저장소 전체를 읽을 수 있으므로 새 노출면은 아님
- 복원: `loadChat`은 메시지 배열을 그대로 돌려줌([chatPersistence.ts:54-72](../../../src/shared/chat/chatPersistence.ts#L54-L72)) → 새로고침 후에도 재시도 가능. 단 **필드 형태 검증이 없음** — 깨진 값이면 재시도 시 무시하도록 좁히기(`unknown` → 타입 가드) 필요
- 복원 후 `draftId`가 TTL(10분) 만료면 서버가 "찾을 수 없음" 안내를 줄 것(계약 §4.3 `not_found`) — 중복 실행 위험은 아님
