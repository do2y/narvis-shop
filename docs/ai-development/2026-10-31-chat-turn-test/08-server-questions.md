# 판매자 승인(confirm) — 서버 계약 확인 질문과 코드 판독 결과

> 작성: 2026-11-05(Q1~Q6) · 추가: Q7(2026-11-09) · Q8~Q11(2026-11-10, 브라우저 테스트에서 같은 승인 요청의 중복 도착 관찰) · 서버 코드는 변경하지 않음
> **경위**: 질문은 서버 담당자의 회신을 전제로 작성했으나, NARVIS 프로젝트가 종료돼 **회신은 받지 않았다.** 협의할 상대가 없으므로
> 답은 개발자가 서버 레포(AI 서버 · BE) 로컬 사본을 직접 읽어 [§5 서버 코드 확인 결과](#5-서버-코드-확인-결과-2026-11-10)에 남겼다(2026-11-10) — **코드 판독이며 실행 검증이 아니다.**
> §1~§4 의 질문과 계약 제안은 작성 당시 형태(요청형 문장 포함) 그대로 둔다. 단 Q9 의 멱등 문장 1곳은 "요청 도착"과 "중복 실행"을 구분하도록 정정했다(2026-11-10).

## 1. 왜 묻는가

판매자가 초안을 승인했을 때 FE는 **그 승인이 실행됐는지 판정할 수 없습니다.** 그래서 지금은 다음과 같이 보수적으로 동작합니다.

| 상황 | 현재 FE 동작 |
|---|---|
| `PRODUCT_UPDATED`를 받음 | 성공으로 표시하지 않음. 이벤트에 `draftId`가 없어 어느 초안의 결과인지 보장되지 않음 |
| action 없이 정상 종료 | 결과 불명으로 잠금, 같은 초안 재승인 불가 |
| 요청 시작 후 HTTP 실패·연결 끊김·SSE `error` | 결과 불명으로 잠금, 자동·수동 재전송 없음 |
| 불명 이후 같은 대상의 새 초안 승인 | 경고와 2단계 확인 후 전송. **중복 실행을 막지는 못함** |

사용자에게 미치는 영향:
- 승인이 실제로 성공해도 카드에 성공이 표시되지 않고, 같은 대상의 다음 승인에서 경고가 한 번 뜹니다.
- 결과 불명 뒤 받은 새 초안을 승인하면 등록·수정·삭제가 중복될 수 있는데, FE만으로는 막을 수 없습니다.

## 2. 질문

**근거 표기**
- **FE 확인**: 현재 FE 코드에서 확인한 사실입니다.
- **과거 문서**: [계약 감사 문서](../../archive/contracts/seller-chat-contract.md)(2026-07-22, AI 서버 v0.4.0 코드 기준)의 내용입니다. **현재 서버에서 확인하지 않았으므로 사실로 간주하지 않습니다.**
- **미확인**: FE가 가진 근거가 없습니다.

### Q1. 승인 성공·실패 응답에 `draftId`를 포함할 수 있나요?

| 근거 | 내용 |
|---|---|
| FE 확인 | FE 타입의 `PRODUCT_UPDATED`·`PRODUCT_UPDATE_FAILED`에는 `message`·`productId`만 있고 `draftId`가 없음 |
| FE 확인 | 등록 초안은 `productId`가 null이라 `productId`로 초안과 결과를 연결할 수 없음 |
| 미확인 | 서버 응답에 `draftId`를 포함할 수 있는지 |

### Q2. `PRODUCT_UPDATED`가 실제로 발행되나요?

| 근거 | 내용 |
|---|---|
| FE 확인 | FE 타입에 `PRODUCT_UPDATED`·`PRODUCT_UPDATE_FAILED`가 있음 |
| 과거 문서 | 승인 성공 시퀀스는 `meta` → `token` → `done{panel:"refresh"}`이며 **action이 없음**. 감사 문서 전체에 `PRODUCT_UPDATED`가 등장하지 않음 |
| 미확인 | 현재 서버의 발행 여부 · 발행한다면 그 시점이 DB 커밋 전인지 후인지 |

| op | 성공 시 시퀀스 | 실패 시 시퀀스 | `action.type` | `action.productId` | `done.panel` |
|---|---|---|---|---|---|
| 등록 | ? | ? | ? | ? (새 상품 id가 오나요?) | ? |
| 수정 | ? | ? | ? | ? | ? |
| 삭제 | ? | ? | ? (`PRODUCT_UPDATED`로 알리나요?) | ? | ? |

함께 확인할 점:
- **실행 후 응답 실패**: 서버에서 실행이 끝난 뒤 스트림이 끊기거나 `error`로 끝날 수 있나요?
- **action 뒤 `error`**: `action` 뒤에 `error`가 올 수 있나요? 온다면 실행 결과는 유지되나요?

### Q4. `already_done`·`stale`·`expired`·`not_found`의 정확한 의미는 무엇인가요?

아래는 **과거 문서**의 내용입니다. 현재도 유효한지 항목별로 확인해 주세요.

| status | 과거 문서의 조건 | 과거 문서의 응답 | 확인할 점 |
|---|---|---|---|
| `already_done` | 이미 실행된 `draftId` 재전송 | HTTP 200 + 안내 `token` + `done{keep}` | 이전 실행의 성공이 보장되나요? 실패한 실행도 포함되나요? |
| `stale` | 승인 시점 재조회 결과가 `before`와 다르거나 상품이 없음 | 같음 | 이 요청에서는 아무것도 변경되지 않음이 보장되나요? |
| `expired` | 생성 시각 + TTL 경과 | 같음 | 같은 질문. TTL 값은 얼마인가요? 실행된 초안도 만료되면 `already_done` 대신 이 값이 오나요? |
| `not_found` | `draftId`가 없거나 소유자가 다름(같은 문구) | 같음 | 실행 후 정리된 초안도 여기에 해당하나요? |

- **FE 확인**: FE는 문구를 파싱하지 않기 때문에(프로젝트 규칙) 현재 네 경우를 구분할 수 없습니다.
- **과거 문서**: `done`에 `confirmStatus`를 싣는 안이 제안만 됐습니다(§5 D-1). 구현 여부는 **미확인**입니다.

### Q5. 승인 요청의 서버 측 멱등성이 보장되나요?

| 근거 | 내용 |
|---|---|
| 과거 문서 | 같은 `draftId` 재전송은 `already_done`으로 끝나고 중복 실행하지 않음(§4.3) |
| 미확인 | 현재 서버에서 유효한지 |

유효하다면 다음도 확인해 주세요.
- **동시 요청**: 같은 `draftId`의 요청 2개가 동시에 도착해도 1회만 실행되나요? 처리 중인 요청의 재전송에는 무엇을 응답하나요?
- **실행 도중 실패**: 일부만 반영된 상태로 끝날 수 있나요? 그 경우 재전송 응답은 무엇인가요?
- **기록 보존 기간**: 실행 기록을 언제까지 보관하나요? 기간이 지나면 `not_found`가 되나요?
- **새 `draftId`**: 같은 내용의 새 초안은 `draftId`가 달라서 이 보호를 받지 못한다고 보는 것이 맞나요?

### Q6. 중복 요청을 막는 idempotency key를 지원할 수 있나요?

| 근거 | 내용 |
|---|---|
| FE 확인 | 현재 승인 요청 본문은 `sessionId`·`threadId`·`action`·`draftId`이며 별도 키가 없음 |
| 미확인 | 지원 가능 여부 · 키 저장 위치와 보존 기간 |

Q5의 `draftId` 멱등이 유효해도 키가 도움이 되는지 판단해 주세요. FE가 가장 우려하는 경우는 **결과 불명 뒤 새 `draftId`로 같은 내용을 승인하는 것**이고, 요청 단위 키로는 이를 막지 못할 수 있습니다. 서버가 같은 내용의 중복을 판별할 방법이 있는지도 함께 알려 주세요.

### Q7. 401 뒤 티켓을 재발급하면 sessionId가 바뀔 수 있나요? (2026-11-09 추가)

판매자 승인과 별개로 **모든 채팅 요청**에 해당하는 질문입니다.

| 근거 | 내용 |
|---|---|
| FE 확인 | 스트림 시작이 401로 거부되면 FE는 티켓을 재발급받아 **1회 재요청**합니다. 재발급 응답의 `sessionId`로 스토어는 갱신하지만, 재요청 body는 **첫 발급 때 만든 것을 그대로** 씁니다([useChat.ts](../../../src/shared/chat/useChat.ts) 재발급 분기) |
| FE 확인 | 그래서 재발급이 다른 `sessionId`를 돌려주면, 재요청의 body `sessionId`(옛 값)와 새 티켓이 서로 다른 세션을 가리킬 수 있습니다 |
| 미확인 | 재발급이 `sessionId`를 바꾸는 경우가 실제로 있는지. FE 테스트 픽스처는 같은 값을 써 왔습니다(변이 D3 생존의 원인) |

1. 401 이후 티켓을 재발급할 때 `sessionId`는 항상 기존 값을 유지하나요?
2. `sessionId`가 바뀔 수 있다면, 새 티켓은 어느 `sessionId`에 귀속되나요?
3. 재요청 body의 `sessionId`와 티켓에 귀속된 `sessionId`가 다르면 서버는 어떻게 처리하나요? (거부·티켓 기준 처리·body 기준 처리 중 무엇인지)
4. 재발급 뒤 재요청할 때 FE가 body의 `sessionId`를 새 값으로 바꿔야 하나요?

**현재 판단**: 서버 계약을 확인하지 못해 **프로덕션 결함으로 확정하지 않았고, 코드도 고치지 않았습니다.** 1번 답이 "항상 유지"라면 문제가 되지 않습니다.

### 배경 — 같은 승인 요청이 서버에 두 번 도착한 관찰 (Q8~Q11, 2026-11-10 추가)

| 근거 | 내용 |
|---|---|
| FE 확인 (브라우저 테스트) | Chromium 헤드리스 · loopback HTTP/1.1 · **테스트 서버**에서, 승인 SSE 요청이 **이전 요청에 쓰던 연결**로 나간 뒤 서버가 **응답 헤더 전에** 연결을 끊으면, **같은 승인 요청(같은 `draftId`·`threadId`·본문)이 새 연결로 한 번 더 도착**했습니다(20/20). 승인이 새 연결에서 시작된 두 조건에서는 다시 도착하지 않았습니다(각 20/20) |
| FE 확인 | 세 조건 모두 FE 앱의 승인 요청은 **1회**였습니다(fetch 계측). 다시 도착한 요청은 FE 코드 아래의 브라우저 계층에서 나간 것으로, FE가 감지하거나 막을 수 없습니다 |
| 미확인 | 브라우저 내부의 정확한 재전송 조건(소스 수준) · 운영 경로(TLS · HTTP/2 여부 · ALB · nginx)에서도 생기는지 · Firefox·WebKit |

**서버가 요청을 받았다는 사실은 처리 결과를 말해 주지 않습니다.** 테스트 서버는 승인을 처리하지 않으므로, 위 관찰은 "같은 승인이 두 번 도착할 수 있다"까지이고 "두 번 실행된다"는 확인하지 않았습니다.
기록: [T2-D1](../2026-11-09-browser-e2e/d1-seller-approval-disconnect.md)

### Q8. 같은 `draftId`의 승인 요청이 중복 또는 동시에 도착하면 실제 작업을 한 번만 적용하나요?

Q5의 구체적 경로입니다. 아래 경우마다 **실제 등록·수정·삭제가 몇 번 적용되는지**와 **두 번째 요청에 무엇을 응답하는지** 알려 주세요.

| 경우 | 설명 |
|---|---|
| (a) 동시 | 첫 요청을 처리하는 도중에 두 번째가 도착함 |
| (b) 응답 유실 뒤 | 첫 요청의 연결은 끊겼지만 서버가 처리를 끝까지 진행했고, 그 뒤 두 번째가 도착함 |
| (c) 처리 전 실패 뒤 | 첫 요청이 아무것도 바꾸지 않고 실패한 뒤 두 번째가 도착함 |

### Q9. `draftId`가 멱등성 키로 쓰이나요? 그렇다면 범위·수명·원자성은 어떻게 되나요?

Q6의 연장입니다. 브라우저 계층의 재전송은 본문이 완전히 같으므로, `draftId` 단위 멱등이 유효하다면 두 번째로 도착한 요청이 **중복 실행으로 이어지지 않을 것**입니다. 요청이 두 번 **도착**하는 것 자체는 멱등으로 막을 수 없습니다.

1. 중복 방지가 **어느 계층**(AI 서버 · BE · DB 제약)에서 이뤄지나요?
2. 키의 **범위**는 무엇인가요? (세션 · 판매자/브랜드 · 전역)
3. **수명**은 얼마인가요? 처리 기록을 언제까지 보관하고, 그 뒤 같은 `draftId`가 오면 무엇을 응답하나요?
4. 중복 판정과 실행이 **원자적**인가요? (a)처럼 동시에 도착한 두 요청이 모두 "처음"으로 판정될 수 있나요?
5. `draftId`와 별개의 멱등성 키(요청 헤더 등)가 필요하다고 보시나요?

### Q10. 첫 요청이 성공했는데 응답이 유실되면 결과를 조회하거나 복구할 수 있나요?

§3의 "`draftId`로 승인 결과를 조회하는 API" 요청을 다시 드립니다. 현재 FE는 이 경우 **"처리 불명" 안내로 끝나고, 판매자가 상품 목록에서 직접 확인**해야 합니다.

- 조회가 가능하다면 어떤 상태(실행됨 · 이전 요청으로 이미 실행됨 · 실패 · 처리 중)를 구분해 돌려줄 수 있나요?
- 조회가 어렵다면, 같은 `draftId`로 다시 승인했을 때 Q5의 `already_done`처럼 **결과를 알려 주는 응답**을 보장할 수 있나요?

### Q11. 운영 경로의 프록시·로드밸런서·서버 재시도 정책은 어떻게 구성돼 있나요?

1. ALB와 nginx의 업스트림 재시도(예: `proxy_next_upstream`)가 **비멱등 POST인 승인 SSE 요청**에도 적용되나요?
2. AI 서버 앞단의 **유휴 연결 타임아웃(keep-alive timeout)** 은 얼마인가요? 브라우저가 연결을 재사용하는 시점과 겹치면 위 배경의 조건이 생길 수 있습니다.
3. 운영 SSE 경로는 HTTP/1.1인가요, HTTP/2인가요?
4. AI 서버 내부에서 실패 시 재시도하는 구간이 있나요?

**현재 판단**: 서버 측 멱등성 · 결과 조회 · 재시도 설정은 모두 **미검증**입니다. FE는 앱 수준 재전송을 하지 않도록 고정했지만(T1 I-6 · T2-D1), 브라우저·중간 장비 계층의 중복 도착은 서버 쪽 보장 없이는 막을 수 없습니다.

### 참고: 패널 동작 확인

승인 질문과 별개로, 초안 카드 표시와 관련해 다음 두 가지를 확인해 주세요.
- **`done{keep}`의 의미**: **과거 문서**는 "우측 그대로"라고 정의하지만, **FE 확인** 결과 현재 FE는 목록으로 복귀시킵니다. 어느 쪽이 현재 의도인가요?
- **`draft`와 `done`의 전송**: 한 번에 flush되나요, 나뉘어 오나요? 초안이 `keep`이나 `refresh`와 같은 턴에 올 수 있나요?

## 3. FE가 기대하는 최소 응답 계약 (제안)

필드 이름과 위치는 협의할 수 있습니다. FE에 필요한 것은 **이 승인 요청의 결과를 초안 단위로 판정할 수 있는 정보**입니다.

```jsonc
// 승인 턴의 종료 프레임 — action 대신 done 에 실어도 무방
{
  "type": "done",
  "data": {
    "finishReason": "stop",
    "panel": "refresh",
    "confirm": {
      "draftId": "a3f1c2d4-…",  // 필수: 요청한 초안
      "status": "executed",     // 필수: 아래 표의 값
      "productId": "101"        // executed 면 필수: 등록은 새 상품 id, 등록·수정·삭제 모두 대상 상품
    }
  }
}
```

| `status` | 서버가 보장할 내용 | FE 동작 |
|---|---|---|
| `executed` | 이 요청으로 실행이 끝났고 커밋됨 | 카드에 성공 표시, 미해결 기록 해제 |
| `already_done` | 이전 요청으로 **성공 실행**이 끝남 | 위와 같음 |
| `stale` · `expired` · `not_found` · 실행 실패 | 이 요청으로 **아무것도 변경되지 않음** | 실패 안내, 같은 초안 잠금, 새 초안에 경고 없음 |

추가로 필요한 보장:
1. **순서**: `confirm` 결과는 커밋 후에 보냅니다.
2. **결과 없는 종료**: `confirm` 결과 없이 끝나거나 끊긴 턴은 FE가 계속 결과 불명으로 처리합니다. 이 경로를 복구할 수 있도록 **`draftId`로 승인 결과를 조회하는 API**가 가능한지도 알려 주세요.
3. **문구**: `message`와 `token`은 표시 전용으로 둡니다. 판정은 `status`로만 합니다.

위 계약이 지원되면 FE의 "성공 미표시"와 "실제 성공 뒤 경고" 문제는 해소됩니다. 결과 조회까지 가능하면 결과 불명 상태도 복구할 수 있습니다.

### 5.2 질문별 답

**Q1. 응답에 `draftId`** — 없습니다(서버 코드). confirm 응답은 `meta{lane:"confirm"}` → `token` → `done{finishReason,panel}`뿐입니다. 다만 서버 내부 `ConfirmOutcome.status`가 이미 6종(`executed`·`stale`·`already_done`·`not_found`·`expired`·`unknown`)을 구분하므로, §3 계약은 이 값을 `done`에 싣는 것으로 구현할 수 있습니다(판독 추론).

**Q2. `PRODUCT_UPDATED` 발행** — 하지 않습니다(서버 코드). AI 서버 `app/`과 `docs/api-spec.md` 어디에도 없습니다. 판매자 스트림 이벤트는 `meta/token/progress/draft/report/done/error`이고 `action`이 없습니다. FE 타입의 판매자 action 2종은 서버가 보내지 않는 값입니다.

**Q3. op별 시퀀스** — 등록·수정·삭제·발송(ship) 모두 같습니다(서버 코드: `_confirm_stream`).

| 결과 | 시퀀스 | `action` | 상품 id |
|---|---|---|---|
| `executed` | `meta` → `token` → `done{refresh}` | 없음 | 수정만 문구에 "(상품 ID N)". 등록은 새 id 없음 |
| `stale` · `expired` · `not_found` · `already_done` · `unknown` | `meta` → `token` → `done{keep}` | 없음 | 없음 |

- **action 뒤 `error`**: action이 없으므로 해당 없습니다.

**Q4. 상태 의미** — 판정 순서는 `not_found` → `already_done` → `expired` → 실행입니다(서버 코드: `confirm_draft`).

| status | 현재 조건 | 이 요청으로 변경 없음? |
|---|---|---|
| `not_found` | 초안 없음 · sellerId/brandId 불일치 · 수정 턴에서 무효화(`cancelled`). 실행된 초안도 checkpoint 정리(마지막 활동 후 `seller_draft_retention_hours` 48시간) 뒤에는 여기 해당 | 예 |
| `already_done` | ① 실행 기록(`result`)이 있는 초안의 재승인 — **이전 결과가 `stale`이어도 해당**하며 이전 문구가 함께 옴 ② 이미 삭제된 상품 삭제 ③ 이미 발송된 주문(409) ④ 바뀐 값이 없는 수정 | 예. 단 **이전 실행의 성공을 보장하지 않음** |
| `expired` | 생성 후 `seller_draft_ttl_minutes`(10분) 경과. `result` 확인 뒤에 판정하므로 실행된 초안은 TTL이 지나도 `already_done` | 예 |
| `stale` | 쓰기 전 검사(재조회 불일치·상품 미발견·카테고리 무효 등) 또는 Spring 4xx 거부 | 대체로 예. 단 그래프 결과에 outcome이 빠진 이상 상태도 `stale`로 처리하므로 100% 보장은 아님 |
| `unknown` | 이번 요청의 실행 대기가 45초 상한에 걸림. **응답은 `keep`이라 FE는 다른 실패와 구분할 수 없음** | 알 수 없음 |

`done.confirmStatus`(과거 문서 §5 D-1)는 구현되지 않았습니다(서버 코드).

**Q7. 재발급과 sessionId**

1. **항상 유지됩니다**(서버 코드: BE `ChatSessionService.reissueTicket`). 받은 sessionId로 티켓만 다시 만들고, 세션이 만료됐으면 새로 만들지 않고 404 `SESSION_NOT_FOUND`를 줍니다. FE `refreshTicket`도 이 API(`POST /api/chat/tickets`)만 부릅니다.
2. 해당 없음.
3. 구매자: body와 티켓 클레임의 sessionId가 다르면 **403 `SESSION_FORBIDDEN`**(서버 코드: AI `app/api/deps.py` `require_buyer_session`). 판매자: 이 대조를 찾지 못했습니다. body sessionId는 대화 id로만 쓰입니다.
4. 바꿀 필요 없습니다.

→ **현재 서버 기준으로 결함이 아닙니다.** 재발급이 sessionId를 바꾸도록 서버가 변경되면 다시 검토합니다.

**Q11. 운영 경로**

1. 승인 SSE는 FE 컨테이너의 nginx를 거치지 않고 `llmSseUrl`(AI 서버)로 바로 갑니다. FE `nginx.conf`에는 AI 업스트림이 없어 `proxy_next_upstream`은 해당하지 않습니다(서버 코드·FE 확인). ALB 설정은 레포에 없어 **미확인**입니다.
2. AI 서버는 `uvicorn app.main:app --host 0.0.0.0 --port 8000`로 실행하며 `--timeout-keep-alive`를 지정하지 않습니다(서버 코드: `Dockerfile`). uvicorn 기본값(5초)이 적용될 것으로 보이나 레포에서 확인한 값은 아닙니다. ALB 유휴 타임아웃은 **미확인**입니다.
3. uvicorn은 HTTP/1.1만 제공합니다. 브라우저↔ALB 구간은 **미확인**입니다.
4. AI→Spring 쓰기는 재시도하지 않습니다. `spring_max_retries`(최대 1)는 검색·배치 조회에만 쓰입니다. confirm 흐름에도 자동 재실행이 없습니다(서버 코드).

**참고: 패널 동작**
- `done{keep}`: 명세(AI `docs/api-spec.md` §3.2)는 "유지"로 정의합니다. 현재 FE가 목록으로 복귀시키는 것은 **명세와 다릅니다**.
- `draft`와 `done`: 초안 턴은 항상 `draft` → `done{replace}` 두 프레임이고, `keep`·`refresh`와 같은 턴에 오지 않습니다(서버 코드). 두 프레임이 한 번에 flush되는지는 보장되지 않으므로 FE는 나뉘어 와도 동작해야 합니다.
