### v3 — 구현 전 재확인 (2026-10-31, A 단위 커밋 `bd07411` 이후) · 아래 v1·v2를 대체

개발자 지시(02 #15): ① 서버에서 확인 못 한 4xx는 "처리 전 거부"로 단정하지 않음 ② 판매자 승인은 **클라이언트가 요청을 시작하지 않았음이 확실한 실패**에서만 재전송 ③ I-4 포함 — 버튼 노출 조건 = 실제 재시도 가능 조건, 판매자 카드 컴포넌트 테스트.

**실패 분류 — 두 갈래로 줄임**

| 분류 | 판정 | 해당 |
|---|---|---|
| **요청 시작 전** | AI 서버로 가는 `fetch`를 **한 번도 호출하지 않았음** | 세션·티켓 확보 실패 · 승계 대기 · (발급 단계 오류) |
| **요청 시작 후** | `fetch`를 한 번이라도 호출함 — 이후 결과는 **서버 처리 여부 불명**으로 봄 | HTTP 응답이 있는 시작 거부(**4xx·5xx 전부**) · 네트워크 오류 · 끊김 · SSE `error` |

- v2의 "처리 전 거부(4xx 6종)" 분류는 **폐기** — 근거가 계약 문서뿐이라 개발자 지시 ①에 따라 단정하지 않음
- 판정 지점: `run`이 `streamChat`을 부르기 **직전**에 "요청 시작" 표시. 401 → 재발급 → 재시도 경로에서 재발급이 실패해도 첫 `fetch`가 이미 나갔으므로 "시작 후"

**요청 유형별 정책**

| 턴 | 요청 시작 전 | 요청 시작 후 |
|---|---|---|
| 판매자 승인 | 재전송 정보 저장 · 버튼 | **재전송 정보 없음 · `retryable:false` · 버튼 없음** · 안내 "요청이 처리됐는지 확인하지 못했어요. 상품 목록에서 반영 여부를 확인한 뒤 다시 진행해 주세요." (SSE `error`의 `retryable:true`도 무시 — 개발자 결정 (나)) |
| 칩 제거 | 재전송 정보 저장 · 버튼 | 재전송 정보 저장 · 버튼 — 단 `retryable:false`(403·409·429)면 없음. 근거: 조건 제거는 대화 맥락 조정이지 영속 데이터 변경이 아니고 계약상 멱등(`op:remove` no-op). ⚠️ 계약 근거라 **개발자 확인 대상** |
| 일반 발화 | 종전대로 | 종전대로 — I-2(범위 밖) |

**요청 정보 저장 구조**

```ts
// ChatMessage 에 선택 필드 1개 — 말풍선 없는 턴이 "재전송해도 되는" 실패로 끝났을 때만
resend?: { kind: "conditions"; actions: ConditionAction[] } | { kind: "confirm"; draftId: string };
```
- 담지 않는 것: sessionId·threadId·티켓·화면 맥락·이미지 — 재시도 시점에 새로 구함
- 재전송은 원래 진입점을 그대로 탐: 칩 → `send("", actions)`(수집 안 함·말풍선 없음·낙관적 제거 재적용 없음), 승인 → `confirm(draftId)`

**버튼 노출 = 재시도 가능 조건 (단일 함수 `canRetry`)**

| 조건 | 이유 |
|---|---|
| 응답 중이 아님 | E1 구간(실패 표시 + 턴 진행 중)에서 버튼이 보이던 것까지 정리 — 1단계는 훅만 막았음 |
| 대상이 마지막 메시지 · assistant · `error` 있음 · `retryable !== false` | 1단계 그대로 |
| **다시 보낼 것이 있음**: 형식이 맞는 `resend`, 또는 바로 앞이 user 발화 | H1 — 없으면 버튼을 그리지 않음 |

같은 `canRetry`를 **훅의 `retry` · `MessageList` 버튼 · 판매자 등록 카드 버튼(I-4)** 세 곳이 씀 → 노출과 실제 동작이 어긋날 수 없음.

**기존 저장 데이터 호환성**

| 저장분 | 동작 |
|---|---|
| `resend` 없는 옛 실패 말풍선(말풍선 없는 턴) | `canRetry` 거짓 → 버튼 없음 · 눌러도(호출돼도) 아무것도 안 지움 — 종전엔 말풍선만 사라짐(H1) |

### 데이터 구조

```ts
// store.ts — ChatMessage 에 선택 필드 1개
/**
 * 말풍선 없는 턴(칩 제거·판매자 승인)이 실패했을 때 **다시 보낼 최소 정보**.

 * sessionId·threadId·티켓·화면 맥락은 담지 않는다 — 재시도 시점에 새로 구한다.
 */
resend?:
  | { kind: "conditions"; actions: ConditionAction[] }
  | { kind: "confirm"; draftId: string };
```

### 실패 분류 — "서버가 처리했는가"

> ⚠️ **v1(아래 접힌 표)은 "요청을 보냈는가"와 "서버가 처리했는가"를 혼동했음** — 개발자가 이 혼동 여부를 검토하라고 요구(02 #12)해 AI가 다시 확인한 결과, HTTP 5xx를 "미도달 확정"에 넣은 것이 틀렸음.
> `504 UPSTREAM_TIMEOUT(first-token)`은 이름 그대로 **파이프라인이 시작된 뒤** 첫 토큰을 기다리다 난 타임아웃이고([chatErrors.ts](../../../src/shared/chat/chatErrors.ts) `case 504` 주석), 502·503은 ALB·nginx가 **처리 중 끊긴 업스트림**을 대신 응답한 것일 수 있음. "응답을 받았다"는 "처리하지 않았다"가 아님.

**v2 — 세 축을 분리함**

| 질문 | 판단 방법 |
|---|---|
| ① 요청이 AI 서버로 **나갔는가** | `streamChat`의 fetch 호출 직전에 표시 — 그 전 실패(세션·티켓·승계)는 "안 나감" |
| ② 서버가 **응답했는가** | `StreamStartError`(HTTP 응답 있음) vs 네트워크 오류·끊김(응답 없음/불완전) |
| ③ 그 응답이 **"처리 전 거부"라고 계약이 보장하는가** | 계약이 파이프라인 진입 전 검증으로 명시한 상태 코드만 |

| 분류 | 해당 실패 | 근거 |
|---|---|---|
| **안 나감** | 세션·티켓 확보 실패 · 승계 대기(`SessionClaimPendingError`) · 발급 단계 404 | ① 거짓 — AI 서버에 요청이 없었음 |
| **처리 전 거부** | `StreamStartError` 중 **400 · 401 · 403 · 404 · 409 · 429** | 계약상 스트림 시작 전 검증 실패(필드·티켓·권한·세션 만료·동시 스트림·요청 과다). 판매자 계약 §4.1: "`meta` 조차 못 받는다" |
| **불명** | `StreamStartError` **5xx 전부**(504 포함) · 위 목록 밖 상태 코드 · fetch 후 네트워크 오류 · 종결 없이 끊김 | 서버가 처리를 시작·완료했을 수 있음 |
| **서버 판정** | SSE `error` 이벤트 | 서버가 `retryable`을 줌 — 단 승인 턴에선 개발자 결정 (나)로 **불명과 같이 취급** |

확인 필요: 위 4xx 목록이 **현재** AI 서버에서도 "처리 전" 거부인지 — 근거가 계약 문서뿐임(판매자 계약은 archive). 확인 전까지는 목록을 넓히지 않음.

### 재시도 동작

`retry(id)`가 대상에 `resend`가 있으면 **실패 말풍선만** 지우고(user 말풍선이 없으므로) `run`을 그 정보로 다시 실행.
- 칩: `send()`를 거치지 않고 `run` 직행 — 낙관적 제거를 다시 하지 않고(이미 지워져 있음), 검색 수집도 하지 않음(S2와 일관)
- 승인: `{ action: "confirm", draftId }`
- 1단계의 가드(스트리밍 중·마지막·실패·`retryable`)를 그대로 거침 → 연타 방지

### 설계 (구현 전 작성분 — 아래는 고치지 않음)

### 원인 다시 보기

| | 지금 | 문제 |
|---|---|---|
| 새 대화 | `abort()` → `reset()` (`isStreaming:false`) → 새 방 | 중단된 턴은 **비동기로** 아직 살아 있음 |
| 이전 턴의 남은 작업 | 세션 확보 `await` 이후 · catch · `finally` · 카드 조회 `.then` | 전부 **"내가 아직 현재 턴인가"를 묻지 않고** 공유 스토어를 씀 |

`abort()`는 네트워크를 끊을 뿐, **이미 시작된 비동기 작업이 스토어에 쓰는 것을 막지 못함** — 세션 확보 `await`는 abort 신호를 받지 않고, 카드 조회 promise도 중단과 무관하게 끝남. 그래서 "abort를 더 빨리"나 "타이밍 조정"으로는 해결되지 않음.

### 설계 — 턴 id로 쓰기 권한을 묶음

```
store:   activeTurnId: string | null          (initial null, 저장하지 않음)

run():   const turnId = newId()
         setState({ activeTurnId: turnId, isStreaming: true, ... })
         const isCurrent = () => getState().activeTurnId === turnId

         ...await acquireTicket()
         if (!isCurrent()) return             ← 새 대화가 시작됐으면 여기서 멈춤(요청도 안 보냄)
         createTurnHandler({ ..., isCurrent })
         ...
catch:   if (!isCurrent()) return             ← 끝난 턴의 실패는 새 대화에 쓰지 않음
finally: if (isCurrent()) { setStreaming(false); setProgress(null); setState({activeTurnId:null}) }
         if (abortRef.current === controller) abortRef.current = null

startNewChat(): abort() → reset()           ← reset 이 activeTurnId 를 null 로 → 이전 턴의 쓰기 권한이 즉시 사라짐

chatEventHandler: onEvent 시작에서 if (!isCurrent()) return
                  카드 조회 .then 에서도 if (!isCurrent()) return
```

| 결함 | 어떻게 막히나 |
|---|---|
| A1 늦은 카드 | 카드 조회 `.then`이 `isCurrent()` 거짓 → 패널에 쓰지 않음 |
| A2 이전 `finally`가 새 턴 잠금 해제 | `finally`가 `isCurrent()` 거짓 → 새 턴의 `isStreaming`을 건드리지 않음 · 세션 확보 뒤 즉시 멈춰 요청도 안 나감 |
| A3 | A2와 같은 경로 |

**소유권을 스토어에 두는 이유** (훅 ref가 아니라): `reset()`이 이미 "새 대화 = 스토어 초기화"의 단일 지점임 → 같은 지점에서 소유권도 회수되어 **별도 동기화가 필요 없음**. 또 판매자·구매자 화면이 같은 스토어를 공유해 훅 인스턴스가 바뀌어도 일관됨.

**언마운트(C1)와의 관계**: 언마운트는 `reset()`을 부르지 않음 → 턴은 여전히 현재 턴 → `finally`가 정상적으로 `isStreaming`을 품. C1 동작 유지(테스트로 확인 예정).

### `activeTurnId` 수명 정의 (개발자 요구로 명시, 02 #12)

| 시점 | 동작 | 불변식 |
|---|---|---|
| **생성** | `run()`이 `isStreaming` 가드를 통과한 직후, **첫 `await` 전에** 새 id 발급 → `activeTurnId`·`isStreaming:true`를 **한 번의 `setState`** 로 기록 | 둘은 항상 같이 바뀜 — `isStreaming === (activeTurnId !== null)` |
| **갱신** | 턴 안에서는 바뀌지 않음. 401 티켓 재시도는 **같은 턴**(같은 id). `retry`·다음 `send`는 **새 턴**(새 id) | 한 턴의 모든 쓰기는 그 id 하나로 판정 |
| **정상 종료** | `settle()`(카드 조회) 대기 후 `finally`에서 `isCurrent()`면 `activeTurnId:null`·`isStreaming:false`·`progress:null`을 한 번에 | 카드는 턴이 현재일 때 들어옴 — R4 유지 |
| **reset (새 대화)** | `abort()` → `reset()`이 `activeTurnId:null`. 이 순간 이전 턴은 **현재가 아님** — 이후 이전 턴의 모든 쓰기 차단, 이전 턴 `finally`는 스토어를 건드리지 않음 | 새 대화의 메시지·카드·세션·로딩은 새 턴만 바꿈 |
| **언마운트** | `reset()`을 부르지 않음 → 이전 턴은 여전히 현재 → 한 틱 뒤 abort → catch(abort) → `finally`에서 정상 정리 | C1·U1 동작 유지 |
| 언마운트 후 늦은 카드 | `finally`가 먼저 `activeTurnId:null` → 그 뒤 도착한 카드 `.then`은 현재 아님 → **버림** | ⚠️ **동작 변화**: 지금은 이탈 후 늦게 온 카드가 스토어에 들어가 재진입 시 보였음. 바뀐 뒤엔 사라짐 — 개발자 확인 필요 |
| 새로고침 | `activeTurnId`는 저장 대상 아님 → `null`로 시작 | 저장 포맷 무영향 |

**`finally`에서 `abortRef` 정리**는 소유권과 별개 — `abortRef.current === controller`일 때만 비움(새 턴의 컨트롤러를 지우지 않게, A2에서 관찰된 문제).

### 서버 상태 동기화 vs 대화 UI — 개발자 결정 반영

개발자 결정(02 #12): **신뢰할 수 있는 완료 이벤트**가 확인되면 캐시 무효화는 허용, 단 이전 턴이 새 대화의 메시지·카드·세션·로딩을 바꾸면 안 됨.

## I-5 설계 v3 — 초안별 승인 상태 (2026-11-04, 위 구현 기준이 조정)

> 개발자 보완 조건(02 #20) 반영: A `closed`와 성공 구분 · B `unknown` 뒤 새 초안 경고 · C 상태 삭제 ≠ 처리 여부 확인 · D 서버 응답 의미 미검증.
> v2의 전이·유일성 범위 중 달라지지 않은 부분은 아래 v2를 따름. **프로덕션 코드 변경 없음.**

### A. action은 특정 초안의 성공을 보장하는가 — **보장하지 않음**

| 확인 | 결과 | 근거 |
|---|---|---|
| 페이로드 | `PRODUCT_UPDATED`에 `draftId` 없음 — `message`·`productId`뿐 | [action.ts](../../../src/shared/types/chat/action.ts) |
| 서버 발행 여부 | **미확인.** 감사 문서의 성공 응답은 `token` + `done{refresh}`로 action 언급이 없음. 등록 카드 주석은 "등록된 productId가 응답에 없다"인데 타입은 `productId` 필수 — 서로 어긋남 | 감사 문서 §C · [ProductCreateCard.tsx](../../../src/features/seller/components/ProductCreateCard.tsx) |
| 현재 매칭 | `productId` 일치 → 없으면 **아무 등록 초안**으로 대체 → 거짓 성공 재현(P4·P6) | [probe-round4-action.json](probes/probe-round4-action.json) |

**v3 판정 규칙 — 카드를 성공으로 표시하는 조건** (셋 다 충족)

1. `PRODUCT_UPDATED`가 **그 `draftId`로 보낸 승인 요청의 스트림**에서 왔고 그 턴이 아직 현재 턴임 (요청 1개 = 스트림 1개라는 전송 수준의 대응)
2. 수정·삭제 초안: `action.productId === draft.productId`
3. 등록 초안: 비교할 id가 없어 1번 대응에만 기댐 — **가장 약한 근거**임을 기록

그 밖의 action(일반 턴, `productId` 불일치)은 카드를 바꾸지 않음. 승인 턴에서 불일치면 `closed`.
기술적으로 확실해지려면 **서버가 action에 `draftId`를 실어야 함** — 서버 협의 사항.

### D. 상태 — 성공 여부와 재승인 가능 여부를 분리

| 상태 | 성공으로 표시 | 같은 초안 재승인 | 뜻 — FE가 **아는 것** | FE가 모르는 것 |
|---|---|---|---|---|
| 없음 | — | 가능 | 승인 전, 또는 요청을 내보내기 전 실패 | |
| `pending` | 아니오 | 불가(진행 중) | 이 초안의 승인 턴 진행 중 | |
| `settled` | **예** | 불가 | 위 판정 규칙을 통과한 서버 성공 이벤트를 받음 | 서버 이벤트 자체의 정확성 |
| `rejected` | 아니오 | 불가 | 서버가 실패 이벤트(`PRODUCT_UPDATE_FAILED`)를 보냄 | 부분 반영 여부 |
| `unknown` | 아니오 | 불가 | 요청을 내보낸 뒤 실패 | **실행 여부** |
| `closed` | **아니오** | 불가 | 서버가 판정 가능한 action 없이 응답을 끝냄 | **실행 여부 — 성공도 실패도 아님** |

- 지금 `settled`는 실패 action도 담음 → **성공 전용으로 좁히고** 실패는 `rejected`로 분리
- `done{refresh}`는 목록 재조회 신호로만 씀. **성공 판정에 쓰지 않음**
- `already_done`·`stale`·`expired`·`not_found`: 과거 감사 문서상의 의미일 뿐 **현재 서버 미검증** · 문구 파싱 금지 → 구분하지 않고 모두 `closed`. "다시 눌러도 소용없다"가 아니라 **"실행 여부를 모르니 같은 초안으로 다시 실행하지 않는다"**로 판단(v2 표의 "다시 눌러 성공? 아니오"는 감사 문서 기준 서술로 격하)

### 사례별 상태 전이표 (개발자 확인 요청 8건)

| # | 사례 | 전이 | 말풍선 | 카드 | 미해결 기록(B) |
|---|---|---|---|---|---|
| 1a | 등록 승인 + 성공 action | `pending → settled` | 서버 문구 | 성공 표시 · 상품 목록 링크 | 없음 |
| 1b | 수정·삭제 승인 + `productId` 일치 성공 action | `pending → settled` | 서버 문구 | 성공 표시 | 없음 |
| 1c | 수정·삭제 승인 + `productId` 불일치 action | `pending → closed` | 서버 문구 | 성공 아님 | 남김 |
| 1d | 성공 action 뒤 `error` (P7) | `settled` 유지 | 서버 오류 문구 · 버튼 없음. **"확인하지 못했어요"로 덮지 않음** | 성공 표시 | 없음 |
| 1e | 실패 action | `pending → rejected` | 서버 문구 | 실패 표시 · 초안 닫기 | 없음 |
| 2 | **요청 시작 전 실패** (티켓 확보 실패·승계 대기) | `pending → 없음` | 실패 · 다시 시도(승계 대기 제외) | 승인 버튼 유지 | 없음 |
| 3 | **요청 시작 후 실패** (401·4xx·5xx·끊김·네트워크·SSE `error`) | `pending → unknown` | 확인 안내 · 버튼 없음 | 승인 버튼 없음 · 안내 · 목록 링크 · 초안 닫기 | 남김 |
| 4 | **action 없는 정상 종료** (`keep`·`refresh`·패널 없음) | `pending → closed` | 서버 문구 그대로 | 승인 버튼 없음 · **성공 표시 없음** · 안내 · 목록 링크 · 초안 닫기 | 남김 |
| 5 | **승인 중 새 대화** | 초안 삭제. 버려진 턴은 소유권 확인에서 상태·메시지·카드를 못 씀. 늦게 온 장바구니·찜 외 action은 무시 | 새 대화에 표시 없음 | 없음 | `pending`을 남김. 단 그 턴이 **요청을 내보내기 전에 멈췄으면 지움** |
| 6 | **`unknown` 상태에서 새 초안 생성** | 새 `draftId` → 상태 없음 → 이전 초안은 교체돼 사라짐 | — | 승인 가능하되 **경고 + 2단계 확인**(아래 B) | 유지 |
| 7 | **다른 `draftId` 승인** | A 진행 중 B 승인 → `isStreaming` 가드로 거부, B는 상태 없음. A 종료 뒤 B는 독립. A 결과가 B를 바꾸지 않음(방어 시나리오 — 계약상 스트림당 초안 0~1) | — | 각자 상태 | 키가 맞으면 B에 경고 |
| 8 | **같은 `draftId` 중복 클릭** | 첫 클릭 `pending`, 렌더 전 두 번째 → `confirm`이 상태로 거부 + `run`의 `isStreaming` 가드 → **요청 1회** | 1개 | 처리 중 | — |

### B. 불명 뒤 새 초안 — 경고와 2단계 확인 (중복을 막지 **못함**)

새 초안은 **새 `draftId`** 라 서버의 `already_done`도 적용되지 않을 수 있음(미검증) → 이전 승인이 실제로 실행됐다면 중복 등록·수정·삭제 가능.

**미해결 기록** — `results`와 별도로 스토어에 `{ draftId, op, productId, label }` 목록.

| 항목 | 정책 |
|---|---|
| 남기는 때 | `unknown`·`closed` 진입 · 승인 중 새 대화·화면 이탈(요청 시작 후) |
| 경고가 뜨는 새 초안 | 등록: 미해결 등록이 있으면(같은 상품인지 판단할 id가 없음) · 수정·삭제: **같은 `productId`** |
| 초안 교체·닫기·새 대화 | 유지 — `reset`이 비우지 않게 별도 처리 |
| 지우는 때 | 사용자가 경고에서 "확인했고 승인" · **로그아웃·신원 변경** (지금 `useLogout`·`useAuthSync`는 채팅 스토어를 안 비움 → 다른 계정에 보이지 않게 구현 시 추가 필요) |
| 새로고침 | 메모리뿐이라 사라짐 → C 한계 |

**화면**: 해당 카드에 처음부터 경고문 — "이전 승인 결과를 확인하지 못했어요. 같은 내용을 다시 승인하면 중복으로 등록·수정·삭제될 수 있어요. 상품 목록에서 먼저 확인해 주세요." 승인 버튼을 누르면 바로 보내지 않고 **[상품 목록 보기] [확인했고 승인] [돌아가기]** 표시. 무관한 상품의 초안에는 경고 없음.

> ⚠️ **기술적 방지가 아님.** 사용자 확인 절차일 뿐이며 "확인했고 승인"을 누르면 그대로 나감. "확인"은 사용자의 진술이지 서버 사실이 아님. 다른 탭·새로고침 뒤에는 뜨지 않음. 실제 방지에는 서버 측 멱등 키·중복 판정이 필요함.

### C. 상태가 사라져도 처리 여부는 확인되지 않음 — 한계

| 사건 | 사라지는 것 | 남는 불확실성 |
|---|---|---|
| 초안 닫기 | 초안·`approval` (미해결 기록은 유지) | 서버에 취소를 알리지 않음 — **닫았다고 취소된 것이 아님** |
| 새 대화 | 초안·`approval` (미해결 기록은 유지) | 승인이 실행 중이거나 끝났을 수 있음 |
| 새로고침·탭 닫기 | **전부**(미해결 기록 포함) | 화면에 아무 흔적도 없지만 서버에서 실행됐을 수 있음 — **FE로는 복구 불가** |
| 다른 탭 | 공유 안 함 | 다른 탭은 경고 없음 |

## I-5 설계 v2 — 초안별 승인 상태 (2026-11-04, v3가 보완)

> 개발자 조건부 승인(02 #19): 초안별 `approval` 방향은 승인. 단 ① action 없이 끝나는 응답을 재승인 가능으로 처리하지 말 것 ② `draftId` 유일성 범위와 새로고침·취소·새 대화의 상태 전이를 정리할 것.

### v1에서 고친 점 (AI 설계 오류 포함)

| v1 | 문제 | v2 |
|---|---|---|
| "`results`는 대화와 함께 저장 → 새로고침 후 `unknown` 유지", "복원된 `pending`은 `unknown`" | **틀린 전제.** 판매자 챗은 `useChatPersistence`를 쓰지 않고 진입 때 `startNewChat()`을 부름 — 새로고침하면 초안 카드 자체가 사라짐 | 새로고침은 복원이 아니라 **초안 소멸**로 정의. 복원 테스트 삭제 |
| action 없이 정상 종료 → 잠그지 않음 | 재승인이 성공할 수 없는 응답을 다시 누르게 함 · 개발자 조건 위반 | **`closed`로 잠금** |
| 초안 2개 시나리오를 주 경로처럼 서술 | 계약상 스트림당 draft 0~1 + 턴의 첫 결과가 이전 결과를 교체 → 보통 카드는 1개 | 방어 테스트로만 유지 |

### action 없이 끝나는 승인 응답 — 계약상 의미

근거: [계약 감사 문서](../../archive/contracts/seller-chat-contract.md) §4.3 — **2026-07-22, AI 서버 v0.4.0 기준이며 현재 서버에서 확인하지 않음.**

| status | 뜻 | 실제 실행 | 다시 눌러 성공? |
|---|---|---|---|
| `not_found` | `draftId` 없음 **또는 소유 불일치**(같은 문구) | 불명 — 이미 실행 후 정리됐는지 FE는 모름 | 아니오 |
| `expired` | TTL 경과 | 이 요청은 실행 안 함 | 아니오 |
| `already_done` | 같은 `draftId`가 이미 실행됨 | **이전에 실행됨** | 아니오(중복 실행 안 한다는 계약) |
| `stale` | 초안 뒤 상품이 바뀌었거나 상품 없음 | 이 요청은 실행 안 함 | 아니오 |

- 넷 다 **HTTP 200 + `token` 안내 + `done{panel:"keep"}`** — `confirmStatus` 같은 구분 필드는 코드에 없음(감사 문서 §D-1이 제안만 함). 문구 파싱은 프로젝트 규칙상 금지 → **FE는 넷을 구분할 수 없음**
- 그래도 판단은 하나로 모임: **어느 경우든 같은 `draftId`를 다시 보내 성공할 길이 없음** → 넷 다 승인 버튼을 다시 열지 않음. 서버 안내는 말풍선에 그대로 남음
- ⚠️ 확인 필요: 감사 문서의 성공 응답은 `token` + `done{refresh}`로 **action이 없는데**, 현재 타입에는 `PRODUCT_UPDATED`가 있음. 지금 서버가 성공 시 action을 보내는지 미확인 → 아래 표에서 action 없는 `refresh`도 잠금으로 처리해 어느 쪽이든 재승인이 열리지 않게 함

### 상태

```ts
{ kind: "draft"; draft: SellerDraft; settled?: ChatAction; approval?: "pending" | "unknown" | "closed" }
```

| 상태 | 뜻 | 승인 버튼 | 카드 안내 |
|---|---|---|---|
| 없음 | 아직 승인 안 함, 또는 요청 전 실패 | 활성 | — |
| `pending` | 승인 턴 진행 중 | 비활성(처리 중) | — |
| `unknown` | 요청 시작 후 실패 — 처리 여부 불명 | **없음** | 상품 목록에서 반영 여부 확인 |
| `closed` | 서버가 action 없이 응답을 끝냄 | **없음** | 왼쪽 안내 확인 · 필요하면 초안 새로 요청 |
| `settled` (기존) | 서버가 action으로 결과 통보 | 없음 | 기존 결과 표시 |

### 상태 전이

| 사건 | 전 → 후 | 기록 지점 |
|---|---|---|
| 초안 도착(수정 턴 포함) | → 없음 — **새 `draftId`이므로 새 상태.** 턴의 첫 결과가 이전 초안을 교체 | 기존 `pushResult` |
| 승인 클릭 | 없음 → `pending`. **`unknown`·`closed`·`settled`면 `confirm`이 거부**(버튼 숨김과 별개인 훅 방어) | `confirm` |
| 티켓 확보 실패 등 요청 시작 전 실패 | `pending` → 없음 | `settleResend` |
| `action` 수신 | `pending` → `settled` | `settleDraft` — **이번 승인의 `draftId`로 지정**(지금은 `action`에 `draftId`가 없어 `productId`로 찾음) |
| action 없이 정상 종료 (`keep`·`refresh`·패널 없음) | `pending` → `closed` | `run` 정상 종료 |
| 요청 시작 후 실패(401·4xx·5xx·끊김·네트워크·SSE `error`) | `pending` → `unknown` | `settleResend` |
| **"초안 닫기"·취소** | 항목 삭제(`dropDraft`). `pending` 중엔 버튼 비활성. 닫아도 서버에 취소를 알리지 않음 → **처리 여부가 바뀌는 것은 아님** | 기존 |
| **초안 TTL 타이머**(등록 초안 10분) | 항목 삭제 | 기존 |
| **새 대화** | `reset`으로 항목 삭제. 버려진 승인 턴은 소유권 확인에서 막혀 기록하지 못함 | A 단위 |
| **새로고침·재진입** | 메모리에만 있어 **초안과 함께 사라짐**(진입 시 `startNewChat`) → 옛 카드로 재승인 불가. 처리 여부는 서버에만 남음 | 기존 |
| **화면 이탈(언마운트)** | `pending`인 채 abort → 재진입 시 위와 같이 비워짐. 방어로 "응답 중이 아닌데 `pending`"도 잠금 취급 | 카드 판정 |

### `draftId` 유일성 범위

| 범위 | 근거 | 설계에서의 사용 |
|---|---|---|
| 서버 | 서버 발급 UUID v4(계약 C-5) · 수정 턴마다 새로 발급, 이전 것 무효화 · 소유 검사 | 유일하다고 **가정은 하지만 의존하지 않음** |
| FE | 비교는 **현재 탭 스토어의 `results` 안에서만**. 저장·캐시·탭 간 공유 안 함 | 다른 대화·이전 세션의 값과 비교할 일이 없음 |
| 다른 턴 | 말풍선을 보지 않음 — 무관한 질문의 실패가 잠금을 만들지 않음 | |
| 다른 탭 | 탭 간 공유 없음 → **탭 사이 중복 승인은 막지 못함**(같은 초안이 두 탭에 있으려면 각자 받아야 해서 드묾. 서버 소유·멱등에 맡김 — 미확인) | 한계 |

### 등록·수정 카드 통일

`approval` 판정 함수 하나를 두 카드가 씀. 등록 카드의 `streamError` 표시는 다른 실패 안내용으로 남기되, **승인 버튼을 막는 판단은 `approval`만** 봄. 삭제는 수정 카드와 같은 컴포넌트라 함께 적용됨.

### 남는 한계 — 결정 필요

| 항목 | 내용 |
|---|---|
| `unknown` 뒤 새 초안 | 입력창은 살아 있어 "다시 만들어 줘" → **새 `draftId`** → 승인 가능. 첫 승인이 실제로 실행됐다면 **등록은 두 건**이 될 수 있음. `draftId` 단위로는 막을 수 없고 안내(상품 목록 확인)에 의존. 입력까지 막을지는 정책 결정 — AI 의견: 막지 않음(수정 요청이 유일한 복구 경로) |
| 패널 가림(I-3) | `done{keep}`·`refresh`는 패널을 목록으로 돌려 잠긴 카드가 안 보일 수 있음 — 잠금은 그대로 유지되며 표시는 I-3 몫 |

### 최소 수정 범위 · 회귀 테스트

## I-5 설계 v1 (폐기 — 기록용, 위 v2가 대체)

> 개발자 결정(02 #18): 별도 작업 · 우선순위 높음. **마지막 말풍선으로 오류를 판단하지 말고 draftId와 승인 요청의 관계를 명확히.**
> 분류: 새 범위 — [07-issues.md](07-issues.md) I-5 (프로브로 재현).

### 지금 방식의 문제

등록 카드의 오류 상태는 `streamError`(= **마지막 말풍선의 `error`**)에서 나옴([ChatPage.tsx](../../../src/features/seller/ChatPage.tsx) `streamError`). 그래서
- 다른 턴의 실패(예: 초안과 무관한 질문의 실패)가 초안 카드를 오류 상태로 만들 수 있고
- 같은 초안의 승인 실패라도 그 뒤에 다른 턴이 오면 오류 상태가 풀림
- 수정 카드는 아예 이 정보를 받지 않음(I-5)

### 설계 — 승인 상태를 **초안 결과 자체**에 둔다

```ts
// ChatResult 의 draft 항목에 선택 필드 1개
{ kind: "draft"; draft: SellerDraft; settled?: ChatAction; approval?: "pending" | "unknown" }
```

| 시점 | `approval` | 기록 지점 | 근거 |
|---|---|---|---|
| `confirm(draftId)` 시작 (첫 `await` 전) | `"pending"` | `run` (승인 턴) | 진행 중 표시 + **새로고침으로 끊기면 결과 불명**이라는 사실을 저장에 남김 |
| `action` 수신 (`PRODUCT_UPDATED`/`FAILED`) | 지움 → `settled` | 이벤트 핸들러의 기존 `settleDraft` | 서버가 결과를 알려줌 |
| 정상 종료했지만 `action` 없음 (서버가 안내 문구만 — `already_done`·`stale`·`expired` 등) | 지움 | `run` 정상 종료 | 서버가 응답을 끝냄. 다시 눌러도 서버가 같은 안내를 줄 것 — **확인 필요**(계약 감사 문서상 HTTP 200 + 안내 문구) |
| 요청 시작 **전** 실패 | 지움 | `settleResend` | 다시 해도 안전(H1) |
| 요청 시작 **후** 실패 · 중단(이탈) | `"unknown"` | `settleResend` · catch(abort) | 처리 여부 불명 |
| 새로고침 후 `"pending"`으로 복원 | `"unknown"`으로 취급 | 카드 판정 | 탭이 닫히는 동안의 결과를 모름 |

**카드 동작** — 등록·수정 카드가 **같은 판정**(`approval === "unknown"`, 또는 응답 중이 아닌데 `"pending"`)을 씀:
- "상품 등록"·"적용"을 감추고 확인 안내 + "초안 닫기"만
- 등록 카드의 기존 `streamError` 표시는 그대로 두되(다른 실패 안내용), **승인 버튼을 막는 판단은 `approval`만** 씀

### 영향 범위 점검

| 질문 | 답 |
|---|---|
| 다른 초안에 영향? | 판정 키가 `draftId` — 서버 발급 UUID, 수정 턴마다 새로 발급되고 이전 것은 서버가 무효화 → 다른 초안 카드와 섞이지 않음 |
| 다른 대화에 영향? | 초안 결과는 새 대화(`reset`)에서 비워짐 + `approval` 기록은 `run`·`settleResend` 안에서만 일어나고 둘 다 A 단위 소유권 확인 뒤 → 버려진 턴이 새 대화의 초안을 바꾸지 못함 |
| 다른 턴의 실패와 섞임? | 마지막 말풍선을 보지 않으므로 섞이지 않음 |
| 저장 호환성 | `results`는 대화와 함께 저장됨 → 옛 저장분은 `approval` 없음 → 종전 동작. 새로고침 후에도 `"unknown"`이 유지돼 잠금이 풀리지 않음 |

### 최소 수정 범위

`shared/types/chat`(`ChatResult` 선택 필드) · `store.ts`(`setDraftApproval`, `settleDraft`에서 지움) · `useChat.ts`(승인 턴 시작·종료·`settleResend`에 기록) · `ProductCreateCard.tsx`·`ProductDiffCard.tsx`(같은 판정으로 버튼 제한) · `SellerWorkspace.tsx`(전달). `retryPolicy`·`chatEventHandler`의 판정 로직은 바꾸지 않음.
