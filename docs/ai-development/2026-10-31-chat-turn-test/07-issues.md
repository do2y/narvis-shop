## I-2. 서버 처리 여부를 알 수 없는 실패 후 일반 발화 재시도 → 작업 중복 실행

| 구분 | 내용 |
|---|---|
| 발견 | Claude Code — H1 분석 중 코드 판독(02 #9). "불명확한 실패 후 무조건 재전송이 안전한가"라는 **개발자 질문**이 계기 |
| **확인된 사실** | ① 종결 없이 끊김(`StreamInterruptedError`)과 기타 네트워크 오류는 `retryable` 기본값 true로 재시도 버튼이 뜸([useChat.ts:287-298](../../../src/shared/chat/useChat.ts#L287-L298), [store.ts:192](../../../src/shared/chat/store.ts#L192)) ② 재시도는 같은 발화를 다시 보냄 ③ `dropLastExchange` 주석의 전제 "실패한 턴은 서버에 닿지 못했으므로"는 이 두 경우에 **성립하지 않음**([store.ts:209-211](../../../src/shared/chat/store.ts#L209-L211)) |
| **재현** | **재현하지 않음.** 서버가 작업을 실행한 뒤 스트림이 끊기는 상황을 만들려면 실제 서버(또는 그 동작을 흉내 낸 목)가 필요함 |
| 관련 — 해결 예정 | B4(위쪽 실패 말풍선 재시도가 **성공한** 마지막 질문을 재전송)는 이 위험을 성공 턴에서도 일으키는 경로였음 → 1단계에서 차단 예정([06-fix-plan.md](06-fix-plan.md)) |
| 잠재 영향 (가설) | "이거 담아줘" 턴이 서버에서 담기를 마친 뒤 응답이 끊기면, 재시도로 **한 번 더 담김**. 찜 추가·장바구니 수량 변경도 같은 구조. 실제 빈도는 모름 |
| 서버 측 확인 필요 | ① 장바구니·찜 액션이 요청 단위 멱등 키를 갖는지 ② `action` 이벤트를 커밋 직후 보내는지(끊김 시점과 커밋 순서) ③ 같은 threadId의 직전 발화와 동일한 재전송을 서버가 감지할 수 있는지 |
| 선택지 (미결정) | (가) 불명 실패에선 일반 발화도 버튼 대신 "장바구니를 확인한 뒤 다시 요청해 주세요" 안내 — 대부분 무해한 질문까지 불편해짐 (나) 서버 멱등 키 협업 (다) 액션성 발화만 구분 — FE가 의도를 알 수 없어 어려움 |

## I-3. 판매자 등록 초안 카드가 패널 상태 "auto"에서 가려짐

| 구분 | 내용 |
|---|---|
| 발견 | Claude Code — 1단계 최종 검토에서 판매자 카드 배선 테스트를 쓰다가(02 #13) |
| **확인된 사실** | 우측 패널은 `panelIntent`로 정해지고 `"auto"`일 때 `showResults = analysisLoading \|\| !!analysisReport` — **초안 카드는 조건에 없음**([ChatPage.tsx:143-146](../../../src/features/seller/ChatPage.tsx#L143-L146)). `"auto"`로 바뀌는 곳: `done{panel:"replace"}`의 `onDone`([:86-104](../../../src/features/seller/ChatPage.tsx#L86-L104)) · 입력창 전송 `sendFromInput`([:223-226](../../../src/features/seller/ChatPage.tsx#L223-L226)). 초안 도착 시 `"results"`로 켜는 것은 이펙트([:126-134](../../../src/features/seller/ChatPage.tsx#L126-L134)) |
| **재현** (jsdom, 화면 전체 렌더) | 초안 턴의 프레임(`meta`·`token`·`draft`·`done{replace}`)을 **한 청크**로 보내면 카드가 보이고, **프레임마다 청크를 나누면 카드가 보이지 않음** — `draft` 뒤 렌더·이펙트가 먼저 `"results"`로 켜고, 이어 온 `done`이 `"auto"`로 덮음. 또 초안 검토 중 입력창으로 수정을 보내면 그 턴 동안 카드가 가려지고, 그 턴이 실패하면 계속 가려진 채 남음 |
| 재현 안 된 것 | 브라우저·실제 서버 — 서버가 `draft`와 `done`을 한 번에 flush하는지, 브라우저에서 두 프레임 사이에 렌더가 끼는 빈도 |
| 잠재 영향 | 판매자가 초안을 받았는데 우측에 카드가 안 뜸 / 수정 요청 실패 후 카드를 다시 볼 방법이 "목록으로"·탭 전환뿐 |
| 서버 측 확인 | `draft`와 `done`의 전송 간격·flush 단위 |
| 수정 방향 (제안만) | `"auto"` 파생에 "확정 전 초안이 있으면 결과 표시"를 포함하거나, `onDone(replace)`에서 이번 턴에 초안이 왔으면 `"results"` 유지 |

## I-4. 판매자 등록 카드의 "다시 시도"가 재시도 가능 여부를 보지 않음

| 구분 | 내용 |
|---|---|
| 발견 | Claude Code — 1단계 최종 검토(02 #13) |
| **확인된 사실** | `ProductCreateCard`는 `onRetry`가 주어지면 오류 상태에서 항상 버튼을 그림([ProductCreateCard.tsx:304-330](../../../src/features/seller/components/ProductCreateCard.tsx#L304-L330)) — 말풍선과 달리 `retryable`을 보지 않음. 오류 상태는 ① 마지막 말풍선의 `error`(`streamError`) 또는 ② `settled`가 `PRODUCT_UPDATE_FAILED` |
| 1단계 이후 동작 | ① `retryable:false`(403·409·429 등) → 카드 버튼은 보이지만 `retry(id)`가 거절 → **아무 일 없음** ② 서버가 등록 실패를 `action`으로 알린 경우 마지막 말풍선엔 `error`가 없음 → `retry(id)`가 거절 → **아무 일 없음** |
| 1단계 이전 동작 | ② 에서 `dropLastExchange`가 실패 여부를 보지 않아 **등록 실패 안내가 담긴 말풍선을 지웠음** — 1단계로 "지움 → 아무 일 없음"이 됨(파괴적이지 않게 됐지만 버튼은 여전히 무의미) |
| 재현 | 코드 판독. ①은 1단계 훅 가드 테스트(`retryable:false`)로 간접 확인. 카드 렌더 테스트로는 미확인 |
| 수정 방향 (제안만) | 카드 버튼 노출을 `retry`가 받아들일 조건(마지막 말풍선이 실패 · `retryable !== false`)과 같게 — H1 2단계에서 승인 턴 재시도 정책을 정할 때 함께 다루는 것이 자연스러움(승인 실패는 대부분 이 카드에서 일어남) |
