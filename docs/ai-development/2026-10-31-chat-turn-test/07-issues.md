## I-3. 판매자 등록 초안 카드가 패널 상태 "auto"에서 가려짐

| 구분 | 내용 |
|---|---|
| 발견 | Claude Code — 1단계 최종 검토에서 판매자 카드 배선 테스트를 쓰다가(02 #13) |
| **확인된 사실** | 우측 패널은 `panelIntent`로 정해지고 `"auto"`일 때 `showResults = analysisLoading \|\| !!analysisReport` — **초안 카드는 조건에 없음**([ChatPage.tsx:143-146](../../../src/features/seller/ChatPage.tsx#L143-L146)). `"auto"`로 바뀌는 곳: `done{panel:"replace"}`의 `onDone`([:86-104](../../../src/features/seller/ChatPage.tsx#L86-L104)) · 입력창 전송 `sendFromInput`([:223-226](../../../src/features/seller/ChatPage.tsx#L223-L226)). 초안 도착 시 `"results"`로 켜는 것은 이펙트([:126-134](../../../src/features/seller/ChatPage.tsx#L126-L134)) |
| **재현** (jsdom, 화면 전체 렌더) | 초안 턴의 프레임(`meta`·`token`·`draft`·`done{replace}`)을 **한 청크**로 보내면 카드가 보이고, **프레임마다 청크를 나누면 카드가 보이지 않음** — `draft` 뒤 렌더·이펙트가 먼저 `"results"`로 켜고, 이어 온 `done`이 `"auto"`로 덮음. 또 초안 검토 중 입력창으로 수정을 보내면 그 턴 동안 카드가 가려지고, 그 턴이 실패하면 계속 가려진 채 남음 |
| 재현 안 된 것 | 브라우저·실제 서버 — 서버가 `draft`와 `done`을 한 번에 flush하는지, 브라우저에서 두 프레임 사이에 렌더가 끼는 빈도 |
| 잠재 영향 | 판매자가 초안을 받았는데 우측에 카드가 안 뜸 / 수정 요청 실패 후 카드를 다시 볼 방법이 "목록으로"·탭 전환뿐 |
| 서버 측 확인 | `draft`와 `done`의 전송 간격·flush 단위 |
| 수정 방향 (제안만) | `"auto"` 파생에 "확정 전 초안이 있으면 결과 표시"를 포함하거나, `onDone(replace)`에서 이번 턴에 초안이 왔으면 `"results"` 유지 |
| 상태 | 2026-10-31 별도 UI 결함으로 유지 → 2026-11-05 수정 승인 (**기존 결함이지만 I-5 사용자 흐름에 직접 영향**) → **데스크톱 레이아웃 개선 `4e96d7c`** → [03 §14](03-validation.md). **전체 해결 아님** — 모바일 접근 불가(I-8) · 돌아갈 입구 없음(I-9) · 브라우저 미검증 |

**원인 — 왜 청크 분할 방식에 따라 결과가 달라지나** (AI 분석, jsdom 재현)

| 단계 | 한 청크 (`draft`·`done`이 같은 `read()`) | 여러 청크 (`draft`·`done`이 다른 `read()`) |
|---|---|---|
| 1 | 파서가 한 청크 안의 프레임을 **동기 루프**로 연달아 처리 → `draft`(결과 추가)와 `done`(`onDone` → `setPanelIntent("auto")`)이 렌더 없이 이어짐 | `draft` 처리 → 다음 `read()`를 `await` — **이 사이에 React가 렌더·이펙트를 실행** |
| 2 | 렌더 → 초안 수 증가 이펙트가 `"results"`로 켬 (**마지막에 실행**) | 초안 수 증가 이펙트가 `"results"`로 켬 |
| 3 | 최종 `"results"` → 카드 보임 | 다음 청크의 `done` → `"auto"`로 **덮음** → 최종 `"auto"` → `showResults`에 초안 조건이 없어 카드 가려짐 |

근본 원인: 패널 상태를 **두 경로(이벤트 핸들러의 `onDone`과 렌더 후 이펙트)가 순서 보장 없이** 쓰는데, 실행 순서가 네트워크 청크 경계에 따라 뒤바뀜. 또 `"auto"` 파생 조건이 초안 카드를 모름.

**범위 확장 (2026-11-04, Claude Code · jsdom 재현 · 새 범위)**: 패널은 초안 **수가 늘 때만** 결과로 전환함(`draftCount` 이펙트). 수정 턴의 새 초안은 이전 초안을 **교체**해 수가 그대로라 **카드가 보이지 않음**. I-5의 경고·승인도 이 경로에선 닿지 않음 — `closed`·`unknown` 초안이 남아 있으면 새 초안을 승인할 수 없음.

**추후 수정 시 필수 검증**: 같은 시나리오를 **한 청크 / 프레임별 청크 / `draft`와 `done` 사이에만 경계**의 최소 3가지로 돌려 모두 카드가 보여야 함. 현재 판매자 `ChatPage.test.tsx`는 이 결함을 피하려고 한 청크로만 보냄(주석 명시) — 수정할 때 이 우회를 걷어내고 다중 청크 케이스를 추가할 것. 입력창 전송(`sendFromInput`) 직후 수정 턴이 실패하는 경로도 함께 검증.

## I-6. 스트림 시작 401의 자동 재시도가 판매자 승인에도 적용됨 — **기존 동작의 안전성 결함**

> 분류: **새 범위** — T1 이전부터 있던 동작(회귀 아님). 다만 H1 2단계에서 정한 정책("요청을 시작한 뒤의 실패는 상태 코드와 무관하게 처리 여부 불명")과 **어긋남**. 고치려면 정책 결정이 필요 → 제안만, 승인 대기.

### 확인된 사실

| 항목 | 내용 | 근거 |
|---|---|---|
| 401이 나는 경로 | `run` → `ensureSession`이 **25초 이내** 캐시 티켓을 재사용(`TICKET_TTL_MS`) → `streamChat`이 `llmSseUrl`로 `POST` + `Authorization: Bearer <streamTicket>` → AI 서버가 티켓 검증 실패 시 **401** (`TOKEN_EXPIRED` 만료 / `TOKEN_INVALID` 서명·형식·scope·없음) | [sessionCoordinator.ts](../../../src/shared/chat/sessionCoordinator.ts) · [streamChat.ts](../../../src/shared/chat/streamChat.ts) · 계약 감사 문서 §4.1·오류표 |
| 언제 생기나 | 티켓 TTL 30~60초인데 캐시는 최대 25초 묵은 티켓을 씀 → 남은 수명이 짧은 티켓 + 지연·시계 차이 / 서버 키 교체 | [chat.md](../../architecture/chat.md) "티켓 TTL" |
| 자동 재전송되는 것 | **처음과 똑같은 body**(`sessionId`·`threadId`·`action:"confirm"`·`draftId`)를 새 티켓으로 **1회 자동 전송**. 사용자에게 보이지 않음 | **프로브 P1 재현**: 등록·수정 모두 `ticket-1` → `ticket-2`, body 동일 → [probe-round3-401-i5.json](probes/probe-round3-401-i5.json) |
| 영향 범위 | 판매자 승인 전부(등록 `create`·수정 `update`·삭제 `delete` — 같은 `confirm` 경로) · 일반 발화(장바구니 담기 등)·칩 제거도 같은 경로 | `useChat.ts` 401 분기 |

### 401일 때 승인이 실행됐을 가능성

- **계약 감사 문서 근거로는 "실행 전"**: 401은 AI 서버의 `deps.get_identity`(엔드포인트 **의존성**)에서 남 → 승인 처리(`_seller_stream`의 confirm 레인 → I-10/11/12)는 엔드포인트 본문이라 그 뒤에 실행됨. "`meta`조차 못 받는다"(§4.1)
- **그러나 확정할 수 없음**: ① 근거가 **2026-07-22 감사 문서(AI 서버 v0.4.0 코드)** 이고 archive에 보관된 것 — 현재 서버 코드 미확인 ② 상태 코드 401만으로는 판단하지 않음(개발자 지시) — 위 근거는 상태 코드가 아니라 "검증 위치가 의존성"이라는 코드 위치 서술에 기댐 ③ ALB 등 중간 계층의 401 가능성은 확인 안 함

### 중복 실행 방지 — 서버 측 보장

| 보장 | 내용 | 확인 수준 |
|---|---|---|
| 인증이 실행보다 먼저 | 위 | 감사 문서(구버전) |
| 승인 멱등 | 같은 `draftId` 재전송 → `already_done` "이미 처리된 승인 요청입니다 — 중복 실행하지 않았습니다"(HTTP 200) | 감사 문서(구버전) |
| 둘 다 유지된다면 | 중복 실행은 없음. 다만 두 번째가 `already_done` 안내로 끝나면 FE는 `PRODUCT_UPDATED` action을 못 받아 **카드가 "완료"로 바뀌지 않음**(미확인) | — |
| 둘 다 깨졌다면 | **같은 상품이 두 번 등록·수정·삭제될 수 있음** | — |

### FE 정책 선택지 (제안 — 승인 대기)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| O1 유지 | 감사 문서 근거로 현행 유지, 한계만 기록 | 변경 없음 | 개발자 지시 ①과 불일치 유지 · 서버 미확인 |
| O2 승인만 자동 재시도 끔 | 승인 턴은 401도 "요청 시작 후"로 보고 확인 안내·버튼 없음 | H1 정책과 일관 | **가장 흔한 무해한 실패(티켓 만료)에서 판매자가 막힘** — 초안을 닫고 다시 만들어야 함 |
| **O3 (추천) 예방 + 승인 자동 재시도 끔** | ① 승인 턴은 전송 직전에 **티켓을 강제 재발급**(캐시 무시 — 남은 수명 ≈ TTL 전체) → 만료 401을 사실상 없앰 ② 그래도 401이면 자동 재시도하지 않고 O2처럼 처리 | 정책 일관 + 흔한 실패를 예방으로 제거 | 승인마다 BE 재발급 1회 추가(승인은 드문 동작). 키 교체 등 `TOKEN_INVALID`는 여전히 막힘(드묾) |

O3 최소 변경(제안): `useChat.ts`의 `run`에서 `resend?.kind === "confirm"`일 때 ① `acquireTicket` 대신 `refreshTicket(channel, sessionId)` ② 401 분기 진입 조건에 `resend?.kind !== "confirm"` 추가. 회귀 테스트: 승인 401 → 자동 재전송 없음·확인 안내 / 승인 전 티켓 강제 재발급 / 일반 발화 401 재시도는 종전대로.
일반 발화(I-2)·칩 제거는 이번 안에서 건드리지 않음.

### 서버 측에 확인할 것
1. 현재 AI 서버에서 티켓 검증이 여전히 엔드포인트 의존성(본문 실행 전)인지
2. 승인 `already_done` 멱등이 현재도 유지되는지 · 그 경우 FE가 받을 이벤트(`action`인지 `token`인지)
